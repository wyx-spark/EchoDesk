## 1. 审计结论

`backend/conversation.py` 的 `MODES` 原有 6 个模式，每个只有**一句话**（平均约 30 字符）。
对照任务书给的 6 个设计维度（角色具体化 / 输出格式约束 / 思维链引导 / 少样本示例 /
边界声明 / 与任务匹配的语气）逐个审计：

| 模式 | 原提示词（全文） | 缺失维度数 | 具体问题 |
| --- | --- | --- | --- |
| `general` | 你是一个通用AI助手，可以回答各种问题。 | **5**（格式/思维链/示例/边界/语气） | 角色笼统；无输出约束，小模型爱写开场白、爱复述问题；没有"不知道就说不知道" |
| `summary` | 你是一个专业的摘要专家，擅长简洁准确地总结文本、会议记录、文章等。请提供清晰、有层次的摘要。 | **4**（思维链/示例/边界/语气） | "清晰、有层次"不可判定；没有条数/字数上限；没有"数字、日期、金额原样保留" |
| `translate` | 你是一个翻译专家，精通多国语言。请根据用户要求进行准确流畅的翻译。 | **5** | 没说"只输出译文"；没说术语与专有名词怎么处理；没有"不擅自增删" |
| `code` | 你是一个编程专家，擅长多种编程语言。请提供代码、解释、调试建议等。 | **5** | 没有"结论 → 最小修改片段 → 验证方法"的结构；没有"不要编 API" |
| `contract` | 你是一个专业的合同审查与摘要助手。请根据用户需求，结合提供的文件内容进行回答。 | **5** | 没限定看哪几类条款；**没要求摘录原文**——而这正是小模型最容易编造条款的场景；没有"未见相关约定，不要臆测" |
| `creative` | 你是一个创意写作助手，擅长生成故事、诗歌、剧本等创意内容。 | **5** | 没有体裁/视角/基调要求；没有"不套用知名作品句子"的边界 |

**共性结论**：6 个模式都只有「角色」一项，且其中 5 个连角色都很笼统（"专家""助手"）；
只有一个模式带一点点语气暗示（"准确流畅""清晰、有层次"都不可判定）。
对比 `backend/prompts.py` 的任务模板（role / format / cot / examples 四要素齐备，
且本轮修掉了模板与模式重复的 4 个主题：summary / contract / translate / code），
**模式提示词的约束力明显低一个档次**——而模式是"默认就在生效"的那一层，
用户不敲 `/task` 时全靠它。

> 实测印证见 §5.3：同一份合同、同一个问题，旧提示词产出 500 token 的议论文且
> 编造了原文没有的"惩罚性赔偿"要求；新提示词按格式给出逐条摘录与建议，421 token 收尾。

## 2. 机制选择与理由

任务书要求评估三条路线并给出选择：**统一** / **模式映射到模板** / **保持独立但同等完整度**。

### 2.1 候选与结论

| 路线 | 结论 | 理由 |
| --- | --- | --- |
| ① 统一成一套机制 | **不选** | 两者的**生命周期与覆盖面不同**：模式是常驻场景（每轮都生效，`/mode` 切换），模板是一次性配方（`/task` 套用）。集合也不重合——`general`/`creative` 没有对应模板，`extract`/`reason` 没有对应模式。强行合并会造出假等价：要么给 general 编一个模板，要么让 `extract` 的"只输出 JSON"变成通用模式的默认行为，两者都错 |
| ② 模式映射到模板 | **不选** | `summary`/`translate`/`code`/`contract` 确实可映射，但 `general`/`creative` 无模板可映射；映射后 `/mode` 会退化成"模板别名"，失去"常驻场景"的语义；且要让模式具备任务级格式（如 JSON 抽取），又会污染默认场景 |
| ③ **保持两套机制，模式提升到同等完整度，且两者叠加** | **选它** | 职责清晰：**模式 = 场景与语气**，**模板 = 本轮的具体输出格式**。可以组合（合同模式 + 推理模板），不产生假等价。执行上补两件事：任务层末尾加 `[优先级]` 裁决行（冲突时以模板为准）；全局纪律放进共享主干 |

### 2.2 顺带修掉的两个机制缺陷（审计中间接发现）

1. **`/task` 会顶掉模式提示词。** `_task` 把模板写进 `conv_mgr.custom_prompt`，而
   `get_system_prompt()` 里 `custom_prompt` 优先、直接跳过 `MODES` —— 于是模板是
   **替换**模式而不是叠加，与 `prompts.py` 文件头自称的"模板是附加在系统提示词后面
   的，不替换对话模式"**直接矛盾**（注释与实现不一致，且文档 `USER_GUIDE` 把
   "覆盖"当成既定行为写了下来）。现在任务层与自定义指令**分开存放**（新增
   `ConversationManager.task_prompt`），模板叠加在模式之上。
2. **`/task off` 会顺手清掉用户的 `/prompt`。** 原实现里两者共用 `custom_prompt`，
   于是"取消任务模板"把用户手写的自定义指令一起删了。现在 `/task off` 只清 `task_prompt`，
   并在自定义指令仍在时明确提示（新增语言键 `cmd.resp.task_cleared_keeps_prompt`）。
3. **`/prompt` 的包装语自相矛盾。** 原措辞是"不要解释，**不要反问**，不要偏离"，
   而模糊提问检测（`prompts.is_vague_question` → `task.clarify_prompt`）与 `reason`
   模板都要求"信息不足时先追问"。现在改为"不要解释、不要偏离；**但用户提供的信息
   不足以作答时，应先问清最关键的一点**"。

## 3. 重写方案

### 3.1 结构：六要素 + 共享主干

每个模式块统一写成带标签的五行（便于脚本检查，也便于模型抓重点）：

```
【角色】…      ← 具体到职务与关注范围，不是"专家"
【输出格式】…  ← 结构、条数/字数上限、要不要复述
【思维】…      ← 先做什么再做什么（给小模型外部脚手架）
【示例】…      ← 一组极简"输入 → 输出"（对小模型比描述更有效）
【语气】…      ← 与该场景匹配的语气
```

第六项**边界**（不知道就说不知道 / 信息不足先问清 / 不编造出处）与视角澄清、
输出纪律一起放在共享主干 `_CORE_RULES` 里，所有模式复用：

* **为什么共享**：这三条与场景无关。写 6 遍既白占上下文（0.8B 模型对冗长提示词更敏感），
  又会在改动时只改到一两处、留下 5 处不一致——正是任务书要求避免的"矛盾指令"。

### 3.2 关键措辞的取舍（都是为了让 0.8B 模型能执行）

| 取舍 | 做法 | 依据 |
| --- | --- | --- |
| 数量上限 | 摘要"≤ 8 条、每条 ≤ 40 字"；合同逐项列 | "简洁一点"这类相对词小模型无法执行；给硬上限才可判定 |
| 示例只给 1 组 | 每个模式 1 组，10~60 字 | 示例对格式遵循度提升最大，但每多一组就多占上下文；1 组足以示范格式 |
| 合同必须摘录 | "摘录必须与原文逐字一致""找不到写『未见相关约定』" | 合同审查是小模型最易编造的场景；要求摘录等于强制其引用可核查的原文 |
| 思维链只给 1 步 | 如"先按时间—主体—动作—结果梳理" | 0.8B 模型给多步会自己乱序；只给一个明确的先后关系最稳 |
| 允许说"不确定" | 主干与合同块都明确写 | 宁可让模型承认不确定，也不要它硬答（幻觉比"不知道"更有害） |

### 3.3 长度预算（完整度 vs 长度的取舍依据）

| 项 | 上限（字符） | 实测区间 |
| --- | --- | --- |
| 单个模式块 | 480 | 209 ~ 313 |
| 模式块 + 共享主干 + 语言指令 | 700 | 417 ~ 521 |

依据：默认 `context_length` 为 **8192 token**（`config.json`；模型训练窗口 32768，
`auto_context` 会按硬件上调）。中文按约 1 字符/token 量级估算，700 字符约占 **8.5%**，
余量留给文件摘要（`max_summary_tokens=400`）与 10 轮对话历史。上限由
`tools/test_capability.py` 第 9 节断言守住，以后加大模式提示词会立刻失败。

## 4. 多语言化：实现方式与体积影响

### 4.1 提示词正文：保持中文、不进语言包（沿用既有约定）

`conversation.py` 与 `prompts.py` 的文件头本来就写明这条约定：正文是**发给模型的内容**，
不是界面文本；译成英文会削弱这些针对小模型跑偏设计的措辞。本次**维持**该决定，
并在注释里把"正文语言"与"回复语言"两件事讲清楚（见下）。

### 4.2 回复语言：改为跟随界面语言（本次的唯一行为变更）

**问题**：原实现把 `请始终使用简体中文回复。` 写死在提示词里 —— 界面切成 English 的用户
仍然只收到中文回复，界面的双语化在"产出"这一侧是断的。

**改法**：新增 `_REPLY_LANGUAGE` 表 + `reply_language_instruction()`，按 `i18n` 当前
locale 取指令：

| 界面语言 | 发给模型的指令 |
| --- | --- |
| `zh-Hans` | 请始终使用简体中文回复，不要输出繁体字。 |
| `en` | Always reply in English. |
| 其它（社区语言包） | 请使用与用户提问相同的语言回复。 |

**未内置语言的处理**：不替用户选语言，交给模型跟随提问语言；社区新增语言包**无需改代码**。

**载体选择**：这 2 条英文/中文指令是**模型指令**而非界面文案，按既有约定不以语言包键存放
（否则会出现"语言包缺键 → 回退成中文指令 → 英文用户又收到中文"的隐式故障）。

### 4.3 界面说明与提示词正文脱钩

语言包的 `mode.desc.*` 原先**就是**模式提示词那句话（一字不差）。重写正文后若继续共用，
`/mode list` 会把整段提示词（含示例）打到对话框里。现在 `mode.desc.*` 改为
**面向用户的短句**（21~30 字符，如"合同条款审查：只关注钱、时间、责任三类风险，逐条摘录原文"），
与正文彻底分开，并在语言包里用 `_note` 注释键向翻译者说明二者关系。

### 4.4 体积与上下文影响

* **语言包体积**：仅新增 5 个短键（`prompt_overrides_task` / `prompt_reset_restores_task` /
  `task_cleared_keeps_prompt` / `task_overridden_by_prompt` / `status.custom_prompt`），
  两种语言各一份，合计数百字节；提示词正文**不进语言包**，所以语言包总量基本不变。
* **上下文长度**：正文仍是中文，中文界面下长度不变；英文界面下语言指令由
  `请始终使用简体中文回复，不要输出繁体字。`（19 字符）换成 `Always reply in English.`（26 字符），
  净增 7 字符（约 7 token），可忽略。
* **后备语言**：未知 locale 的指令略长（22 字符），同样可忽略。

### 5.1 结构与长度断言（`tools/test_capability.py` 第 9 节，新增 39 项）

### 5.3 实际效果抽查（旧 / 新提示词各跑一次）

方法：脚本 `artifacts\ab_prompts.py`——旧提示词**从 git 直接取**
（`git show HEAD:backend/conversation.py`，不手工复述），同一进程、同一模型
（`Qwen3.5-0.8B-Q4_K_M`，`n_ctx=8192`）、同一份文件、同一个问题、同一组生成参数
（contract 模式温度 0.3，`max_tokens=500`），**只换系统提示词**。

* 输入：一段采购合同节选（交付 60 日、验收合格后 30 个工作日付款、逾期日 0.3% 违约金；
  刻意**未约定验收期限**）
* 问题：审查这份合同的付款与交付条款，指出其中的风险。
* 旧系统提示词 167 字符；新系统提示词 561 字符。

| 维度 | 旧提示词（14.5s，500 token，**触顶截断**） | 新提示词（12.1s，421 token，自然收尾） |
| --- | --- | --- |
| 输出格式 | 未遵循任何指定结构，写成议论文（"### 1. 付款节点过于紧迫（核心风险点）"） | 按「付款条件／交付期限／违约责任／争议解决／缺失条款」组织，每条含原文摘录 → 风险 → 建议 |
| 原文依据 | 把"合同总额（即 128.6 万元）"当成"违约金基数门槛"自行发挥 | 逐字引用"第四条 甲方应在收到全部货物并验收合格后 30 个工作日内支付合同价款" |
| 是否编造 | 编造了原文没有的"缺乏惩罚性赔偿"要求 | 未编造；对不确定处写"该条款是否适用需人工确认" |
| 边界意识 | 无 | 明确指出"未约定验收期限"这一**真实缺失**，并给出可落地的补充条款 |
| 长度控制 | 500 token 触顶被截断，内容不完整 | 421 token 自然结束，结构完整 |

结论：新提示词在**格式遵循、原文可核查、保守语气、长度控制**四项上都有可观察的改善，
且改动可归因（唯一变量是系统提示词）。

## 7. 与任务书的偏差、未完成项与需确认事项

### 7.1 偏差

1. **记录文件位置**：任务书写 `docs/v0.2.1-提示词优化记录.md`，实际落在
   `records/v0.2.1-提示词优化记录.md` —— 因为 v0.2.1 期间维护者已把全部 `*记录.md`
   移入仓库根目录的 `records/`，新建记录放在 `docs/` 会与该约定冲突。
   （同时把 `check_feedback.ps1` 的过程文档排除规则扩到新文件名，否则门禁会重新
