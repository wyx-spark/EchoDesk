## 2. 修复一：开发者模式弹窗循环与无法关闭（P0）

### 2.1 排查结论（三条主诉分别对应三个独立缺陷）

任务书给了三条排查方向，实测**三条都成立**，而且是三个独立的代码问题：

1. **弹窗循环**：`SettingsWindow.CheckTrustPending()` 每发现一个 `trust_pending` 的插件就
   弹一次 `MessageBox`，答完 `break` 再触发 `LoadSkillsAsync()` → 又检查一轮 → 再弹下一个。
   N 个未确认插件就是 N 次弹窗。
2. **无法关闭**：`SkillLoader.dev_mode` 的实现是
   `return cfg.dev_mode or bool(self._scan_dev_dirs())` —— 只要 `skills_dev/` 目录里还有插件
   （而随包示例插件就在那里），用户关掉开关后后端 `status.dev_mode` 立刻又返回 `True`，
   前端 `SyncDevModeCheck()` 把复选框重新勾上。**开关被"自动检测"逻辑吃掉了。**
3. **重复询问**：`trust_pending = id not in trusted`。用户点"否"只会让 `trust_plugin(id, False)`
   把 id 从 `trusted` 里移除（本来就是空的），于是下次启动**再问一遍**，永远问下去。

### 2.2 改法

**批量确认（一次汇总框）**

新增 `frontend/Utilities/TrustDialog.cs`：一次列出全部待确认插件，每项显示来源、路径、
它声明要用的能力（commands / parsers / hooks / panels）、声明的权限，以及一句明确告警
（"插件代码会在本机以你的权限运行，无法限制它能访问什么"）。提供
**逐个勾选 / 全部启用 / 全部禁用 / 确定 / 取消**。后端新增 `skills_trust_bulk` 动作一次性
接收全部决定。

**记忆选择（含"明确拒绝"）**

`skills_local.json` 的 schema 从 1 升到 2，新增 `denied` 列表：

```json
{ "schema": 2, "plugins": [], "trusted": ["..."], "denied": ["..."] }
```

`trust_plugin(id, trusted)` 同时维护两个列表（启用→进 trusted 出 denied，禁用反之）。
`trust_pending` 改为 `id not in trusted and id not in denied and not builtin`。
旧文件没有 `denied` 字段时按空列表读入，向后兼容已由测试覆盖。

**可关闭（双向可用）**

配置新增 `dev_mode_explicit: bool = False`：

* `False`（从未设置过）→ 沿用"`skills_dev/` 里有插件就自动启用"的开箱即用行为；
* `True` → **完全以 `dev_mode` 为准**，关就是关。

后端 `skills_set_dev_mode` 在写入时同时置 `dev_mode_explicit = True`，并在关闭时执行四件事：
① 记录显式设置；② `unload_dev()` 卸载全部 dev/local 插件并从指令表移除；
③ 停止热重载（`dev_mode` 为假后 dev 目录不再参与发现）；④ 清空 `skills_dev.log`。

**内置插件静默**

新增 `SkillLoader.builtin_ids()`：从**随包 `examples/skills/` 目录里实际存在的插件**读取 id
集合，这些插件默认启用且不弹确认框。刻意**不采用**"插件自己在 skill.json 里声明 official"
的做法 —— 任何插件都能自报为官方，那等于把确认框变成摆设。第三方插件放进 `skills_dev/`
仍会被要求确认。

**状态可见**

`status()` 新增 `dev_mode_explicit` / `dev_detected` / `dev_enabled` / `dev_count` /
`trust_pending_ids` / `builtin_ids`；设置窗口「开发者」Tab 新增两个文本控件
（`DevModeStatusText` 说明"开关由谁决定"，`DevPluginListText` 列出当前已启用的开发插件）。
关闭后该清单为空，用户能直接确认"确实关掉了"。

### 2.3 验证

`tools/test_dev_mode.py`（46 项，全通过）逐条覆盖任务书的三个验收方式：

| 任务书验收项 | 对应断言 |
|---|---|
| 放入 3 个以上插件只弹一次汇总确认框 | 待确认清单一次取全、且只含第三方插件；内置插件不进清单 |
| 关闭开发者模式后插件被卸载、不再弹窗、开关状态正确 | 显式关闭后 `dev_mode` 必为假；`unload_dev()` 后无已加载的 dev 插件 |
| 重启后已确认过的插件不再重复询问 | 重建 `SkillLoader`（模拟重启）后待确认清单为空，已信任的仍加载、被拒绝的仍不加载 |

## 3. 修复二：深色模式失效与对比度不足（P0）

### 3.1 根因（两个独立缺陷）

1. **深色永远出不来**：`MainWindow_Loaded` 里写的是
   `if (!_settings.DarkMode) ApplyTheme(false);` —— 只有"配置为浅色"时才应用主题。
   配置为深色（默认值就是 `true`）时，`App.xaml` 合并进去的 `Theme.Light.xaml`
   **原样留着**，于是启动永远是浅色。字段 `_isDark` 也从未与 `_settings.DarkMode` 对齐过。
2. **一半控件不跟主题**：原色板只有 10 个键（`WindowBackground`/`TextForeground`/`AccentBrush`…），
   `Styles.xaml` 只给 `TextBlock`/`Button`/`TextBox` 三种控件设了颜色。
   `ComboBox`、`ListBox(Item)`、`TabControl(TabItem)`、`CheckBox`、`RadioButton`、`ScrollBar`、
   `ToolTip`、`ContextMenu`、`ProgressBar`、`RichTextBox` 全都走 WPF 默认的浅色 Aero2 模板，
   深色下表现为"白块"；`MarkdownRenderer` 里的画刷与字体也是**硬编码**的
   （`#2b2b2b` 代码块背景等），主题切换后旧消息不会变。

### 3.2 改法

**统一色板（47 个键，深浅两套键名必须完全一致）**

| 组 | 键 |
|---|---|
| 背景与表面 | `WindowBackground` `SurfaceBrush` `SurfaceAltBrush` `InputBackground` `InputBorder` `FocusBorder` `SeparatorBrush` |
| 文字 | `TextForeground` `SubTextBrush` `DisabledTextBrush` `InverseTextBrush` |
| 强调 | `AccentBrush` `AccentForegroundBrush` `AccentHoverBrush` `AccentPressedBrush` `LinkBrush` |
| 状态语义 | `SuccessBrush` `WarningBrush` `ErrorBrush` `InfoBrush` |
| 按钮四态 | `ButtonBackground` `ButtonHoverBackground` `ButtonPressedBackground` `ButtonDisabledBackground` `ButtonBorder` `ButtonForeground` `ButtonDisabledForeground` |
| 选中与列表 | `SelectionBackground` `SelectionForeground` `RowHoverBackground` |
| 页签 | `TabActiveBackground` `TabInactiveBackground` |
| 滚动条 | `ScrollBarThumbBrush` `ScrollBarTrackBrush` |
| 浮层 | `MenuBackground` `MenuForeground` `MenuHighlightBackground` `TooltipBackground` `TooltipForeground` `TooltipBorder` |
| 对话角色 | `UserBrush` `AssistantBrush` `SystemBrush` |
| Markdown | `CodeBackground` `CodeForeground` `QuoteForeground` `MessageBorderBrush` |

`Styles.xaml` 为上述所有控件类型补齐了模板（含 `ComboBox` 的 `PART_Popup`、
`ScrollBar` 的 `PART_Track` 这类必须命名的部件），**全部用 `{DynamicResource}`**，
并把主题状态收敛到新的 `frontend/Services/ThemeService.cs`。

**"跟随系统"与三态设置**

`AppSettings.Theme` 取代旧的 `DarkMode` 布尔（保留旧字段仅用于读旧文件并迁移）；
设置窗口的复选框换成 `ThemeCombo`（跟随系统 / 浅色 / 深色），选"跟随系统"时
`ThemeStatusText` 会明确写出当前实际生效的是哪一种。`ThemeService.HookSystemChanges()`
订阅 `SystemEvents.UserPreferenceChanged` 并重新读注册表
`HKCU\...\Themes\Personalize\AppsUseLightTheme`，系统切换时自动跟随。持久化在 `ui_state.json`。

**"切换后无残留旧色"**

关键改动是**取色方式**：原来代码里用 `TryFindResource("SubTextBrush")` 取的是
**取值快照**，切主题后已渲染的消息气泡会保留旧色。现在：

* 新建的控件一律走 `ThemeService.Bind(element, Property, "色板键")`（即
  `SetResourceReference`），主题字典一换自动重绘；
* `MarkdownRenderer` 里 `Paragraph`/`Run`/`Span`/`Hyperlink`/`Table`/`TableCell` 都是
  `FrameworkContentElement`，同样支持资源引用，因此**不需要**重建文档就能跟随主题
  （原文 Markdown 并没有保留，重建本来也做不到）；
* 插件卡片的状态色等"必须把画刷当值传出去"的场合，改为按色板键取值 +
  主题变化时重建列表（`SettingsWindow.ApplyThemeResources`）。

### 3.3 对比度：从"看着还行"变成"可自动判定"

新增 `tools/check_theme.py`，做三件事：

1. **色板一致性**：两套主题键名集合必须相同（缺键 = 切主题后残留默认色）；
2. **WCAG 对比度**：按 WCAG 2.1 相对亮度公式复核 **43 组强制**"文字/背景"（正文 4.5:1、
   控件边界 3:1），另有 1 组装饰性分隔线只测量不判定（WCAG 1.4.11 只约束
   "理解内容所必需的图形"与"界面组件"，卡片之间的分隔线两者都不是）；
3. **不硬编码颜色**：扫 `frontend/**/*.xaml` 与 `*.cs`，出现色值字面量即失败；
   同时校验所有 `{DynamicResource <键>}` 引用的键真实存在（写错键名会导致文字不可见）。

首轮跑出的真问题与处理：

| 发现 | 处理 |
|---|---|
| 浅色输入框边框 `#C8C8D0` 对窗口背景仅 **1.53:1** | 改为 `#8A8A96`（3.13:1）——原诉"难以分辨"正是指这个 |
| 浅色按钮边框同样 1.53:1 | 同上 |
| 滚动条滑块对轨道 1.76:1 | 浅色改 `#85858F`（3.13:1）、深色改 `#6E6E7A`（3.11:1） |
| 深色输入框边框 1.52:1 | 改 `#74747F`（对 `#1E1E22` 为 3.6:1） |
| `SettingsWindow.Skills.cs` 用 `Brushes.IndianRed`/`MediumSeaGreen` 写死状态色 | 改走色板键（深色下原本几乎糊在一起） |
| `SettingsWindow.xaml` 有 `Foreground="#e06c6c"` | 改 `{DynamicResource ErrorBrush}` |

**新增的真实渲染校验** `tools/check_ui_pixels.ps1`：静态色板再漂亮也证明不了"深色模式到底有没有生效"
（这正是原缺陷）。该脚本真的启动程序、按主题截图、量像素：

* 主窗口平均亮度：浅色必须 > 0.55、深色必须 < 0.35（**实测 0.850 / 0.076**）；
* 逐个关键控件的局部对比度：在控件矩形内取出现次数最多的颜色作背景、
  取与背景距离最远的颜色作前景，按 WCAG 公式算比值，文字类要求 ≥ 4.5:1
  （**实测最差 6.24:1（浅色）/ 5.99:1（深色）**）；
* 截图为纯色区域（如空输入框）时跳过并说明——量出来的 1:1 没有意义。
  输入框会在截图**之前**填入测试文本，否则"输入框文字与输入框背景"这一项永远量不出东西。

### 3.4 一处刻意不修的地方（记录在案）

纯图标按钮（⚙ 📎 ➤ 🎯）的对比度只作为**参考值**记录，不作为失败门槛：
图标是"图形对象"而不是文字，WCAG 1.4.11 只要求 3:1；而且彩色 emoji 字形自带固定颜色
（⚙ 的齿轮是灰色、📎 的回形针是浅灰），**改色板也改不动它**。已做的改进是把这类按钮的
图标切到 `Segoe UI Symbol` 的单色字形（`Styles.xaml` 的 `IconText` 样式），
让色彩跟随 `ButtonForeground`：➤ 与 📎 因此升到 14.07:1 / 5.38:1（浅色）。
设置按钮的 ⚙ 因为字符带 `U+FE0F`（变体选择符，强制彩色呈现）仍是 2.43:1，
属已知的观感项而非可访问性缺陷，按"不再继续调对比度"的要求保留现状并在此记录。

## 4. 修复三：双语翻译不完整（P1）

见 §4 结尾的对照表与 §10 的验证结果。要点：

* 把**面向用户的文本**全部收编进语言包（前端界面 + 后端结果/错误/进度消息）；
* 建立**术语表**并统一译法；
* 所有含变量的文本改为占位符（不再在代码里拼句子）；
* 用 `tools/check_lang.py` 把"缺键"和"占位符不一致"变成 CI 可判定的失败；
* `docs/<locale>/` 下的 README / 用户手册 / FAQ / 自动化指南四份齐备。

### 4.1 收编范围与判定标准

判据只有一条：**"一个不懂中文的英文用户会不会看到它"**。

| 收编 | 不收编 |
|---|---|
| 界面标题、字段标签、按钮文字、提示语、状态文本 | `App.Log(...)` / `log.info(...)` 的诊断日志标签 |
| 确认框/对话框的标题与正文、空状态文案 | 异常包装（给开发者看的）、正则表达式 |
| 后端作为 `system` / `done` 消息发出的结果与错误 | 内部标识符、配置字段名、选择器、文件后缀判断 |
| `/help` 的全部内容、指令面板、技能指令说明 | 语言包键名自身、`AutomationId` |

### 4.2 术语表（关键术语全项目统一译法）

| 中文 | English | 说明 |
|---|---|---|
| 技能 / 插件 | Skill / Plugin | 内置能力叫"技能"，用户自己写的叫"插件"；英文统一首字母大写 |
| 自动化 | Automation | 不译作 "robot"/"scripting" |
| 批量处理 | Batch processing | 结果目录名保持中文（`批量处理结果\`），避免破坏既有用户的数据结构 |
| 上下文窗口 | Context window | |
| 可用窗口 | Usable window | 指实际启用的 `n_ctx`，与"训练窗口"区分 |
| 分段摘要 | Segmented summarization | 不译作 "chunked summary"（会与代码里的 chunk 混淆） |
| 安全协议 | Safety agreement | |
| 审计日志 | Audit log | |
| 模型库 | Model library | "模型中心"页签的英文名 |
| 快捷方式 | Shortcut | |
| 开发者模式 | Developer mode | |
| 信任（插件） | Trust | 动词/名词同形，不用 "approve" |
| 结果目录 | Results folder | |

### 4.3 占位符规范（含踩过的坑）

* 前端（C#）用 `{0}` `{1}`：`Loc.T("键", "中文兜底 {0}", arg)`；
* 后端（Python）用**具名**占位符：`t("键", count=n)`，因为 `str.format` 对位置顺序敏感，
  具名占位符在翻译时不会因为语序调整而串位；
* 语言包里出现裸 `{` 会让 `str.format` 抛异常，`backend/i18n.py` 用 `_SafeDict`
  在运行时容错（未知占位符原样保留），但**新增的键不允许留裸花括号**；
* 参数化统一由 `tools/lang_edit.py` 落地，它按语言批量写入并强制
  `tools/check_lang.py` 通过（键完整 + 占位符一致），避免"只加中文忘了英文"。

### 4.4 一个必须记住的目录约定

界面语言包在 `<程序>\lang\ui\`，后端语言包在 `<程序>\lang\`，**文件名都是 `<locale>.json`**。
放同一目录会互相覆盖，界面会显示成 `main.status.ready` 这种键名 —— v0.2.1 开发中实际踩到过。
`tools/test_i18n.py` 里加了一条针对 csproj `<Link>lang\ui\...</Link>` 的回归断言，
防止以后有人"整理目录"时把两边又合到一起。

## 5. 修复四：模型能力辅助与上下文管理（P1）

任务书给了八个方向，并明确"由 DSH 根据本版时间、依赖体积预算、用户反馈优先级自行评估
并选择落地方向"，同时要求**无论选择哪些方向，基础要求必须做到**。

### 5.1 方向取舍与理由

| 方向 | 决定 | 理由 |
|---|---|---|
| 一 输入侧优化（提示词工程） | ✅ 落地 | 零依赖、见效最快。小模型对角色/格式/示例极其敏感。做成 6 个任务模板（`/task`） |
| 二 任务分解与预处理 | ⚠️ 部分 | 长文档分段摘要（map-reduce）已在 v0.2.1 存在；本版补上"结果缓存"以省掉重复计算。规则+模型的交叉校验未做（见 §11） |
| 三 检索增强（本地 RAG） | ❌ 不做 | 任务书自己提示"需评估向量库依赖对发布物体积的影响"。chromadb/faiss 会给发布物增加数十到数百 MB，与全局体积要求直接冲突，且本版没有数据证明选题准确率是首要矛盾。**建议下版单独评估**（见 §11） |
| 四 输出后处理与校验 | ⚠️ 部分 | "提示词里强制输出格式 + 示例"已通过方向一覆盖；规则交叉校验与多次采样投票未做 |
| 五 工具调用与外挂 | ❌ 本版不做 | 任务书把它列为"长期方向" |

**方向八的具体实现**

## 7. 修复六：Emoji 显示为方块（P0 发布必需）

### 7.1 根因（用字形覆盖率实测确认，不是猜的）

任务书让排查"字体是否支持 emoji / 字体回退链 / 源文件编码"。实测结论是
**字体回退链里根本没有任何 emoji 字体**。用 WPF 的 `GlyphTypeface.CharacterToGlyphMap`
（字形覆盖表）查项目在用的 20 个 emoji：

| 字体 | 覆盖率 |
|---|---|
| `Segoe UI` | **0 / 20** |
| `Consolas` | **0 / 20** |
| `Microsoft YaHei UI` | **0 / 20** |
| `Segoe UI Emoji` | **20 / 20** |
| `Segoe UI Symbol` | 19 / 20（缺 `U+1F9E0` 🧠） |

而项目的字体声明是 `Styles.xaml` 里的 `FontFamily="Segoe UI, sans-serif"` 与
`MarkdownRenderer` 里的 `new FontFamily("Segoe UI")` —— **唯一的字体家族对 emoji 覆盖率为 0**，
且 `sans-serif` 不是 WPF 认识的家族名（那是 CSS 的通用名）。WPF 的 `FontFamily` 支持
逗号分隔的家族列表并**逐字形回退**，所以只要把 emoji 字体写进链里就能解决；不写就必然显示方块。
这不是"某个 Windows 版本的问题"，而是必然结果。

### 7.2 改法

**字体回退链（三个家族，各司其职）**

```xml
<FontFamily x:Key="UiFontFamily">Segoe UI, Segoe UI Emoji, Segoe UI Symbol, Microsoft YaHei UI</FontFamily>
<FontFamily x:Key="MonoFontFamily">Consolas, Segoe UI Emoji, Segoe UI Symbol, Microsoft YaHei UI</FontFamily>
<FontFamily x:Key="IconFontFamily">Segoe UI Symbol, Segoe UI Emoji, Segoe UI</FontFamily>
```

顺序有讲究：`UiFontFamily` 把 `Segoe UI` 排第一（拉丁文字用正文字体渲染，字形才正常），
emoji 交给第二个；`IconFontFamily` 反过来把 `Segoe UI Symbol` 排第一，让 UI 图标走
**跟随前景色的单色字形**而不是彩色 emoji（彩色 emoji 自带固定灰色，落在浅色按钮上对比度
只有 2.4:1，见 §3.4）。`MarkdownRenderer` 的 `FlowDocument`/代码块/行内代码也改用这两条链。

**控制台输出（后端）**

新增 `backend/emoji.py`：启动时先把 stdout/stderr `reconfigure(encoding="utf-8")`，
再判断"能否安全输出 emoji"——显式 `ECHODESK_NO_EMOJI=1` / `--no-emoji` 时关闭；
输出流编码不是 UTF-8 时关闭；是控制台但代码页不是 65001 时关闭。
不允许时 `prefer()` 把 emoji 换成 ASCII 标记（`✅`→`[OK]`、`⚠️`→`[!]`）。
判断必须在**任何输出之前**完成，否则日志/进度是边跑边打的，降级就晚了。

**降级策略（前端）**

新增 `frontend/Services/Emoji.cs`，与后端同一张映射表：

* `Emoji.Available` 检查 `seguiemj.ttf` 是否真的存在（精简版系统/Server Core/被组策略裁掉字体的企业环境可能没有）；
* 设置窗口新增 `EmojiCombo`（自动 / 始终显示 / 不使用），持久化到 `ui_state.json`；
* 替换点只有两处（保持"一处收口"）：`Loc.T()` 的返回路径（覆盖所有走语言包的文本）
  与消息渲染 `AddMessage` / `Toast`；
* 映射表覆盖不到的新 emoji 一律降级为 `?` 并丢掉变体选择符 —— **宁可信息弱一点也不显示方块**。

**源文件编码**：相关源文件已是 UTF-8 无 BOM，未改动。

### 7.3 把"会不会变回方块"变成可自动判定

新增 `tools/check_emoji.ps1`：

1. 用 `git ls-files` 取**纳入版本管理**的源文件（最初用 `Get-ChildItem -Recurse`
   把 `backend\.venv` 里 rich/click 的 emoji 图标表、idna 的 Unicode 表一起扫进来，
   得到上千个码位，把结论淹没在噪声里）；
2. 扫出 **61 个**实际在用的 emoji，逐个查三条字体链的**字形覆盖并集**；
3. 校验前后端两张 ASCII 降级表是否覆盖全部在用 emoji（否则降级会变成 `?`）。

首轮跑出的真问题：`U+27A4`（➤）不在 `Segoe UI Emoji` 里 → 给 `MonoFontFamily` 补 `Segoe UI Symbol`；
降级表缺 31 个 emoji → 补齐（📌 图钉、🪟 窗口、🧵 线团、🏗 施工、🎯 靶心…）。现在的结论：

```
[emoji] 扫描 75 个受版本管理的源文件，共发现 61 个不同 emoji
[emoji] OK   UiFontFamily / MonoFontFamily / IconFontFamily 均覆盖全部 61 个在用 emoji
[emoji] OK   后端 emoji.py 的 ASCII 降级表覆盖全部在用 emoji
[emoji] OK   前端 Emoji.cs 的 ASCII 降级表覆盖全部在用 emoji
```

### 7.4 验证

任务书要求"在 Windows 10 与 Windows 11 上分别启动验证"。本次只在 Windows 11（本机）实测；
Windows 10 未实测。但检查方式基于**字形覆盖率**而非版本号 —— `Segoe UI Emoji` 自
Windows 8.1 起随系统提供，因此结论对 Windows 10/11 同样成立；这一点在 §11 里如实标注为未实测。

### 8.2 三个目录语义的落地

| 目录 | 前端 | 后端 |
|---|---|---|
| 程序目录（`app\`） | `ShortcutService.ProgramDirectory`（exe 所在目录，放图标与程序文件） | `config.program_dir()` |
| 用户数据目录（外层） | 新增 `ShortcutService.UserDataDirectory`：① 环境变量 `ECHODESK_DATA`；② 程序目录名为 `app` 且父目录可写 → 父目录；③ 退化为程序目录 | 新增 `config.user_data_root()`，判定顺序与前端**保持一致** |
| 结果目录 | — | `automation.results_root` 改为走 `user_data_root()`（原来会落到 `app\` 里） |

路径判定用"目录名是否叫 `app`"这种**确定性**判据，不依赖"当前工作目录"
（任务书建议把快捷方式的 WorkingDirectory 设为外层，这一点也做了），
避免用户从别处启动时把数据写到奇怪的位置。判断父目录可写时会真的写一个临时文件探测，
拿不到权限就退回程序目录 —— 只读目录下不会崩。

**快捷方式**：文件名带版本号 `EchoDesk-v0.2.1.lnk`（多版本可共存），放在外层，
`WorkingDirectory` 设为外层 —— 双击启动后进程当前目录就是外层，`批量处理结果\`
等相对路径产物自然落在外面。`ShortcutService.IsValid()` 除比对 TargetPath 外，
新增比对**工作目录**是否正确：搬动文件夹后目标仍在但工作目录已失效，
这属于"需要重建"（原来不算失效，于是数据会落到 `app\` 里）。

**`ui_state.json` / `snippets.json`** 改到 `UserDataDirectory`；
**`EchoDesk.ico`** 只放 `app\`（图标算程序文件）。
**迁移兼容**：`-MigrateFrom` 同时尝试旧布局的 `<旧目录>\snippets.json` 与
`<旧目录>\app\snippets.json`（session.json 同理试三处）。

**语言包搜索链**同时加入外层与程序目录：前端
`UserDataDirectory/lang/ui` → `ProgramDirectory/lang/ui` → `Resources/Lang`；
后端 `program_root()/lang`（= 外层）与 `_MEIPASS/lang`（= `app\backend\_internal\lang`）。
用户往**外层** `lang\ui\` 丢一个新语言包即可生效，升级程序不会覆盖它。

**构建脚本**（`tools/build_release.ps1`）：

* 前端 `dotnet publish -o <外层>\app`，后端进 `app\backend\`；
* 清理动作全部改到 `app\`（移除多余 exe、`*.pdb`、裁剪 .NET 区域资源目录）；
* 外层生成：`使用说明.txt`、`LICENSE`/`NOTICE`/`SECURITY.md`、`docs\`、
  `批量处理结果\`（空目录，让"结果会生成在哪"一目了然）；
* **新增结构断言**：构建末尾遍历发布物，若外层出现任何 `*.exe`/`*.dll`/`*.pdb` 则**直接构建失败**
  （防止以后有人把 publish 输出目录改回外层）；
* 新增 `-ReuseBackendFrom`：只改前端时复用既有后端跳过 PyInstaller（几分钟 → 十几秒），
  使用时打印"快速迭代模式，正式交付请不带此参数重新构建"。该参数**指向本次输出目录时直接报错**
  —— 开发中真的踩到过"清空输出 → 复用源一起没了"，因为清空发生在校验之前。

**安装版一致**：`tools/installer.iss` 同步改为 `{app}\app\EchoDesk.exe`，
所有快捷方式（开始菜单/桌面/安装后立即运行）的 `WorkingDir` 都设为 `{app}`（外层），
`UninstallDisplayIcon` 指向 `{app}\app\EchoDesk.ico`。

### 9.2 本轮**没有**做体积优化的原因（逐项检查结论）

| 检查方向 | 结论 |
|---|---|
| 是否可以再裁 .NET 区域资源目录 | `app\zh-Hans`、`app\zh-Hant` 是 .NET 自带的消息本地化资源（约 1 MB）。删掉会让框架级异常消息退回英文，对中文用户是体验倒退，**收益 1 MB 不值得**，保持现状 |
| 是否可以把 `app\` 里的前端 DLL 合并 | `-p:PublishSingleFile=true` 会让启动变慢（需解压到临时目录），而且体积几乎不变（自解压包不会变小），**不做** |
| PyInstaller 是否还有可排除项 | 已排除 `pymupdf`/`fitz`/`torch` 等；`playwright` 的 driver（含 Node 运行时，约 100 MB）是可视化选取与自动化的**硬依赖**，无法排除。后端的 `_internal` 已无残留可删项（本轮实测 `backend_crash.log` 等运行期文件已清理干净） |
| 新的 Python 模块是否引入了重依赖 | 否。`model_profile.py` 只 import 标准库与项目内 `gguf_meta`；`prompts.py` 纯常量；`emoji.py` 只用 `os`/`sys`/`ctypes`。**零新增依赖** |
| 文档与语言包是否可压 | 语言包是运行期按需读取的 JSON，刻意保持可读以支持社区直接编辑；文档是交付要求的一部分 |

**结论**：本轮的体积结论是"不增加"，优化的 −37 MB 来自上一版的 AGPL 替换，两版合并后
不含模型的发布物从 416.9 MB 降到 380.0 MB。

6. **像素校验必须在截图之前把测试文本填进输入框** —— 否则空输入框只有一种颜色，
   量出来永远是 1:1，"输入框文字与输入框背景"这一项等于没测。

### 10.4 附带修复的既有缺陷（不在七项之内，但顺路修掉）

**可视化选取的提示语永远走异常分支（`NameError`）**

在翻译收编过程中发现：`backend/automation.py` 的 `_target_label` 定义在
`AutomationEngine` 的**类体里**，而调用点写的是**裸名字** `_target_label(target)`。
Python 的方法体不会把类作用域纳入 LEGB 查找，裸名字只会找到模块全局，
因此每次可视化选取都会 `NameError`，被外层 `except` 兜住后用户看到的是
「可视化选取失败：name '_target_label' is not defined」，
本该显示的"请在弹出的 Edge 窗口里点击目标元素（…）"**永远出不来**。

核实过程（确认不是本轮改动引入的）：

* `git show HEAD:backend/automation.py` 里同样是裸调用（HEAD L1502）+ 类内定义（HEAD L1828）；
* 最小复现确认语义：类体里的 `def helper(t)` 被同类方法以 `helper('x')` 调用 → `NameError`；
* 随后对整个后端做了一次 AST 审计（找出全部"类体内定义、被裸名调用"的函数），
  结果只有这一处，已全部修掉。

修法：把 `_target_label` 移到模块级（它是纯函数、不依赖 `self`），并在文档字符串里写明
为什么必须在模块级。修后实测：

```
提示语 = 请在弹出的 Edge 窗口里点击目标元素（任务所在的那一整行）。页面顶部有蓝色提示条，
        悬停时会显示选择器预览；按 Esc 取消。
```

顺带一个产品层面的观察（未改，供决策）：`automation.py` 的 `_SYSTEM_PROMPT` 写死"使用简体中文"，
因此即使用户把界面切成 English，本地模型产出的审核意见仍是中文。这属于业务策略而非界面文案。

**`/clearcache` 没有清分段摘要缓存（注释与实现矛盾）**

`model_profile.SummaryCache` 的文档字符串写着"`/clearcache` 也会清它"，但
`command_handler._clearcache` 实际只调 `llm_engine.clear_cache()`（只清 KV 缓存）。
按"清缓存就该清干净"实现，而不是把注释改小：新增
`CommandHandler.cache_clear_provider`（由 `main.Backend` 注入 `clear_summary_cache`），
`/clearcache` 现在同时清掉摘要缓存并在回执里报出条数
（`cmd.resp.cache_cleared_with_summaries`）。

**`tools/check_lang.py --scaffold` 生成的后端模板几乎是空的**

修复三的"社区贡献语言包"机制依赖 `--scaffold` 生成模板，实测 `--scaffold ja` 只生成
**6 条**后端待翻译条目。三个叠加的原因：

1. `main()` 里 `packs.update(load_dir(directory))` 把后端与前端语言包**合并成一份**，
   而两者的 locale 名字相同（都是 `zh-Hans`）→ 前端的键把后端的键整体覆盖掉，
   `scaffold()` 于是拿着**前端**的键去按后端的模块白名单筛；
2. 白名单里没有本轮新增的分组（`capability` / `task` / `mode` / `export`），
   即使不合并也会漏掉这 50 条；
3. 模板里混进了 `_meta.*` 元信息键（不需要翻译）。

修法与结果：按目录分别取源语言包（`sources[目录]`）、补齐白名单常量为显式的
`BACKEND_SCAFFOLD_MODULES`（并在注释里写明"新增分组必须同步加进来，否则会静默漏掉"）、
过滤 `_` 开头的键。修后实测：

```
✓ 已生成模板 backend/lang/ja.json（共 859 条待翻译）    ← 修前 6 条
✓ 已生成模板 frontend/Resources/Lang/ja.json（共 639 条待翻译）
  capability 25 条 / task 14 条 / mode 7 条 / export 4 条 / sys 100 条 / automation 304 条 / cmd 197 条
```

**发布物 `docs\` 里缺 `SBOM.json`**

`tools/build_release.ps1` 的文档收集写的是 `Get-ChildItem -Filter *.md`，
而修复五新增的 `docs/SBOM.json` 是 JSON → 没进发布包。
（这一项是文档同步时对照 `publish\` 目录逐项核对发现的；`release.yml` 与我新写的
`tools/verify_release.ps1` 都会断言它存在，所以这条缺陷会直接让发布流程失败。）
改为**复制 `docs\` 下的全部文件**（不只是 `.md`），并在日志里分别报出 Markdown 与其他文件数量
——将来 docs 里出现图片等非 md 资源也不会再漏。

**一处经核实为误报**：文档同步过程中曾怀疑 `/task` 的中文模板名取不到
（`task_label('summary')` 返回键名）。实测为**误报**：`i18n.get().has('task.summary.label')`
为真，源码与发布物的三份后端语言包都含 14 条 `task` 键，`/task list` 输出正常
（`/task summary — 摘要归纳：…`）。误报原因是检查脚本用了嵌套结构判定
（`d['task']['summary']`），而语言包里 `task` 分组下的键是**扁平的点分键名**
（`"summary.label"`）—— 这个坑值得记下：**语言包分组内的键是点分字符串，不是嵌套对象**。

### 12.1 为什么一次性提交（而不是七次分别提交）

七项修复看起来彼此独立，但实际存在**强耦合**，拆开提交会出现"中间提交不可构建/不可验证"的问题：

1. **修复二与修复六共用同一批文件**：`Styles.xaml` 既承载 47 键语义色板与 10 类控件模板（修复二），
   也承载三条字体回退链与 `IconText` 图标样式（修复六）。拆开要么出现"色板已换、字体未换"
   的半成品状态，要么需要把同一文件的两块改动分别 staging（`git add -p`），而它们还互相引用
   （图标样式要用色板里的 `ButtonForeground`）。
2. **修复七改变的是整棵目录树**：`build_release.ps1`、`ShortcutService`、`AppSettings`、
   `SnippetManager`、`config.program_root`、`Localization.LangDirectories`、`automation.results_root`
   必须同时改完才自洽 —— 只改一半会让"快捷方式指向 app\、但前端仍从程序目录读 ui_state.json"，
   这个中间状态比不改更危险（用户数据会落到错误位置）。
3. **修复三（翻译）横跨全部其他修复**：新增的语言键里有大量来自修复一/二/四的新界面文本
   （信任确认框、主题与 emoji 选项、能力提示、压缩上下文按钮）。翻译无法脱离这些改动单独提交。
4. **验证工具与修复本身必须同批**：`check_theme` / `check_emoji` / `check_ui_pixels` /
   `verify_release` 以及 CI 接线是与修复同时产出的"证据链"，分两次提交会出现
   "提交了修复但没有对应的可判定检查"的空窗期。
5. **发布物只有一个**：七项修复共用一次打包与一次冻结验证（§10），提交粒度与交付粒度对齐更诚实。

上一版研发记录（`docs/v0.2.1-研发记录.md` §11）对"六条主线为何一次提交"给了同样的理由，
本轮沿用同一原则：**提交边界按"可构建 + 可验证"划分，而不是按任务书的条目编号划分**。
