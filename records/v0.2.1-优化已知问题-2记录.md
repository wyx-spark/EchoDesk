## 二、本轮实现

### 任务四：抽取式预筛（`backend/extractive.py` 新增）

任务书把"抽取式预筛"列为**收益最大**的一条（"模型只处理抽取后的内容（原文本的
10-20%），模型调用次数与生成长度同步下降。抽取本身不需要模型，毫秒级完成"）。

实现：TextRank 选句 + **稀有度加权** + **两遍选句** + **事实密度自适应比例**。
纯标准库（不引 jieba/numpy，见 `tools/check_requirements.py` 的依赖白名单），
3000 字符的段实测约 8 ms。

**关键决策与实测依据**（全部可复现：`artifacts/probe_extractive.py`）：

1. **纯 TextRank 方向是错的**。它衡量"这句话与其他句子有多像"，于是选出的是
   *重复套话* 的句子；而合同里真正的要点（`1,860,000 元`、`2026 年 3 月 31 日`、
   `按日 0.3%`）恰恰只出现一次，中心度低、排不到前面。实测 721 字符的中文合同
   样本在 ratio=0.18 时只选出 4/30 句，**关键数字 0/6 保留**。
   → 加入"稀有度"信号（该句包含多少"全文只出现一次"的特征，含数字的再加权），
   与中心度各占一半（α=0.5 由两个样本的保留率扫描定出，扫描表在模块注释里）。
2. **两遍选句**。只按"得分高→装预算"会有系统性偏差：一条长句 + 它的邻居就能
   吃光预算，剩下十几条短句（"付款期限：30 日。"这种恰恰是要点）一条都进不来。
   → 第一遍只装得下才收；第二遍按"每字符得分"回填，把"挑最长的好句"矫正为
   "在有限字数里装进尽量多的要点"。
3. **结构性标题不可丢**。"采购合同"四个字长度惩罚 0.25 倍、稀有度 2，怎么排都
   进不了前几名，但它丢了摘要就没了主体 → 文档前 3 句里的标题行无条件保留。
4. **事实密度自适应**。抽取的最小单位是整句而预算按字符算：英文协议样本每句
   约 75 字符且一句一个关键数据，35% 的预算只够装 3 句 —— **必然丢掉一半事实**，
   与"这一句重不重要"无关，纯粹是句长决定的算术结果。
   → 平均句长 < 60 字符（"一句一个事实"）时把比例抬到 0.50。
5. **性能闸门**。8000 句（31.5 万字符）实测要 22.9 秒 —— 预筛本应毫秒级，
   跑 20 秒就是纯负担 → 段长超过 12000 字符一律原样返回（摘要器按 3000 字符
   分段，正常不会触发）。

接线（`summarizer.py`）：`model_input` 先预筛再送模型；提示里的字符区间仍指
**原文**（界面上要显示的是"这段来自原文哪一块"）；兜底文本用**原文**而不是残段；
预筛抛异常安全退回原文。`SummaryResult` 与进度事件带预筛统计
（`extractive_chunks` / `extractive_origin_chars` / `extractive_input_chars`），
任务书要求的"确认抽取式预筛生效"由此可断言。

**实测**：47KB 文本按真实分段口径（3000 字符/段）逐段抽取
`50421 → 17880 字符`（压缩 **2.8 倍**），总耗时 **136 ms**。

配置：`summarize.extractive` / `extractive_ratio`(0.35) / `extractive_min_chars`(600)，
三处均已写进 `backend/config.json` 与 `deploy/config.json`。
测试：`tools/test_extractive.py` **83 项**。

### 任务五：流式卡顿与爆发

任务书要求"逐层排查三个环节"。实测结论与修法：

1. **后端 stdout 缓冲**：已经是对的（`_write` 每条 `flush`），**不是**根因。
2. **模型生成节奏（真根因之一）**：`llama_cpp` 的流式生成器在 **prefill 阶段会
   阻塞几十秒**，消费者直接 `for chunk in stream` 时这段时间**没有任何数据可
   flush** —— 无论怎么 flush 都发不出去。
   → `llm_engine._iter_with_heartbeat`：读者线程 + 有界队列，消费者用
   `get(timeout=...)`，超时就产出心跳。于是"永远不会长时间无输出"，
   心跳间隔 `config.stream_heartbeat_seconds`（默认 1.5 秒）。
3. **前端 UI 更新（真根因之二）**：Markdown 有 60ms 节流，但**思考区每次增量都
   重建 FlowDocument**，且 `ScrollToBottom()` 每个 delta 都触发全页测量。
   → 把"思考区重渲染"与"滚动到底"一并纳入 50ms 节流（`AppSettings.StreamThrottleMs`），
   只保留文本累积（O(1)）是每 delta 做的。
4. **prefill 状态提示**：心跳带 `waiting_first_token`，状态文案区分
   "正在处理输入…"与"正在生成…"（此前只有笼统的"处理中"）。
5. **历史加载**：核查确认历史里**只存最终消息**（`conversation.add_message` 只写
   role/content/timestamp/reasoning），流式中间态从来不落库，这一条本来就满足。

**踩过的两个坑**（回归测试逼出来的，都写进了代码注释）：

* 读者线程若一路把流抽干，用户点"停止"之后模型还在继续算（既浪费 CPU，
  "停止"也退化成"停止显示"）→ 停止信号必须传进读者线程。
* 停止检查若放在"取出之前"，会把"模型已经生成、只差交付"的那一块整段丢掉，
  于是"停止前界面上已经显示出来的思考"在 `done.reasoning` 里凭空消失
  （既有中断回归用例正好断言了这一点）→ 按"停止被发现时手上那一块的序号"
  精确截断：它之前的照常交付，它之后的丢弃。

测试：并入 `tools/test_reasoning.py`（新增"任务五 · 流式心跳与运行指标"一组），
**122 项**全通过；另有 `artifacts/probe_heartbeat.py` 直接量出
"prefill 3 秒期间收到 5 次心跳、停止 1.00 秒内返回、逐 token 不攒批"。

### 任务七：状态区实时指标

任务书要求"指标从后端获取，不能仅靠前端估算"。实现：

* `llm_engine.StreamStats`：首 token 延迟、总耗时、输出字符数、**输出 token 数
  （用模型真分词器精确数；分词器不可用时标注 `tokens_estimated`）**、token/s、
  是否已过 prefill、是否被中止。
* 心跳（`progress`）与 `done` 都带 `stats`；前端 `ApplyStreamStats` 只做格式化，
  **不估算 token**；秒表（已用时）由前端本地走（心跳 1.5 秒一次，只靠心跳会一顿一顿）。
* 行为按任务书逐条落实：流式实时更新；首 token 前显示"⏳ 等待首 token"；
  完成后保留最终值、下次请求开始时重置；失败显示失败；中止标注"已中止"；
  **无模型整块隐藏**（不显示 0 或占位符）；更新频率 500ms（`_metricsTimer`）。
* 位置：状态区 `WrapPanel` 末尾新增 `MetricsText`（无指标时 `Collapsed`，不占位）。

### 任务二：联网搜索未被有效利用

任务书要求"逐环节排查"四个环节。逐条结论：

| 环节 | 结论与修法 |
| --- | --- |
| 搜索触发 | 开关开启时每次提问都查（**按需触发**，见下方自行判断项）；`Backend.search_diagnostics()` 暴露"是否执行" |
| 结果返回 | 旧实现把失败也拼成字符串（`"搜索失败: …"`），调用方靠 `"未找到" not in result` 这种脆弱判断区分成败 → 改为结构化 `SearchResult` / `SearchOutcome`（`ok`/`error`/`results`/`elapsed_ms`） |
| 结果注入 | 旧实现注入 `参考以下网络信息：\n<裸文本>`，小模型在这种"没结构、没要求"的上下文里会直接忽略 → 改为**编号列表 + 明确引用指令 + "不足就说不知道"的出口**；条数默认 3→**5**、单条摘要 400 字符、总长 3000 字符 |
| 模型利用 | 注入文本要求"优先依据上述结果作答、引用时标注编号 [1]"，并给出"结果不足就明说"的出口（否则小模型倾向编造以显得有用） |

另外按任务书"结果为空或质量差，明确告知用户而非静默继续"：失败与空结果都**不注入
任何文本**（旧实现会把"未找到相关结果。"当资料喂给模型，模型据此编造），
并给用户一句明确的话（区分失败与空结果两种情形，`sys.search_failed` /
`sys.search_empty` 双语键）。

**自行判断项**：① 触发时机 → **按需**（沿用开关语义）：本地小模型没有可靠的
"这题需不需要联网"判断力，用模型做路由要多一次推理（纯 CPU 上几秒到几十秒）
且不稳定，而用户按下开关本身就是明确的意图表达；② 条数与长度上限 → 5 条 ×
400 字符，最坏约 1000 token，占 8192 窗口约 12%，对 0.6B/1.7B 是安全区间。

测试：`tools/test_search.py` **59 项**（桩 DDGS，不联网）。

### 任务九：上下文压缩策略

按任务书列的业界做法改掉五件事：

1. **触发按 token 比例**（`config.compact.trigger_ratio`，默认 **0.70**，原为硬编码 0.8）；
2. **grace zone**：最近 `grace_turns`（默认 3）**轮**逐字保留，与 `keep_ratio`
   的 token 预算**取并集**（谁保留得多听谁的）—— 旧实现只看 token 预算，
   一条超长消息就可能压掉刚发生的对话、留下更早的内容；
   若 grace zone 覆盖全部历史：自动压缩**如实回答"无需压缩"**（不擅自压掉刚说过的
   话），手动压缩则把 grace 收缩到 1 轮再做一次并在回执里标注（用户点了压缩却
   什么都不发生是更糟的体验）；
3. **摘要提示词可自定义**（要求保留"需求与目标 / 关键决定 / 背景信息（人名、金额、
   日期、编号、路径、参数）"），并新增 `/compact focus on <重点>`：重点是**追加**
   进提示词而不是替换它；解析宽松且不误伤 `/compact auto|off`；
4. **大块内容单独处理**：新增 `_truncate_tool_outputs`，文件/搜索/自动化结果这类
   "一条几万字符"的消息在喂压缩器之前保留**头 60% + 尾 30% + 长度说明**
   （旧实现 `content[:300]` 等于把整条内容丢掉，连"这里曾经有一大段文件内容"
   都看不出来；保留头尾是因为标题/摘要在前、结论/落款在后）；
5. **压缩事件可追溯**（`backend/compact_log.py` 新增）：追加式 JSONL
   （`compact_log.jsonl`）记录触发原因/方式/模式、阈值与比例、压缩前后 token 数、
   被压缩与保留条数、grace 轮数、摘要全文、用户重点、当场用的提示词、
   大块内容截断统计与错误；坏行跳过（一行坏了不废整份日志）；超上限裁剪最早的
   事件；`log_content=false` 时只记长度与计数（**可脱敏**）；
   `replay()` 按时间累计拼接，回答"现在这段摘要里哪几句是第几次压缩加进来的"
   （**可回放**）。`Backend.compaction_diagnostics()` 暴露阈值/保留策略/日志汇总/
   回放步数/最近事件。

测试：`tools/test_compaction.py` **77 项**。

### 任务八：多文件上传

任务书把"处理逻辑 / 上下文组织 / 边界情况 / 与现有机制兼容"四组都列为要求。

后端：

* `conversation.FileEntry` 文件登记表（有序列表 + `active_index`），新增
  `add_file` / `remove_file` / `remove_file_by_name` / `select_file` /
  `file_names` / `total_chars` / `set_entry_summary`。
* **老字段 `file_name` / `file_content` / `file_summary` / `file_summary_meta`
  保留为只读属性代理**（映射到当前活动文件）：这四个字段在指令、状态显示、
  摘要触发、会话读写里被引用几十处，逐一改写任何一处漏改都是运行时崩溃；
  属性代理让既有调用方与测试**零改动**（`set_file` / `set_file_summary` /
  `has_file()` 也都保留）。
* `build_messages` 逐份注入，每份带 `【文件内容 N/M：名字】` 标签；总长受
  `config.files.total_chars` 约束，**从后上传的开始装**（刚拖进来的通常就是这次
  要用的），装不下的不注入并由 `last_injection_note()` 如实点名 —— 任务书要求
  "总内容超出窗口时触发分段摘要，或提示用户选择部分文件"，本实现选**提示**，
  把取舍说出来而不是静默丢文件。
* 会话持久化写入 `files` 列表（**不写正文**，只写文件名/摘要/体积/落盘路径 ——
  正文动辄几十万字，写进 session.json 会让它膨胀到几十 MB，而正文随时可以从原
  文件重新解析），同时保留旧的 `file_*` 字段；读取时两者都认，**老会话自动升级**
  成单文件列表。
* 新增 `Backend._load_one_file`（结构化返回）、`load_files_into_context`
  （批量：逐份独立 try/except，**单份失败不影响其他**，超上限的不处理并如实说明）、
  `_stream_files`（流式：逐份 `file_status` 行 + 摘要进度 + `done` 带文件清单）；
  `summarize_current_file` 拆出 `summarize_entry`（多文件下必须能指名摘要哪一份）。
* 新增 `config.files` 段：`max_count=10` / `total_chars=60000` /
  `disk_threshold_chars=20000`；超过阈值的单文件**正文落盘**到 `file_cache\`，
  上下文只放指针 + 摘要（与任务九"大块内容单独处理"同一条思路）。

前端：`OpenFileDialog.Multiselect = true` 并接收 `FileNames`；拖拽取**全部**路径
（不再 `[0]`）；两条路径汇聚到同一个 `UploadFilesAsync`（行为一致）；
逐份状态就地更新同一条消息（`⏳ [i/n] 名字…` → `✅/❌`）；摘要进度复用同一行并带
`[i/n]` 前缀；选择超过 10 个或总量超过 60MB 时先弹确认框（用户同意才继续并只处理
前 10 个）。

**顺带修掉的既有缺陷**：指令参数此前用 `str.split()` 分词，**路径含空格就会被
切开** —— 单文件时代表现为"路径含空格就加载失败"，多文件时代会变成"一次加载 N 个
不存在的路径"。改为引号感知分词（双/单引号都认）：`/file "C:\My Docs\a b.docx"`。

测试：`tools/test_multifile.py` **77 项**。

### 交付要求：前端识别 `$$ $$`

`MarkdownRenderer` 此前完全不认公式。现在：

* **块级**（整行或多行被 `$$` 包起来）→ 单独成**居中 + 等宽**的公式段；
* **行内** `$...$` 与同行 `$$...$$` → 行内等宽片段（公式在句子中间时居中会把
  句子劈成两半，所以只有块级才居中）。

**不做 LaTeX 排版**：WPF 没有原生公式引擎，社区方案要么依赖 WebView2
（本项目刻意不引入）、要么依赖第三方渲染库（体积与许可证成本都超出"识别 `$$`"
这一条要求）。按"等宽 + 可选中复制"呈现公式源码，对"把 LaTeX 粘到别处继续编辑"
最友好，也最不容易出错。

**最大的风险是不误判美元金额**（`价格 $100 到 $200`），判据刻意保守：出现 LaTeX
特征字符 `\ ^ _ { } = + ( )`、数学函数/命令名、希腊字母名，或比较运算两侧
（跳过空白后）是字母/数字且至少一侧是字母 → 公式；纯数字/货币、含中文字符、
长度 > 200 → **不是**公式。

验证：`artifacts/MarkdownProbe/`（**直接编译仓库里的真源码**，不是复制品，
否则会失真）构造真 `FlowDocument` 后递归断言，**23 项**全通过：
块级/同行/行内三种形态、5 组美元金额全部不误判、中文不当公式、
标题/代码块/表格/粗体/列表等既有 Markdown 不受影响。
探针抓出并修掉两个真缺陷：① 同行 `$$...$$` 完全没被识别（块级扫描只认"行首"）；
② 比较运算判据里"紧邻字符"在 `x > 0` 中是两个空格，判据永远匹配不上（改为跳过空白）。

### 任务十七：多语言与文档

* 本轮所有新增文案都走语言包，中英齐全、占位符一致
  （新增 `sys.search_failed` / `sys.search_empty` / `sys.files_*` /

## 四、未完成项与评估后不在本版实现的任务

### 1. 任务六 对话区虚拟化（**不在本版实现**）

任务书对这一项给的要求最细（虚拟化容器、可变高度测量与缓存、滚动锚定、
流式与虚拟化的配合、性能验证、降级与兼容），工作量相当于重写消息区：

* 现状是 `ScrollViewer` + `StackPanel` + `Children.Add`，消息元素是
  `RichTextBox`（可选中复制、Markdown、字号随全局变）与 `TextBox`（纯文本），
  外加思考折叠区与复制操作条。
* 改成 `ItemsControl + VirtualizingStackPanel` 要求**每条消息的数据驱动化**
  （现在是命令式构造 UI），并且要在虚拟化下保住六项现有能力：可选中复制、
  思考折叠状态、代码块高亮、Markdown 渲染、字号调节、主题切换。
  "可变高度 + 回收容器"与"RichTextBox 的高测量成本"叠加，是本任务书里唯一
  **风险高于收益**的一项：做一半会把"滚动卡"换成"内容错位/复制失效"。
* 本轮选择了**先做能立刻见效的部分**：任务五的前端节流（思考区重渲染 + 
  滚动到底合并到 50ms）已经削掉了长会话滚动卡顿的主要来源（每个 delta 一次
  全屏测量）。虚拟化留待专门一轮，方案与取舍见下一轮的任务书。

### 2. 任务十 工具调用流水线（**不在本版实现**）

现状：自动化有 `before_task/after_download/after_summary/after_task` 四个钩子
与 JSONL 审计（`automation_log.jsonl`，含脱敏）；**没有**统一的
pre / ask / guard / execute / post 五段中间件。

不在本版做的理由：本项目的"工具"只有三类（内置指令、技能命令、自动化任务），
其中只有自动化是真·外部副作用操作且**已有**审计；把五段流水线架起来之后，
真正要接的只有"插件声明的 destructive 命令要弹确认"这一条（当前前端硬编码
`/clear`、`/clearcache`）。为一个调用点引入一套抽象层，属于"有了形状没有内容"。
留待技能生态里出现更多有副作用的工具时再做，否则抽象的形状会是错的。

**本轮顺带修掉相关的一处真问题**：指令参数分词不支持引号，导致"路径含空格就
加载失败"（见任务八）。

### 3. 任务十一 会话持久化与崩溃恢复（**未实现，已知缺口**）

现状：每轮与退出时整文件覆盖写 `session.json`；崩溃只留 `backend_crash.log`，
最近一轮正在生成的内容会丢。任务书要求的"追加式 JSONL + 定期 flush 检查点 +
崩溃后重建 + 被中断轮次可恢复"都还没做。

为什么留到下一轮：它要与任务九的
`compact_log.jsonl`（本版新增，已经是同一套"追加式 JSONL + 回放"的模式）
统一设计事件格式，否则会出现两套互不相干的事件流。本版已经把
`compact_log.py` 的写法与回放做成可复用的形状（`iter_events` / `replay`），
下一轮按同一模式实现会话日志即可。

### 4. 任务十二 MCP / 十四 多模型适配器 / 十五 子代理 / 十六 任务看板（**不在本版实现**）

* **MCP**：需要引入 `mcp` 客户端依赖（体积 + 许可证），并定义与现有技能系统的
  关系。本版先把"技能运行期加载器"的既有能力核对清楚（见核查表任务十三），
  在技能生态真正被第三方使用之前引入 MCP，会连"谁是主、谁是桥"都不确定。
* **多模型适配器**：云端 API 意味着**联网 + 密钥 + 计费**，与本项目"全离线、
  数据不出本机"的核心卖点直接冲突（`docs/PRIVACY.md` 的隐私承诺）。
  要做也必须先由用户显式开启并明确告知数据会离开本机，属于产品决策而非纯技术
  实现，本版不做。
* **子代理与工作流**：需要多次串行推理；纯 CPU 上单次推理就几秒到几十秒，
  把一个任务拆成四步会让总耗时变成分钟级，收益（"拆解能力"）与小模型的
  规划能力不匹配。等有了更快的推理后端（GPU 或云端适配器）再评估。
* **任务看板**：自动化任务目前是"一次运行一个、结果落 results\ 目录"，
  看板要有意义得先支持多任务并发与持久化任务队列（现在没有）。UI 插件面板
  已接线（技能可注册面板），看板可以基于它做，但需要先有任务队列。
