# v0.2.1 模型市场优化记录

> 任务书：`prompts/EchoDesk-v0.2.1模型市场优化.md`。
> 本文记录实现方案、关键决策、与任务书的偏差与未完成项；结论性数字见
> `records/v0.2.1-发布记录.md` §24。

任务书要解决的问题是一句话：**搜索 `GGUF` 命中数千条，用户最多只能看到 21 条，而且看的是
"最近 30 天下载量"**。因此本轮的重点不是"把列表做得好看"，而是把
"取全 → 装下 → 找得到 → 排得对"这条链路打通。

---

## 一、先摸清接口的真实行为（探针实测，不是照文档猜）

任务书给的是目标，接口能不能做到得先量。`artifacts/probe_hf_api*.py` 六个探针的结论：

| 事实 | 实测结果 | 影响 |
| --- | --- | --- |
| `expand=downloadsAllTime` | **有效**，返回 `downloadsAllTime` 字段 | 任务一的落点 |
| 传了 `expand` 之后 | 响应体**只剩被 expand 的字段**（只剩 `_id/id/trendingScore/downloadsAllTime`） | 必须一次列全所有需要的字段 |
| 同一个 `expand` 值重复出现 | **HTTP 400** | 参数必须去重（`dict.fromkeys`） |
| `limit` 上限 | 1000；传 2000 / 5000 都被**静默截断到 1000** | 分页按 1000 发，不能"让服务端自己截" |
| 分页方式 | `Link` 响应头里的**游标**（offset 无效，没有 `page` 参数） | 必须顺着游标翻 |
| `Link` 头里的主机 | 镜像站返回的是 **`https://huggingface.co/...`** | 照抄会把后续分页全打到官方站（本机官方站超时），只能取 `cursor` 再拼回当前源 |
| 服务端 `sort=downloads` | 按**最近 30 天**排（该列单调，历史总量列不单调） | 展示顺序必须本地重排 |
| `sort=downloadsAllTime` | **HTTP 400**，不存在 | 同上 |
| `direction=1` | **HTTP 400**（只接受 -1） | 不支持升序 |
| 接口返回总条数 | **没有**（响应头也没有） | "共 N 条"只能在取完后才精确 |

**如果照任务书字面实现而不做这些探针，会踩的坑**：只加一个 `expand=downloadsAllTime` →
tags/likes/lastModified 全部消失（列表元数据变空）；把 `expand` 写死一份再加一份动态追加 →
每次请求 400，搜索整体不可用；照抄 `Link` URL → 在只通镜像的网络里第 2 页就死。
这三条都写进了代码注释与测试断言（`tools/test_model_market.py` 的 A1/A2/A9）。

## 二、任务一：下载量口径

- 请求显式带 `expand=downloadsAllTime`（连同 `downloads/likes/lastModified/createdAt/tags/author/
  gated/private/pipeline_tag/library_name`）。
- 条目上给出 `downloads`（展示值）、`downloads_all_time`、`downloads_recent`（30 天）、
  `downloads_source`（`all_time` / `default_fallback` / `none`）。
- **缺字段回退并标注**：服务端没给 `downloadsAllTime` 时回退到 30 天值，`downloads_source`
  标成 `default_fallback`；响应汇总里给 `downloads_metric`（`all_time` / `mixed`）与
  `downloads_fallback_count`，状态行写明"其中 N 条缺少历史总量字段，已回退为「最近 30 天」并逐条标注"。
  判断用 `is None` 而不是真值 —— `downloadsAllTime` 为 0 是新模型的正常取值。
- 状态行固定写出口径：**"下载量口径：历史总下载量（与 Hugging Face 网页上的「30 天下载量」
  不是同一个数）"**。

**实测口径差异的量级**（`artifacts/smoke-market.log`）：第一页里
`TheBloke/phi-2-GGUF` 历史总量 **60,526,632**、最近 30 天只有 **17,675**。
旧代码显示的正是后者 —— 差三个数量级，"热门模型"和"最近有点热"完全是两回事。

**排序口径的偏差**：任务书说"列表展示与排序均基于历史总下载量"，但服务端没有这个排序字段。
落法是**远端排序只决定抓取窗口装哪些条目，展示顺序一律本地按历史总下载量重排**。
在结果没撞上限（全部取回）时，本地排序就是**全局精确排序**；撞上限时窗口的选取退化为
"服务端 30 天口径的前 N 条"，这一点在偏差章里明说了。

## 三、任务二：自动取回全部结果

### 上限的具体数值（任务书要求自行判断）

| 闸门 | 默认值 | 为什么是这个数 |
| --- | --- | --- |
| 总条数 `max_items` | **5000** | 实测 `GGUF` 关键词下 5 页 ×1000 条全部是新条目（>5000）。5000 条含全部字段的响应约 2.9 MB，前端解析与本地筛选都是毫秒级；再往上收益递减而内存线性增长 |
| 请求次数 `max_requests` | **8** | 单页 1000，8 次理论上够 8000 条；配合条数上限实际最多 5 次 |
| 耗时 `max_seconds` | **90** | 实测 5 页约 15 秒（镜像站），90 秒给慢网留足余量又不至于让用户干等 |
| 绝对封顶 `HARD_MAX_ITEMS` | **20000** | 用户反复点"继续加载"的总规模上限，防内存被吃光 |

全部可配（`config.json` 的 `model_hub` 段）。**上限按"每轮"计算而不是累计**：
第一版按累计算，第二次点"继续加载"时"距离上限还差 0 条"会退化成一次只取 1 条（实测踩到）。

另外一个第一版踩到的坑：上限是"软"的 —— 页大小固定 1000，上限设 100 时第一页会一次塞进
250 条，续载逻辑随之全乱。修法是**本页只请求"还差多少就到上限"那么多条**
（`limit = min(1000, 本轮剩余, 硬上限剩余)`），上限就是精确的。

### 进度、停止、重试

- 新增**流式动作** `model_hub_load`：每取完一页发一条 `hub_progress`
  （`phase/loaded/pages/requests/elapsed/has_more/limits`），前端显示"正在取回结果：已加载 N 条
  （用时 x 秒）"。进度行用独立 `type`，与既有 `summary_progress` 同一套机制，不干扰 delta/done 语义。
  另外前端每秒自增一次"用时"，避免两页之间看起来像卡死。
- 「停止」走既有的 `stop` 信令（不是 CancellationToken）：stdout 是单条共享流，
  中途放弃读取会让后续响应错位，这一点与下载取消同源。
- **重试**：单页失败重试 `download_retries` 次（1.5s/3s/4s 退避）；**第 1 页失败先换另一家数据源**
  （比在同一条死路上重试更有意义）；连续失败中止，`stop_reason="error"`，
  **已取回的结果全部保留**并在消息里写明"已加载 N 条"。

### 缓存：位置与有效期（任务书要求自行判断）

- **内存**：`ModelHub._session` 保存当前数据集，供 `model_hub_query` 做本地筛选/翻页（后端重启即失效）。
- **磁盘**：`<用户数据目录>/cache/model_hub/<sha1>.json`，键 = `版本|数据源|关键词|排序维度`。
  选用户数据目录的理由：那里一定可写、会随用户数据一起被备份、且**不污染程序目录**
  （便携版里 `app\` 是程序本体）。可用 `search_cache_dir` 覆盖。
- **有效期 6 小时**（`search_cache_ttl_hours`，与技能市场缓存同一量级）。过期后联网重取；
  **离线降级时过期缓存照用**（标了"离线模式"），因为"过期的结果"远好于"一片空白"。
- 「刷新」按钮 → `refresh=true` 跳过内存与磁盘缓存；换排序维度是**另一个缓存桶**，
  所以"排序切换会重新请求远端，已缓存该排序时优先用缓存"这条自然成立（实测：切到 likes 会重取，
  切回 downloads 命中缓存）。

**实测效果**：`GGUF` 5000 条首次 15.7 秒 / 5 次请求；同一关键词再次搜索 **0.24 秒**（命中缓存）。

## 四、任务三：分页显示

- 每页 20 条（可选 20/50/100），**分页与筛选的逻辑在 `backend/model_query.py`**（见第五节）。
- 布局：模型页网格改成 8 行 —— 结果列表占 `*` 独立滚动，分页控件单独一行 `Auto` 固定在下方，
  因此"滚动列表时分页控件不动"是**结构上成立的**，不是靠样式凑出来的。
  UI 探针用 `ScrollPattern` 真的滚了一下列表并断言分页控件的位置没变。
- 窄窗口：分页控件用 `WrapPanel`（换行而不是裁切），与主窗口状态栏同一套做法。
- 边界（都有断言）：第 1 页禁用"首页/上一页"、最后一页禁用"下一页/末页"；
  越界页码夹到最近的合法页并提示；非法输入（`abc`/空/0）给出提示且**不跳页**；
  页码框回车即跳转（`KeyDown` 里判 `Enter`）。

## 五、任务四/五/六：本地筛选、结构化筛选、排序

### 关键决策：数据变换放后端，前端只负责画

任务书里的分页、本地筛选、结构化筛选、四种排序**全是纯数据变换**，而"第一页/最后一页/
非法页码/筛完为空"正是任务书点名要验的边界。本仓库有 Python 测试体系、**没有 C# 测试体系**，
把逻辑写在 C# 里等于"写完无法证明它对"。

因此：**逻辑放在 `backend/model_query.py`（纯函数、不持有状态、不碰网络），
前端通过 `model_hub_query` 拿算好的一页**。

这不违背"本地实时筛选、不重新请求远端"：`model_hub_query` 是**进程内往返**，
一次网络请求都不发（实测 5000 条的筛选+排序+分页约 40 毫秒，人脸感知不到）。
任务书要防的是"每敲一个字就去搜一遍远端"，这条被"`model_hub_load` 负责远端、
`model_hub_query` 负责本地"的分工从结构上挡住了。

前端相应的取舍：**远端搜索框不再"输入即搜"**（旧行为 400ms 防抖自动搜），
改为**回车或点「搜索」触发**。原因是自动加载全量意味着敲第一个字母就可能触发 5000 条的加载；
本地筛选框则保留 150ms 防抖的实时过滤（任务书的要求）。这是一处**刻意的行为变更**。

### 同维度多选 = 或（任务书偏差，见第七节）

### 结构化筛选器

| 维度 | 数据来源 | 落地字段 |
| --- | --- | --- |
| 参数量区间 | 仓库名解析（`(\d+(?:\.\d+)?)\s*[bB](?![A-Za-z])`，量化标签不会误判） | `param_b` → `p_le1/p_1_3/p_3_8/p_8_20/p_20_40/p_gt40/unknown` |
| 量化格式 | 名称/文件名解析 | `quant_code`（**语言无关的代码**，如 `Q4_K_M`；取不到为空串，界面显示本地化的"未知"） |
| 更新时间 | API 的 `lastModified` | `u_7/u_30/u_90/u_365/u_old/unknown` |
| 是否本地已下载 | 本地模型库扫描 | `installed`（不限/只看已下载/只看未下载） |
| 是否推荐 | 既有硬件推荐逻辑 | `recommended` |

- 分面选项带**计数**（如"Q4_K_M (123)"），计数基于**关键词筛选后、结构化筛选前**的集合 ——
  否则用户一勾选，其它选项就消失了。计数为 0 的选项不渲染。
- 「量化格式」比的是 `quant_code` 而不是界面文案：把界面文案当筛选键会导致
  "界面语言一换、筛选条件就失效"。顺带修掉一个潜在 i18n-in-data 问题（原来的
  `quantization` 字段在未知时返回的是本地化的"未知"）。

### 排序

四个维度都**本地重排**（原因见第二节），并列时以仓库名做最终裁决保证可复现 ——
没有这一步，输入顺序来自网络，翻页时会出现重复/漏条。

## 六、任务七：性能与体验

- **虚拟滚动不做**：任务书自己写了"若每页固定 20 条，可不做虚拟滚动"，本实现就是固定 20 条。
- **加载不阻塞界面**：流式 + 异步；后端在忙时返回结构化 `busy: true`（新增字段），
  界面提示"后端正在处理其他任务（例如正在生成回复）"，而不是误报"模型中心坏了"。
  > 协议层限制如实说明：单条 stdout 是共享流，两个线程同时写会交错成坏 JSON，
  > 因此长任务期间后端**一律拒绝并发请求**（既有设计）。这一轮只是把"忙"变成了可识别的原因。
- **错误处理**：远端不可达、单页失败、返回格式异常各有文案与重试/继续入口。
- **离线降级**：远端不可达时展示**磁盘缓存 + 本地已下载模型 + 默认模型**，状态行标「📴 离线模式」。
- **默认模型钉住**：它**单独成一份 `pinned`，不进 `items`**，显示在结果列表上方、标注来源
  （"来源：config.json 里的默认模型仓库 …·固定显示，不计入下方的分页条数"）。
  任务书允许"不干扰分页计数"，这样"共 N 条 / 第 x / y 页"没有歧义。
- **顺带修掉的性能坑**：`_is_installed_repo` 原先对**每条**结果都调一次 `registry()`
  （读 JSON + 核对磁盘），一页 20 条时无感，自动加载到 5000 条就是 5000 次磁盘读写。
  改为"已下载仓库集合"算一次并缓存，下载/删除/重扫后失效。

## 七、与任务书的偏差

| # | 任务书原文 | 实际做法 | 原因 |
| --- | --- | --- | --- |
| 1 | "列表展示与排序均基于历史总下载量" | 展示与**本地**排序按历史总下载量；远端请求仍用 `sort=downloads`（30 天口径）来选取抓取窗口 | 服务端没有 `downloadsAllTime` 排序（实测 HTTP 400）。结果全部取回时本地排序即全局精确排序；撞上限时窗口的**成员**受 30 天排序影响，已在状态行与本文说明 |
| 2 | "筛选器为多选，条件之间为'与'关系" | **同维度内多选是"或"，不同维度之间是"且"** | 同维度真做"与"必然恒为空：一个模型不可能既"≤1B"又"20–40B"。取分面筛选的通行语义 |
| 3 | "筛选范围：仓库名、描述、标签" | 仓库名、标签、以及**由接口元数据合成的"描述"**（`pipeline_tag`/`library_name`/标签） | 列表接口**不返回模型卡正文**；要拿到真描述得对 5000 个仓库各发一次详情请求。完整正文仍在「详情」面板里 |
| 4 | "量化格式：从文件名解析" | 从**仓库名**解析（`Q4_K_M` 等），拿不到时归入"未标注"档 | 列表层只有仓库名，文件名要到详情里才有。多数 GGUF 仓库一个仓库含多种量化，仓库名不体现量化 —— 界面按计数如实呈现（实测 5000 条里只有 4 种量化代码），选具体量化版本仍要进详情 |
| 5 | "排序切换时重新请求远端…若已缓存该排序下的结果，优先使用缓存" | 完全照做（每个排序维度一个缓存桶） | — |
| 6 | 未提 | **远端搜索框取消"输入即搜"**，改为回车/按钮触发 | 全量加载下"输入即搜"会让敲第一个字母就触发数千条的加载 |
| 7 | "每页条数选择（可选）" | 做了（20/50/100，默认 20） | — |
| 8 | 任务八提到 `AUTOMATION_GUIDE`（若涉及） | **未改**，条件不成立 | 自动化流程不经过模型市场，该文档没有对应章节可写 |

## 八、未完成项与已知限制

1. **服务端 30 天排序影响"继续加载"的窗口成员**（偏差 1）。要彻底消除只能等 HF 提供
   all-time 排序；届时代码里把 `_SORT_MAP["downloads"]` 改一个值即可，本地重排逻辑不用动。
2. **没有模型卡正文**（偏差 3）：本地按描述筛选的能力受限于接口。
3. **单次加载 5000 条上限**：`GGUF` 这类宽关键词仍然需要用户点"继续加载"才能看到全部
   （当前实测 >5000 条）。这是刻意的安全上限，不是取不全。
4. **协议层不支持并发请求**（第六节）：聊天流式生成期间，设置窗口里的市场查询会收到
   `busy` 并被拒绝。界面已给出可读提示，但要真正并发需要给 stdout 加请求-响应配对，
   属于协议级改造，不在本任务范围。
5. **`tools/verify_release.ps1` 的 `Invoke-Python` 仍硬编码 `python`**：上一轮清单收口时
   记过同类问题（`Invoke-Python` 用开发环境解释器）。本轮新增的市场测试在该助手下面跑的是
   发布物后端（`--packaged`），所以不受影响，但这条技术债仍在。

## 九、验证方式与结果

### 自动化测试

`tools/test_model_market.py`（新增，**134 项断言全过**）：

- **加载器部分用本机 HTTP 桩**（`http.server`）仿真 HF 的真实行为：游标分页在 `Link` 头里、
  `expand` 只回被 expand 的字段、**重复 `expand` 即 400**、`limit` 静默截断。
  这样"口径回退 / 三个上限 / 重试与中止 / 续载 / 缓存与过期 / 离线降级 / Link 指向别的主机"
  每条都能精确构造、每次运行结果一致，**不依赖外部网络**。
- **查询引擎部分**覆盖分页边界、四种排序、五个筛选维度、三层数字、空结果出口、分面计数，
  以及"逐页遍历的并集等于全集（无重复无遗漏）"这条强断言。
- 最后驱动**真实后端**跑 `model_hub_load`（含进度事件）+ `model_hub_query`（翻页/排序/筛选/
  非法页码/空结果出口/缓存命中，实测缓存命中 0.36 秒）。

`tools/ui_probe.ps1` 新增 2c 段（真实窗口、UIA 驱动）：加载 → 分页控件存在与总条数显示 →
滚动列表验证分页控件不移位 → 下一页/末页/首页 → 页码跳转（合法/非法/回车）→
每页条数 20/50/100（真的选中 50 并断言总页数 250 → 100）→ 列表区域独立滚动 →
展开筛选面板勾选分面（断言本地筛选后条数 5000 → 242 且页码回 1）→
制造空结果验证"重新搜索远端"出口 → 重置筛选 → 默认模型钉住行。**全部通过**。

### UI 探针跑出来的四个真问题（都不是"探针自己闹脾气"）

这一轮最有价值的部分是**真界面探针把四个只有真人点才会碰到的问题逼了出来**：

1. **整轮加载失败的原因被吞掉** → 用户看到空列表，只能自己再点一次「搜索」/「刷新」。
   状态行只在 `has_more` 为真时才显示加载结果里那句话，而"加载中断（已取回 0 条）：…"
   恰恰发生在 `has_more` 为假时。修法：那句话**总是**显示。**这正是用户反馈的
   「搜索的时候要点刷新才能出来结果」的成因。**
2. **失败后不自动重试**：网络抖一下就空手而归，用户必须手动再点一次。
   修法：一轮下来一条都没取回、且结束原因是 `error`，等 1.2 秒**自动重试一次**，
   并在状态行写明"正在自动重试"（关键词本来就没命中时 `stop_reason=none`，不重试）。
3. **复选框挂错了事件**：分面复选框挂的是 `Click`，而 WPF 的
   `ToggleButtonAutomationPeer.Toggle()`（无障碍工具、UI 自动化、UI 探针都走这条）
   只调 `OnToggle()`、**不触发 `Click`** —— 鼠标点没问题、自动化点就"点了没反应"。
   改成 `Checked`/`Unchecked`（这也是复选框的正确事件）。
4. **`GetInt` 假设 JSON 数字都是整数**：`recommend_basis.ram_gb = 31.7` 是小数，
   `GetInt32()` 直接抛 `FormatException`（"One of the identified items was in an invalid
   format"），表现为**每次渲染推荐依据都报"本地筛选失败"**。这个坑一直在，
   只是旧代码只在"搜索结果出来后"才会读到 `ram_gb`，而旧探针从不搜索，所以没人碰到。
   改成"整数优先、小数四舍五入"。

另外两处是**测量/判据**本身的修正（写在代码注释里，避免下次又踩）：

- **"设置窗口打开耗时 < 500ms"量错了对象**：第一次对刚出现的窗口做 UIA 遍历要从零建立
  provider 树，这笔一次性开销（实测约 2 秒）被算进了计时。证据：同一份 `EchoDesk.exe`，
  在计时前先做一次 UIA 预热的探针量出来是 0.26 秒，不预热就是 2.3 秒。
  修法是在计时**之前**预热 UIA —— 门禁要求（<500ms）本身没问题，错的是测量点。
- **`Find-AnyById` 偶发返回 null**：同一轮里前一批控件全部找到、紧接的一批全部找不到、
  再往后又全部找到（UIA 客户端在界面忙碌时的瞬时失败）。改成内部重试 3 次，
  **断言没有放宽**（元素最终仍必须被找到）。
