## 一、任务书的两处口径问题（按"最合理理解"执行，如实记录）

**（1）文件名不符。** 指定的是 `prompts/EchoDesk-v0.2.1综合优化已知错误-1.md`，
目录里实际存在的是 `prompts/EchoDesk-v0.2.1优化已知问题-1.md`（最新的一份，文内标题一致）。
按"取最接近的现实文件"执行，未作询问。

**（2）任务三的前提与代码不符 —— 这是最重要的一处。**
任务书说"当前模型市场按硬件条件过滤推荐模型"。实测：**代码里没有任何按硬件过滤模型列表的逻辑**。
模型市场（`frontend\SettingsWindow.xaml.cs` + `backend\model_hub.py`）只有三个**用户可调**的过滤器
（排序方式、量化格式、最低下载量），全部由用户在界面上设置，与硬件无关；
硬件探测（`model_profile._read_machine_memory` + `recommend_config`）此前只用于"设置 → 模型"里的
能力画像与生成参数推荐，**从未参与市场列表**。

于是重新定位"默认模型 `Qwen3.5-0.8B-Q4_K_M.gguf` 显示不出来"的**真实根因**：

> 市场列表列的是**仓库**（如 `unsloth/Qwen3.5-0.8B-GGUF`），而默认值 `model_path` 是**文件名**；
> 列表完全由"按下载量排序的**一页**远端搜索结果"构成，**没有任何逻辑保证**默认模型所在的仓库会出现——
> 关键词搜不到、下载量排在几十名开外、或分页边界，任何一项都能让它缺席。

所以修法不是"放宽过滤"，而是**把默认模型的仓库钉进列表**（与搜索条件无关，永远在第一位）。
任务书要求的"显示全部"因而已达成（现在确实不隐藏任何条目），只是达成方式与它设想的"去掉过滤"不同。

## 二、任务一：无模型就绪（后端不再阻塞、不再退出）

### 实现

| 位置 | 改动 |
| --- | --- |
| `backend/llm_engine.py` | 新增 `NoModelError` 与 `LazyLLMEngine`（`LLMEngine` 的子类）：未加载时 `llm is None`，**保持同一个对象**，等模型到位后 `load()` 原地加载 |
| `backend/main.py` | `Backend.__init__(config, model_path="")`；`_build_engine` 在无路径时返回 `LazyLLMEngine`；新增 `model_ready` / `model_state()` / `guide_text()` / `load_model()` / `scan_models()`；`warmup()` 在无模型时跳过；`_attach_context()` 增加 `model_ready` 字段 |
| 启动流程 | 缺模型时**不再**征询后退出：建好 Backend → 发一条**非阻塞** `need_download`（`blocking:false`）→ 发 `ready`（带 `model_ready:false`、`model_state`、`model_missing`） |
| 删除 | `_await_download_decision()`、`_download_with_progress()`（前者专用）与 3 个随之失效的语言键 `sys.await_download_confirm` / `sys.model_declined` / `sys.model_missing_no_repo` |

### 关键决策：为什么用"同一个引擎对象"而不是"换一个引擎"

热加载有两条路：换一个新引擎对象，或让原对象内部把模型加载进来。这里选了后者，因为
`command_handler.llm_engine`、`summarizer.engine`、`Backend.llm` 等多处都持有引用，
换对象就要逐个重新接线，**漏一个就会"看起来加载成功了、实际还在用旧对象"**，而且是静默的。
`LazyLLMEngine` 只在"真的会碰到底层 `Llama` 对象"的入口改成抛 `NoModelError` 或退化为估算，
父类其余方法（清缓存、窗口描述、速度提示）照常可用。

### 功能边界（任务书表格的落地方式）

引导逻辑收口在**少数几个入口** `except` / 判断一次，而不是散落在几十处调用点（漏一处就是一个崩溃）：

| 类别 | 请求 | 无模型时行为 | 实现位置 |
| --- | --- | --- | --- |
| 推理 | `chat`、`chat_stream` | 返回引导文案并记入历史 | `_handle_chat` / `stream()` 开头的 `model_ready` 分支 |
| 依赖模型 | 分段摘要 | 说明需要模型并给出引导 | `summarize_current_file` 开头 |
| 依赖模型 | 自动化 | **先给引导，不打开浏览器** | `_stream_automation` 开头 |
| 不依赖模型 | 文件解析 | 照常解析并保留全文；过长时**不摘要也不截断** | `load_file_into_context` |
| 不依赖模型 | 技能市场 / 设置 / 模型市场 / 会话历史 | 照常 | 无需改动 |
| 状态查询 | `context`、`model_state` | `model_ready:false` + 真实原因 | `_attach_context`、`model_state()` |

token 计数在无模型时退化为 `len(text)//2`（`LazyLLMEngine.count_tokens`）——
文件解析、上下文占用显示、摘要触发判断都要用它，而这些**无模型时也必须能用**。

## 三、任务二 / 五：引导、重新扫描、热加载

- **引导文案**（`sys.no_model_guide`）包含：当前无可用模型、推理不可用、三条可行路径、
  以及**模型文件夹的真实路径**（不是占位符）。
- **`model_scan`**（新动作，「重新扫描模型文件夹」按钮）：重读模型目录，
  手工放入的 `.gguf` 会被登记；**只有一个模型时自动加载**并提示；空目录时明确说明目录路径。
- **`model_load`**（新动作，本地模型库里的「加载」按钮）：热加载单个模型。
- **下载即热加载**：`_stream_model_hub_download` 成功后调用 `load_model()`，
  响应带 `model_load` / `model_state`；失败时保持无模型状态并把原因写进 `done` 文案。
- **失败保持可重试**：损坏文件 / 格式不支持 / 内存不足都在 `load_model` 的异常分支里，
  只回报错误、不改动已加载的模型状态。

## 五、任务四：分段摘要的过程反馈、心跳、超时与中断

### 事件模型

`summarizer.py` **只抛结构化事件**（`phase` / `status` / `index` / `total` / `elapsed` /
`chunk_elapsed` / `chars` / `tokens` / `slow` / 各累计计数），**不含任何界面文案**——
摘要算法不应该关心当前是哪种界面语言，也不会把语言固化在导入时。
文案由 `main.py._summary_progress_text()` 按语言包解析后放进 `content` 字段，
前端既能显示文本、也能用结构化字段画进度。

### 四项要求的落地

| 要求 | 做法 |
| --- | --- |
| 过程可见 | 新增流式动作 `file_stream` 与 `summary_progress` 事件；前端在对话框里**就地更新同一条消息**（长文档十几段不会刷屏） |
| 不让用户干等 | 每段走 `engine.chat_stream` 逐 token 迭代，每隔 `heartbeat_seconds`（默认 5 秒）至少发一次心跳，心跳里带"当前段已生成多少字符" |
| 故障排查 | 正常耗时 → 只报进度；**偏慢**（超过 `slow_chunk_seconds`）→ 标注 `slow` 并继续；真故障 → 分状态报错（`failed` / `timeout` / 全部段落失败）并给恢复建议；"没动静"由心跳里的 `tokens` 字段暴露 |
| 超时与中断 | `chunk_timeout_seconds`（0 = 不限）+ `chunk_timeout_action` = `skip` / `retry` / `abort`；`action=stop` 置位的事件被逐 token 检查，**立刻**中止当前段 |
| 日志 | 只记段号、字符数、耗时、状态与计数，**从不记文档正文**（正文可能含合同金额、当事人） |

### 实现与任务书的三处偏差（都是刻意的，理由如下）

1. **中止不注入半份摘要**：任务书只说"能正确中断并清理"。这里选择在中止时返回
   `summarized=False`，原文完整保留在上下文中，由用户重试 —— 半份摘要静默进入上下文
   比失败更危险（用户会以为看到的是全文要点）。
2. **`retry` 只重试一次**：单段超时后重试一次；再超时按 `skip` 处理。否则一个病态段落
   可以把整篇时间耗光，与"不让用户干等"矛盾。
3. **非流式引擎只能段间中断**：没有 `chat_stream` 的引擎（例如测试里的假引擎、第三方实现）
   无法在段内打断，事件里以 `stream:false` 如实标注，**不假装**能中途打断。

### 新增配置（`config.json` 的 `summarize`）

`progress_events`（默认 true）、`heartbeat_seconds`（5.0）、`slow_chunk_seconds`（60）、
`chunk_timeout_seconds`（0）、`chunk_timeout_action`（`skip`，非法值回落）。

## 九、未完成 / 已知限制（如实列出）

1. **非流式引擎没有心跳**：没有 `chat_stream` 的引擎只能在段间报进度（事件里 `stream:false`）。
   本项目自带引擎都有流式接口，因此实际运行不受影响。
2. **`model_scan` 只扫配置的模型目录**（`model_hub.models_dir`），不做全盘搜索 ——
   全盘搜索既慢又涉及越权读取用户其它目录，不在本任务范围内。
3. **界面进度是单行就地更新**，不是带百分比条的独立控件：这一版把信息量放在"第几段/耗时/阶段/是否偏慢"，
   进度条需要知道"每段等长"这个前提，而段落长度会因为按句切分而波动，用它反而会误导。
4. **`SOURCE_DATE_EPOCH` 仍未做**（上一轮遗留）：让后端构建也字节可复现，
   需要再打一次包并重验，属独立改动。
5. **`verify_release.ps1` 的测试仍跑在全局开发环境**（上一轮已报告）：
   其 `Invoke-Python` 写死裸 `python`，与已修的 pyinstaller 是同一类问题。
