# v0.2.1 SBOM 与许可证清单环境收口记录

> 本文记录"`gen_sbom.py --check` 报 22 处不一致"这一问题的定位、收口过程与结果，
> 以及过程中发现的一处**超出本轮授权范围、需要决策**的发布物版本偏差（见第五节）。
> 所有结论均为实测，证据文件在 `artifacts\`（该目录不进库）。

## 一、现象与根因

`python tools\gen_sbom.py --check` 报 22 处不一致、退出码 1。基线明细：

| 类别 | 含义 | 数量 |
| --- | --- | --- |
| A | 清单里有、本机环境里没有 | 3 |
| B | 发布闭包里有、清单里没有 | 2 |
| C | 同名包版本不一致 | 17 |
| D | 许可证标注不一致 | 0 |
| E | 本机环境里有、但不在发布闭包也不在清单里（开发机残留） | 78（默认不阻断） |

**根因不是清单错，而是跑检查用的解释器不对**（实测确认，不是推测）：

* `docs\SBOM.json` 与 `docs\THIRD_PARTY_LICENSES.md` 是用**干净 venv**（`artifacts\clean-venv`，
  只装 `backend\requirements.txt`）生成的 —— 这也是 `tools\check_bundled_packages.py`
  注释里写明的既定设计（"清单代表*应该*随包分发什么"）。
* 那次核对用的是**本机全局 Python**（`C:\Users\backt\AppData\Local\Programs\Python\Python313\python.exe`），
  它有 **132** 个发行包，其中 **78** 个是开发期残留（easyocr / torch 链、extract-msg 链、
  ollama、msoffcrypto-tool 等），且多个包的版本与干净 venv 不同。
* 决定性证据：**用已有的干净 venv 解释器跑同一条 `--check` → A–E 全 0、退出码 0**
  （`artifacts\sbom-check-cleanvenv-existed.txt`）。
  也就是说，在本次收口**开始之前**，"干净环境口径"下的漂移就已经是 0；
  22 处差异 100% 由解释器选择造成。

B 类的两项值得单独说明，它是上一轮记录里 `httpx` / `httpx2` 之谜的完整解释：

| 环境 | `huggingface_hub` | 它声明的 HTTP 依赖 | 闭包里因此出现的包 |
| --- | --- | --- | --- |
| 全局开发环境 | 1.27.0 | `httpx<1,>=0.23.0` | `httpx 0.28.1` + `httpcore 1.0.9`（即 B 类两项） |
| 干净 venv | 2.0.0 | `httpx2<3,>=2.0.0` | `httpx2 2.13.1` + `httpcore2 2.13.1` |

即：闭包是按**当前环境里实际安装的那些版本**的 `Requires-Dist` 展开的，
两个环境装的是同一份 `requirements.txt`，但解析到的 `huggingface_hub` 大版本不同，
传递依赖自然分叉。

## 二、执行过程与收口结果

严格按任务书步骤执行：

1. 删除 `artifacts\clean-venv` 并用当前 Python 重建：`python -m venv artifacts\clean-venv`
2. 只装运行依赖：`artifacts\clean-venv\Scripts\python.exe -m pip install -r backend\requirements.txt`
3. 用干净解释器重跑：`tools\gen_licenses.py`、`tools\gen_sbom.py`
4. 验证：`artifacts\clean-venv\Scripts\python.exe tools\gen_sbom.py --check`

结果：

| 检查 | 结果 |
| --- | --- |
| `gen_sbom.py --check` | **A–E 全 0 → 退出码 0** |
| `gen_sbom.py --check --strict-env`（干净环境专用，把 E 类也算失败） | **A–E 全 0 → 退出码 0** |
| `check_requirements.py --venv artifacts\clean-venv\...` | 14/14 通过，`requirements.txt 覆盖了后端全部第三方顶层导入` |

**重建前后的 venv 逐个包比对**（`artifacts\clean-venv-pkgs-existed.tsv` ↔ `...-rebuilt.tsv`）：
55 个发行包，只有两项不同 ——

* `filelock` 4.0.3 → **4.0.4**：上游在此期间发了新版，属正常的"从零建环境"结果；
* `pip` 25.1.1 → 26.2.1：`ensurepip` 自带的 bootstrap 版本。

**一处主动偏差（已做，如实记录）**：重建后额外执行了
`-m pip install --upgrade pip`，把 pip 提到 26.2.1，以复现清单里原有的 bootstrap 基线。
理由：pip 不随发布物分发，若不提，这次提交会往合规清单里塞进一个与"收口"毫无关系的
`pip 25.1.1` 版本变更，让评审者去追一个不存在的问题。

## 四、顺带修掉的一处陈旧：中文译本落后于英文版

**发现**：`docs\THIRD_PARTY_LICENSES.zh-Hans.md` 还停在 **52 个包 / 13 条直接依赖**，
而英文默认版已是 **55 个包 / 17 条直接依赖**。具体缺：

* 明细表缺 3 行：`cffi`、`cryptography`、`pycparser`；
* 直接依赖表缺 4 行：`cryptography`、`duckduckgo_search`、`llama_cpp_python`、`urllib3`；
* 正文首句"扫描到的 Python 发行包共 **52** 个"与英文版的 55 不符。

这三行正是上一轮"把 `cryptography` 补进 `requirements.txt`"时新增的包，
而四条直接依赖是更早修 `gen_licenses.py` 名称归一化（`llama_cpp_python` /
`duckduckgo_search` 曾因下划线被漏出直接依赖表）时新增的 —— 译本一次都没跟上。

**为什么一直没被发现**：`tools\check_lang.py` 的"共用双语文档"检查只比**章节结构**
（两份都是 5 个二级标题、编号一致），表格内容不在校验范围内。

**修法**：译本 = 译本抬头（前 7 行，含"以英文版为准"声明）+ 英文默认版正文（第 3 行起），
按此重装后两张数据表 72 行逐行一致。译本保持 LF 落盘（与它原有换行一致）。

**新增门禁**（`tools\check_lang.py`）：新增 `DATA_TABLE_PAIRS` 与 `check_data_tables()`，
对许可证清单这一对**按表分别**逐行核对两张数据表。

* 为什么只对这一份、不做成通用规则：另外三对（`EULA` / `PRIVACY` / `ENCRYPTED_DOCUMENTS`）
  的表格单元格是**叙述文字**，译文与英文版就不该逐字相同，逐行比对必然误报。
  许可证清单的表格是**数据**（包名 / 版本 / 许可证标识符），不随语言变化，必须一致。
* 为什么按表分别比对：第一版把所有表合成一个集合，结果"直接依赖表整段缺 4 行"
  被明细表里的同名行**掩盖**了（cryptography / duckduckgo_search / llama_cpp_python /
  urllib3 在两张表里都出现），是改成按表比对后才暴露出来的。
* 有效性证据：门禁加上、译本尚未修复时，它准确报出 3 处 ——
  明细表缺 3 行、`filelock` 版本不符（4.0.4 vs 4.0.3）、直接依赖表缺 4 行；
  修复后转为通过（2 张表 / 72 行）。

**为什么不用"生成器直接代写中文译本"来根治**：看起来更省事，但仓库里已经注明
"彻底修法是让生成器输出**英文**默认版（属独立任务）"。到那时中文译本必须是**真翻译**，
而不是英文正文的逐字复制，生成器代写会挡在那条路上。因此选择用**门禁**把漂移挡住、
把翻译内容留给人工决定。

## 五、SBOM 声明的版本 ≠ 发布物里的版本（本轮只报告，后续提交已按方向 1 实施）

本轮只报告不动手（"只收口清单、不改依赖"的授权边界）；后续提交采纳方向 1 修掉了根因，
见 `records/v0.2.1-版本同步与重打包记录.md`。

**事实**：发布物 `publish\EchoDesk-v0.2.1\app\backend\_internal` 里保留了 11 个
`.dist-info`，它们的版本与本机**全局**开发环境 **11/11 完全一致**，与本次生成清单所用的
干净 venv 有 **6 处不同**：

| 包 | 发布物（=`_internal` 的 dist-info） | 干净 venv（=清单与 SBOM 写的） |
| --- | --- | --- |
| click | 8.4.2 | **8.5.0** |
| cryptography | 50.0.0 | **50.0.1** |
| huggingface_hub | 1.27.0 | **2.0.0** |
| numpy | 2.5.2 | **2.5.3** |
| pydantic | 2.13.4 | **2.13.5** |
| tqdm | 4.70.0 | **4.70.1** |
| duckduckgo_search / llama_cpp_python / MarkupSafe / playwright / pywin32 | 一致 | 一致 |

**原因**：`tools\build_release.ps1:241` 调用的是 PATH 上的 `pyinstaller`，
它实际解析到 `C:\Users\backt\AppData\Local\Programs\Python\Python313\Scripts\pyinstaller.exe`
（**全局开发环境**），而不是干净 venv 里的那一个。所以后端是"在开发机环境里分析打包"的，
而 SBOM / 清单描述的是干净 venv —— 两边口径不同，这正是
`check_bundled_packages.py` 开头注释所承认的那处差异。

> **更正（后续提交）**：本节最初写的是"**5 处不同**"，并漏了 `tqdm`。
> 实际是 **6 处** —— 发布物里是 `tqdm 4.70.0`，清单声明的是 `4.70.1`。
> 差错是人工逐项比对时漏行造成的；后来给 `check_bundled_packages.py` 加版本门禁时，
> 用 `artifacts\replay_old_artifact_gate.py` 回放旧发布物的 `.dist-info` 清单，
> 它一次就报出 6 处，这才发现少算了一处。表格与结论已按实测更正。

**影响**：随发布物分发的 `docs\SBOM.json`（并且已被 `publish\SHA256SUMS.txt` 收录、锁定哈希）
对这 6 个包声明了**从未随包分发**的版本号。对外部审计方而言，这是一份不准确的物料清单。
`check_bundled_packages.py` 只比对"`_internal` 的顶层模块名能否对应到已声明的发行包"
（当时 0 可疑），**版本差异不在它的射程内**，所以它一直是绿的。

**两个方向（本轮均未执行，方向 1 已在后续提交中实施）**：

1. **让发布物与清单一致（推荐，已采纳）**：用干净 venv 的 PyInstaller 打包
   （`artifacts\clean-venv\Scripts\pyinstaller.exe`），使发布物与合规清单口径统一。
   代价：要重打两份安装程序、重算 `SHA256SUMS.txt`，可能需要移动标签。
   → 实施过程与结果见 `records/v0.2.1-版本同步与重打包记录.md`。
2. **让清单与发布物一致**：把生成环境改成打包机（全局）环境。**不推荐** ——
   `gen_sbom.py --scope release` 虽然只保留闭包内的包、不会把 78 个开发残留写进去，
   但 `gen_licenses.py` 的「全部 Python 发行包明细」会列全 132 个，等于把开发机残留
   写进对外合规清单。

推荐方向 1 的另一个理由：它顺带把"打包机环境漂移"这个更根本的问题一起收掉，
而 `requirements.txt` 已经为它准备好了 —— 干净环境 55 个包、`--strict-env` 为 0。

## 七、未做的事

* **未重打安装程序**：本轮只收口清单。`publish\` 与两份 `Setup.exe` 里的
  `docs\SBOM.json` / `THIRD_PARTY_LICENSES*.md` 仍是修正前的版本
  （实测：`publish\EchoDesk-v0.2.1\docs\SBOM.json` 的 `created` 仍是
  `2026-09-25T13:28:46Z`、`filelock` 仍是 4.0.3），`SHA256SUMS.txt` 里那三行哈希
  也已与仓库现状不符。`publish/` 与 `artifacts/` 都在 `.gitignore` 里，
  因此**仓库状态不受影响**，但发布物要重新生成才能带上修正后的清单。
* **未动 `requirements.txt`**（无需补声明）。
* **未改 `tools\gen_licenses.py`**（理由见第四节末）。
* **观察到但未改**：`gen_licenses.py` 以文本模式写 `docs\THIRD_PARTY_LICENSES.md`，
  在 Windows 上落盘是 CRLF，而 `.gitattributes` 声明 `*.md text eol=lf`
  （`gen_sbom.py` 则显式用 `newline="\n"`）。每次 `git diff` 都会因此多一句 warning；
  提交内容不受影响（git 按属性归一化）。修法是生成器那一行加 `newline="\n"`，属独立小事。
