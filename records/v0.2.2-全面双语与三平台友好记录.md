### 1.3 审计工具本身踩到的三个坑（工具可信度问题）

这三个都是"审计结论错得看不出错"的类型，记下来免得下次重犯：

1. **`git ls-files` 会把非 ASCII 路径转义成八进制** —— 不加 `-z` 时，`records/v0.2.1-跨平台记录.md`
   会变成 `records/v0.2.1-/344/277/256/…`，于是分类、成对性判断、报告全部错位。
   第一版报告里 20 个中文名记录文件全被归进「其它」。修法：`git ls-files -z` + 按 NUL 切分。
2. **`re.match` 让"不带 `^` 的模式"永远匹配不上** —— 类型规则里 `\.(ico|png|icns)$` 这类写法在
   `re.match` 下从字符串第 0 位开始比，永远失败：`assets/EchoDesk.ico`、`assets/EchoDesk.png`
   全落进「其它」。修法：改用 `re.search`。
3. **配对的"无扩展名"分支漏了** —— `LICENSE` ↔ `LICENSE.zh-Hans.md` 是一对，但分组时只收 `.md`
   结尾的文件，于是 `LICENSE` 被排除，**一对完整成对的文件被报成"两个单语"**。
   修法：分组时额外收 `LICENSE`/`NOTICE` 这类无扩展名文件，并把基名统一去掉 `.md`。

### 1.4 第一版门禁报了 18 项"问题"，其中没有一项是真缺陷

第一版 `--check` 自己也查了 `docs/` 成对文档的标题层级序列与文首声明，一次报出 18 项。
逐项核对后结论是：**全是"我的规则 ≠ 项目既定规则"**——
`LICENSE`/`NOTICE` 是法律文本（不该加译者声明）、`docs/DEVELOPER.md` 是指针文件（结构与正文不同）、
`docs/THIRD_PARTY_LICENSES.md` 有**写在注释里的已知偏差白名单**……

而 `tools/check_lang.py` **早就在做这件事**，而且做得更好：它比的是二级章节的**编号序列**
（认得 `## 三、标题` 这种中文编号）、章数不同时的降级策略、以及一张写明原因的偏差表。

**决策：本门禁不再重复 `check_lang.py` 的活**，只保留三件确实没人管的事（见 7.1）。
两个门禁对同一件事各有一套口径，只会制造噪音和互相打架的修复方向。这一段写进工具 docstring，
免得后来者再写第三套。

### 2.2 三平台命令示例的呈现方式（任务书交由 DSH 决定）

**选定：统一语法优先 + 差异单独标注。**

- 优先给三平台通用的写法：`python` 而不是 `py -3`、`git` 而不是 `git.exe`、正斜杠路径、`~/.ssh`；

覆盖的七类命令：安装、构建、运行、打包、测试、Git 操作、依赖安装 —— 由三份文档承担

## 三、读代码之后发现的真缺陷（本轮顺带修掉）

这一节的每一处都不是"文档措辞"问题，而是**代码或文档与实际行为不符**。它们都是
"按任务书要求核对事实"时撞出来的 —— 这是本轮意外但最有价值的产出。

### 3.1 用户数据目录：前后端在 standalone 布局下算出**两个不同的目录**（真实缺陷）

后端的 `backend/config.py:user_data_root()` 只判断"父目录是否叫 `app`"，而前端（Avalonia 的
`UserPaths.DataRoot`）判断的是"程序目录是否叫 `app`"。两种布局下结果如下：

| 布局 | `config.py` 在哪 | 修前后端结果 | 前端结果 | 是否一致 |
| :--- | :--- | :--- | :--- | :--- |
| Windows 安装/便携（PyInstaller onedir） | `<发布>\app\backend\` | `<发布>` | `<发布>` | ✅ |
| **Linux/macOS（standalone）** | `<发布>/app/backend/app/` | **`<发布>/app/backend`** | `<发布>` | ❌ |
| 源码检出 | `<仓库>/backend/` | `<仓库>` | — | ✅ |

后果：同一个发布物里，前端把 `snippets.json`、`ui_state.json` 写到 `<发布>/`，
后端把 `session.json`、`results/`、缓存写到 `<发布>/app/backend/` —— **用户看不到自己的历史**，
而且这种缺陷在界面上完全不像"路径错了"，只表现为"设置没了""历史没了"。

**修法**：`user_data_root()` 改为**逐级向上跳过容器目录**（`app` / `backend`），
第一个不在其中的祖先就是数据根。四种真实布局都得到同一个答案（已加校验，见 7.2）。
**这是本轮唯一的代码逻辑改动**，与任务书任务三"不改动代码逻辑，只改注释"的约束有出入，
理由与影响写在 4.2。

### 3.2 后端工作目录：模型/插件目录在三平台上落点不同（真实缺陷）

后端所有相对路径都是相对**工作目录**解析的（`models_dir` 默认 `"models"`、
`skills_runtime` 的 `skills_dev`）。Windows 的 WPF 前端把工作目录设为后端 exe 所在目录
（`…\app\backend\`），而 Avalonia 原来传的是 `backend/app` ——
于是 Linux/macOS 上模型目录变成 `…/app/backend/app/models/`，
**用户按文档把 `.gguf` 放对了地方却不被识别**。

**修法（三处一起改，口径统一）**：
- `frontend-avalonia/.../Services/BackendService.cs`：`WorkDirectory` 由 `backend/app` 改为
  `backend`，参数由绝对脚本路径改为相对 `app/main.py`；
- `tools/pack_backend.py` 的 `run-backend.sh` / `run-backend.bat`：加 `cd` 到脚本所在目录
  （原来 cwd 跟着调用者跑，同一个包在不同地方启动会去找不同的 `models/`）；
- `tools/check_standalone_backend.py`：协议验证的调用口径跟着改成 `cwd=<tree>` + `app/main.py`
  —— **原来用 `cwd=app` 验证，于是"验证通过"并不代表发布物里那条路径也对**。

### 3.3 CI 里一条门禁因为写死版本号而**永远跳过**（真实缺陷）

`.github/workflows/ci.yml` 的 `release-gates` 作业里：

```powershell
if (-not (Test-Path "publish\EchoDesk-v0.2.1\app\backend\_internal")) { Write-Host "…跳过…"; exit 0 }
```

版本升到 v0.2.2 之后这个判断**永远为假**，于是"打包模块比对"这条门禁再也没跑过；
而日志只写"本作业未构建发布物"，看起来完全合理。这是**同类缺陷的第三次复发**
（前两次：`verify_release.ps1` 的 `$Version` 默认值、`check_bundled_packages.py` 的 `INTERNAL`），
说明"默认值/路径里写死版本号"是这个仓库的**系统性弱点**。
**修法**：从 `backend/version.py` 读 `APP_VERSION`。

### 3.4 文档里写着代码中不存在的路径：`%APPDATA%\EchoDesk`

`frontend-avalonia/.../UserPaths.cs`、`AppSettings.cs`、`SnippetStore.cs`、`PlatformInfo.cs`
的注释都写着"Windows 用 `%APPDATA%\EchoDesk`"，`docs/*/COMPLIANCE.md` 沿用同一说法。
核对代码后确认：**这个仓库里没有任何一条路径写到 `%APPDATA%`** ——
- WPF 的 `ShortcutService.UserDataDirectory`：`ECHODESK_DATA` → 程序目录名为 `app` 取上级 → 程序目录；
- Avalonia 的 `UserPaths.DataRoot`：Windows 分支同样是程序目录；
- `grep APPDATA frontend/` 无任何代码命中。

**修法**：
1. 改正 4 处源码注释（并标明"此前写错了"）；
2. 删除 `PlatformInfo.UserDataDirectoryName` —— 它**定义后从未被调用**（`git grep` 只有定义行），
   三元表达式两个分支还完全相同（`IsWindows ? "EchoDesk" : "EchoDesk"`），
   死代码 + 错注释的组合最容易被后来者当真；
3. 改正 `CONTRIBUTING`、`docs/*/DEVELOPER.md` 里的表述，并明确写"**它不是 `%APPDATA%`**"；
4. `docs/*/FAQ.md`、`docs/*/README.md`、`docs/*/AUTOMATION_GUIDE.md` 里
   "程序目录本身（若就装在 `%APPDATA%\EchoDesk` 下，那它就是它）"这种**写法是准确的**（它讲的是
   "如果碰巧装在那里"），保留。

### 3.5 合规文档里对安装程序默认目录的描述与实际行为不符（真实缺陷）

`docs/*/COMPLIANCE.md` 写安装程序"默认装到 `{autopf}\EchoDesk`，非管理员安装落到
`%LOCALAPPDATA%\Programs\EchoDesk`"。而 `tools/installer.iss` 的实际行为是：

```
DefaultDirName={code:GetDefaultDir}     ; GetDefaultDir = ExtractFileDir(ExpandConstant('{srcexe}'))
AppendDefaultDirName=no
UsePreviousAppDir=no
PrivilegesRequired=lowest
```

即**默认装到安装程序自己所在的文件夹**，与 `%LOCALAPPDATA%\Programs` 无关。
这对企业部署者是有实际影响的描述（"装完在哪个目录、那个目录可不可写"直接决定要不要外移产物路径）。
**修法**：按 `installer.iss` 的实际行为重写该段（中英两版），并注明"本文档早前的版本写错了"。

### 3.6 `docs/en/FAQ.md` 的"适用版本"停在上一个版本

`docs/en/FAQ.md:3` 是 `Applies to version: v0.2.1`，中文版是 `v0.2.2`。
本轮版本号扫描时用的词表没覆盖 `Applies to version` 这一句，所以上一轮漏掉了。已统一为 v0.2.2。

### 3.7 `pack_crossplatform.py` 的顶层文件清单漏了英文 `NOTICE`（合规问题）

跨平台发布物的 `TOP_LEVEL_FILES` 里有 `NOTICE.zh-Hans.md`，**却没有 `NOTICE`**（英文正本）；
`SECURITY`、`CONTRIBUTING`、`CODE_OF_CONDUCT` 三对也全都不在清单里，
而 `tools/build_release.ps1` 的 Windows 发布目录这几样都有。
对外分发时"只给译本、不给正本"是**合规问题**而不是排版问题（Apache-2.0 要求随分发保留 NOTICE 原文）。
**修法**：清单补齐到 14 项，并且**缺文件时要点名报出来**（原来 `if os.path.isfile(src)` 静默跳过，
这正是漏掉 NOTICE 却没人发现的原因）。

## 四、任务三：代码注释的双语策略（决策与理由）

### 4.1 决策：**保留中文注释为主，新增注释按"读者是谁"决定；不逐文件改中英双语**

| 范围 | 策略 | 理由 |
| :--- | :--- | :--- |
| 既有 `backend/`、`frontend/`、`frontend-avalonia/` 注释 | **保留中文**，不做无差别双语化 | 30 个后端文件 + 59 个前端文件全部双语会让注释体积翻倍、评审面铺满整个仓库，而**信息量不变**；主要维护者是中文使用者（任务书自己也这么描述） |
| 本轮**新增/修改**的注释 | 中文为主，**平台相关处必须写明适用平台** | 新增注释的读者是"下一个改这里的人" |
| 面向贡献者的**公共约定**（命令、路径、结构） | 写进文档（`CONTRIBUTING`、`docs/*/DEVELOPER.md`）而不是散在代码里 | 这些约定需要被检索到，代码注释检索不到 |

**为什么不选"统一英文"**：任务书建议"新增注释统一英文"，但那会让既有中文注释与新增英文注释
在同一文件里混杂，读者需要在两种语言间切换；而本项目的**文档正本已经是英文**
（`README.md`、`docs/en/*`、`.zh-Hans.md` 译本），英文读者走文档即可，
代码注释保持单一语言（中文）反而更一致。**这是与任务书建议不同的选择，理由如上。**

### 4.2 平台相关代码的标注（做了两类）

**第一类：整个脚本/工程只在一个平台成立 → 在文件头声明一次。**

给 `tools/` 下 12 个 `.ps1` 与 2 个 `.bat` 各加了一行文件头标注，例如：

```
# 适用平台：Windows 发布链（PyInstaller + rcedit + Inno Setup），三平台各自有别的打包脚本
```

## 六、任务五 / 六 / 七

### 6.1 配置示例：从"逐字复制"改为"生成时注入双语说明"

`config.example.json` 原来是 `Copy-Item backend/config.json`（逐字复制）。用户拿到的是
200 多行没有任何解释的 JSON：字段什么意思、改了会不会生效、**"用户数据目录"在他的平台上到底是哪个路径**，
全都要去翻文档。任务书 5.1 要求的正是这件事。

**做法**：新增 `tools/gen_config_example.py`，在副本上注入两个字段：

```
"_comment"          —— 这个文件是什么、怎么用它、覆盖机制（config.user.json）、路径怎么写（中英双语）
"_platform_paths"   —— 用户数据 / 结果 / 模型 三个目录的三平台对照
```

**为什么不直接往 `backend/config.json` 里加 `_comment` 字段**：那是**运行期**配置，会被 pydantic
加载。往里塞非模型字段是在赌"模型允许额外字段"，赌输的后果是**后端启动即失败**。
注入放在**副本**上，运行期配置一个字不动（工具里写明了这个理由）。
生成器是 Python，因此 Windows 发布链（`build_release.ps1`）与跨平台打包
（`pack_crossplatform.py`）走同一条路径、得到同一份结果，口径不会漂移。

顺带修掉一处误导：路径说明原本想写 `C:\Users\<用户名>\...`，但 JSON 里反斜杠必须转义
（于是文件里显示成 `C:\\Users`，读者会以为要敲两个反斜杠）。现在改为**推荐一律写正斜杠**
（Windows 也接受），三平台通用且不用转义。

### 8.3 本轮发布管理与标签推进（重要决定）

**决定：把 `v0.2.2` 标签推进到本轮的提交。**

理由：
1. 本轮任务书本身就叫 `prompts/EchoDesk-v0.2.2全面双语与三平台友好.md`，
   `backend/version.py` 也已经是 `v0.2.2` —— 两轮工作同属 v0.2.2 这个版本；
2. v0.2.2 的 GitHub Release 目前**只是草稿清单、尚未发布**（本机无凭据，创建 Release 是人工步骤），
   因此此时推进标签没有"已发布版本被改写"的问题；
3. 若不推进，就会出现"安装包自称 v0.2.2、而 v0.2.2 标签指向不含该安装包的提交"——
   本项目最看重的**归档 ⟷ 提交 ⟷ 标签**三者对应关系会断掉。

**代价（必须知道）**：
- 标签需要**强制推送**（`git push --force origin v0.2.2`）；
- `publish/archive/v0.2.2/` 里上一份产物移入 `superseded/` 留证，
  `MANIFEST.json` 更新为新提交 SHA 并记录这次推进；
- 若维护者此前已经基于旧标签草拟了 Release 说明，需要重新生成一遍
  （`artifacts/gen_release_notes.py` 可复刻 CI 的填充逻辑）。

**同类做法在本仓库有先例**：v0.2.1 曾因"跨平台工作被误并入 v0.2.1"而把标签从跨平台提交
移回跨平台之前的提交（见 `records/v0.2.1-发布记录.md` §30）。本轮是反方向的同一操作。

## 十一、本轮自己制造并修掉的两处回归（如实记录）

"三平台友好"这类改动最容易的翻车方式，是**在改的过程中把原本能跑的东西弄坏**。
本轮真的弄坏了两次，靠"改完必须真跑一遍构建/门禁"才发现。

### 11.1 给 `.bat` 加中文注释，**把发布构建弄失败了**

我给 `tools/set_metadata.bat` 在文件**最前面**加了一行中文 `rem`（平台标注）。而该文件的结构是
`@echo off` → `chcp 65001 >nul` → 若干中文注释。于是 cmd.exe 用**传统代码页**
（简体中文 Windows 上是 GBK）去解析那行 UTF-8 中文，多字节序列把行尾吃掉，
后面的内容被当成命令执行：

```
C:\...\EchoDesk>get
'get' is not recognized as an internal or external command, operable program or batch file.
!! 发布构建失败：元数据写入 失败（退出码 1）
```

`tools/fetch_tools.bat` 更危险：它**根本没有 `chcp` 行**，整个文件都在这个风险下
（它带着中文注释却能跑通属于历史运气，不是设计）。

**修法**：`set_metadata.bat` 的标注移到 `chcp 65001` **之后**；`fetch_tools.bat` **补上
`chcp 65001 >nul`**（让它原有与新增的中文注释都真正安全）。
并把这个坑做成门禁规则（`audit_repo.py --check` 的第 4 条）：
**非 ASCII 不得出现在代码页切换之前**（没有 `chcp` 行则整个文件都不允许）。
反证测试通过 —— 放一个"中文在 chcp 之前"的 `.bat` 进去，门禁报错并以 1 退出。

### 11.2 用 PowerShell 改文件引入了 5 个 UTF-8 BOM

我用 `Set-Content -Encoding UTF8` 改了 5 个文件（`docs/en/FAQ.md` 与 4 个 `.ps1`），
而 **Windows PowerShell 5.1 的 `-Encoding UTF8` 会写入 BOM**。仓库约定是无 BOM
（`tools/check_docs_links.ps1` 对 `.md` 会直接报警，原始 `.ps1`/`.bat` 也全部无 BOM）。
`check_docs_links.ps1` 的 WARN 把它抓了出来：

```
WARN docs/en/FAQ.md: 带 UTF-8 BOM（仓库约定 .md 不带 BOM）
```

**修法**：写一个只做"去 BOM"的小脚本按字节处理，并全仓库复扫确认。
**教训**：在 PowerShell 里改文本文件，别用 `Set-Content -Encoding UTF8`
（要么用 `-Encoding utf8NoBOM`（PS 7+），要么用 Python 的 `newline=""` 精确写）。

### 11.3 顺带一个工具教训：`String.Replace` 没有三参重载

修 `.bat` 时我写了 `$t.Replace($a, $b, 1)`（想只替换第一处），.NET Framework 的
`String.Replace` 只有两参重载 → 抛异常。**幸运的是异常发生在 `WriteAllText` 之前，
文件没有被写坏**（如果顺序反过来，就会写出一份"删掉了旧行、没加新行"的文件）。
结论：批量改文件要"先算完整结果、再一次性写入"，并且每一步都要能重放。
## 十二、本轮教训（写给下一轮）

1. **中文技术写作里嵌入 ASCII 双引号会截断 Python 字符串** —— 本轮在三个新工具里连犯三次
   （`add("…"未被忽略"…")`）。写成「」或在写完后立刻 `ast.parse` 复验，是唯一有效的防线
   （我试过写扫描器，但 `"""` 文档串本身就有奇数个引号，噪音淹没了信号）。
2. **"写死版本号/路径"是这个仓库的系统性弱点** —— 同一类缺陷已复发三次
   （`verify_release.ps1`、`check_bundled_packages.py`、`ci.yml`）。凡是"某个文件在某个版本目录下"
   的判断，一律从 `backend/version.py` 取版本，不要写常量。
3. **审计工具的结论错起来是"无声的"** —— 编码、正则锚点、配对规则三处小错会让整份报告失真，
   而报告"看起来很正常"。因此本轮给审计工具写了反证测试，并把作用域（只审计被跟踪文件）写进注释。
4. **给子代理的"权威约定"必须自己先核对** —— 我在任务书基础上转述的 `%APPDATA%\EchoDesk`
   是错的（任务书本身就错），四个子代理里有两个据此写出了错误文档，最后要回头逐个纠正。
   **任务书不是事实来源，代码才是。**
5. **不要造第二套门禁** —— 第一版 `audit_repo.py --check` 与 `check_lang.py` 对同一件事各有一套口径，
   报出 18 项"问题"全是噪音。发现重叠时要**收敛到一处**并写清分工。
