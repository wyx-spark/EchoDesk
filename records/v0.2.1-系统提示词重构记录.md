# v0.2.1 系统提示词重构 记录

任务书：`prompts/EchoDesk-v0.2.1系统提示词重构.md`
前置轮次：`records/v0.2.1-提示词优化记录.md`（给每个模式补齐"六要素"）、
`records/v0.2.1-研发记录.md`（提示词工程的整体由来）

本轮**不是**再给提示词加内容，而是修上一轮的副作用：约束加码之后，模型对任何问题都套
固定格式、信息不全就拒绝作答、用户说不清时只会反问 —— 也就是任务书里的三个现象。

---

## 一、诊断：三个现象各追到哪几句

审计口径：任务书要求"先读 `conversation.py` 的 `MODES` 与 `prompts.py`，以实际存在的
模式与提示词为准"。实际读下来是**两层提示词、四个位置**在共同施压：

| 层 | 位置 | 作用 |
| :--- | :--- | :--- |
| 模式层 | `conversation.MODES`（6 个） | 场景与语气，含"六要素" |
| 共享层 | `conversation._CORE_RULES` | 视角 / 边界 / 输出纪律（3 条） |
| 任务层 | `prompts.TASK_TEMPLATES`（6 个） | `/task` 套用的本轮输出格式 |
| 会话层 | `prompts.is_vague_question` + `clarification_prompt` | 模糊提问的短路话术 |

### 现象一：总按提示词分点说明

| 句子 | 为什么致害 |
| :--- | :--- |
| `general`：“需要分点时写「1. 2. 3.」” | 只说了"要分点时怎么写"，**没说什么时候不必分点**。模型默认"列三条"最稳妥。 |
| `summary`：“先一句话结论；**再**用不超过 8 条要点列出关键信息” | "再"是无条件的。130 字的通知也照样列要点——实测 0.6B 列 4 条、1.7B 列 **7 条**。 |
| `summary` 任务模板：“先用一句话给出全文结论；**再**用不超过 8 条要点” | 同一要求在两处各写一遍，措辞都是无条件的。 |
| `code`：“先一句话结论；**再**给最小修改片段；**最后**给一条验证方法” | 三段结构无条件。问"这个 API 怎么用"也会收到代码块 + 验证步骤（`code` 任务模板同样三段）。 |
| `prompts.build_system_prompt` 结尾：“[重要] 严格遵守上述输出格式” | 把上面的无条件格式**升级成硬要求**：小模型读到"严格遵守"就不再判断详略。 |
| `_CORE_RULES` 第 3 条 | 只有"输出纪律"（不要开场白/复述），**没有任何一条讲详略**。 |

### 现象二：没有详细信息就不推测

| 句子 | 为什么致害 |
| :--- | :--- |
| `_CORE_RULES` 第 2 条：“信息不足到无法作答时，**先问清最关键的一点再回答**” | 顺序写反了：先问 → 于是"没有可回答的内容"成了合法输出。 |
| `contract` 边界：“找不到对应条款时写「未见相关约定」，不要臆测” | 与上一条叠加，模型选择最保守写法。实测"这个条款有问题吗"在 0.6B/1.7B 下都只回**「未见相关约定」**（4~6 字）。 |
| `contract` 语气：“**宁可**写「需人工确认」，也不给确定结论” | 把"拒绝"说成了美德。 |
| `reason` 任务模板 `cot`：“信息不足时**先追问**，而不是猜一个答案” | 第三处重复同一顺序，且措辞最硬。 |
| 自定义指令包装语：“信息不足到无法作答时，应先问清最关键的一点” | 第四处。四层都这么说，模型没有别的选择。 |

### 现象三：用户不知如何表达时模型也帮不上

- 会话层唯一的机制是**追问三点**（`task.clarify_prompt`：对象 / 输出形式 / 约束）——
  它把组织语言的责任推回给"本来就说不清"的用户，且只在"无历史且无文件"时触发。
- 真正常见的场景（已上传文件、问"这个怎么办"）连追问都不触发，只剩
  `general` 那句"按最可能的一种回答，并在最后一句说明另一种理解是什么"；
  实测 0.6B 输出的是抽象说明（"另一种理解是……"），**不是可选方向**。
- 没有任何模式或机制"替用户把可能的意思说出来"。

### 上一轮为什么没发现

上一轮的验证是"结构检查（五要素齐备）+ 长度断言 + 单次抽查（`artifacts/ab_prompts.py`
用合同审查场景跑一次）"。"审查这份合同条款"本来就是**该详细回答**的问题，
正好掩盖了"简单问题也被套满格式"；而"信息不全"根本没进过抽查场景。
本轮因此把抽查升级成**带客观判据的对比测试**（见第三节）。

## 二、本轮实现

### 2.1 共享主干：3 条 → 7 条，新增的四条都是"放松"

`conversation._CORE_RULES`（全部模式共用一份）：

| 条目 | 内容要点 | 性质 |
| :--- | :--- | :--- |
| 1. 视角 | 「用户」指提问的人；复述时引用他最近一次输入 | 保留 |
| 2. 边界 | 不知道就说不知道；**不编造**事实、数据、法条、条款或出处 | 保留（底线） |
| 3. 详略自定 | 能一句话答完就一句话；复杂才分点；别为凑格式硬分点 | **新增** |
| 4. 先答后问 | 信息不全时先按最可能的一种理解作答 → 说明假设 → 再问要不要展开；**不要只回「请提供更多信息」** | **新增（改写第 2 条）。顺序反转是本轮的核心** |
| 5. 摊开推测 | 只有当结论确实取决于没给的信息时才用「如果是 A，建议 X；如果是 B，建议 Y」，并标成推测 | **新增** |
| 6. 引导 | 问题含糊时列出 2~3 种可能方向、各配一句做法让他挑；毫无线索才追问 | **新增** |
| 7. 输出纪律 | 纯文本；不要开场白与自我说明、不复述用户的话；多方案给推荐与理由 | 保留 |

第 2 条的"不编造"一字未动 —— 放松的是**顺序与详略**，不是底线。

### 2.2 每个模式新增第 6 个要素「详略」

六个原有模式各加一行 `【详略】`，把"该说多少"的判断权交给模型。
逐模式调整（任务书给了方向，具体措辞由本轮定）：

| 模式 | 原问题 | 具体改法 |
| :--- | :--- | :--- |
| `general` | 过度分点 | 输出格式改为"**需要并列信息时**才写 1. 2. 3."；详略："能一句话答完就一句话，不要为了显得完整硬凑三条" |
| `summary` | 短文本也分点 | **把阈值写进输出格式**："短材料（200 字内）说完就停，不要分点；确实需要分点时每条不超过 40 字"；详略补充"长材料才列要点、最多 8 条" |
| `translate` | 过度解释译文选择 | 详略："忠实原文优先：除非我明确问，不要解释你为什么这样译，也不要替我补充背景"；语气改为"随原文分层：合同严谨、技术中性、口语自然"（不再是所有场景都"严谨保守"） |
| `code` | 每个回答都三段 | 详略："问 API 用法、参数含义、报错原因时一两句答完就够；只有确实要改动代码，才给最小修改片段和一条验证方法" |
| `contract` | 过度追问 | 详略："还没给材料时，先列这类合同最常见的风险（付款／交付／违约／争议／缺失条款）各一句，**但不要写成「原文摘录」形式**（没有原文就没有摘录）；给了材料才逐条摘录"；语气从"宁可写需人工确认"改为"严谨保守，不夸大" |
| `creative` | 反而太发散 | 详略："需要多个方案时给 2~3 个就收住，不要一路发散；每个用一句话标出特色"（唯一收紧的模式） |

任务书要求"防止改过头"的四条硬要求逐条对照：

- **不得编造**：主干第 2 条 + 各模式边界里的"不要臆测 / 不编造 API / 不换算不推断"全部保留；
- **不得省略关键免责**：`contract` 边界新增（并强化为必须）"涉及重大金额或不可逆决策时**必须**写明「建议人工复核」"（原来只是"宁可写需人工确认"）；
- **不得牺牲关键格式**：`contract`"摘录必须与原文逐字一致"、`translate`"不改动数字"、`summary`"数字日期金额原样保留"逐字保留，并有断言守住；
- **追问仍可用**：主干第 6 条仍保留"毫无线索才追问"，`contract` 在用户什么都没给时仍会问"是哪一种"。

### 2.3 新增引导模式 `guide`

`/mode guide`（别名 `/mode 7`、`/mode gd`，温度预设 0.6）：
"用户说不清自己想要什么时，帮他找到方向"——列出 2~3 种最可能的理解、每种配一句
"你会怎么处理"、最后问选哪一个而非替他决定；方向必须来自用户确实提到的线索，
一点线索都没有时直接问最关键的三个问题。

为什么做成**独立模式**而不是只写在共享主干里：共享主干那条（第 6 条）是"谁都可能碰到
含糊提问"的兜底行为，而引导模式是"用户明确知道自己在含糊、专门来要方向"的场景 ——
两者措辞强度不同（模式下要求列完方向就停手，等用户选定再给正式回答）。
温度取 0.6：要比 `code`/`contract`（0.2/0.3）敢猜，又比 `creative`（0.9）收得住。

### 2.4 模糊提问兜底话术：追问三点 → 引导方向

`prompts.clarification_prompt()`（会话层短路，**不调用模型**）重写：

- 旧：`你的问题信息还不够，我需要确认几点…1. 具体对象？2. 输出形式？3. 约束条件？`（3 条都是**问句**，承诺型条目 0 条）
- 新：`我先按最可能的意思列出几种情况，你回一个编号就行：1. 你手上有份东西…我针对它作答 / 2. 你要的是一套做法…我直接给步骤 / 3. 有个现象或报错…我按可能原因逐条排`（3 条都**替用户把意思说出来并承诺做法**）

方向**按提问内容挑**（`prompts.guide_direction_ids`，关键词命中优先、不足用默认补足、
恒为 3 个不重复）：提到报错 → "排查现象"排第一；提到文件/合同 → "处理材料"排第一。
方向**文案走语言包**（`task.guide_dir.<id>`），英文界面下不会漏出中文。

`main.py` 的短路行为同步改了一处：**引导模式下不走这条短路**，交给模型现列方向
（那个模式的系统提示词本身就是这件事，可以更贴合用户那句话）；其余模式仍用确定性话术。

### 2.5 任务模板层：条件式格式 + `relax` 标志

- `summary`：短材料一段话 / 长材料才分点；
- `contract`：还没给正文时先列 3~5 条常见风险并问属于哪种（**不要只回"请提供合同全文"**）；
- `code`：问用法、参数、报错一两句答完，需要改动才给代码与验证；
- `reason`：新增 `【假设】` 一栏，"信息不足时先按最可能的情况给出结论并标注假设"（删掉"先追问"）；
- `translate`：补"除非我明确问，不要解释你为什么这样译"；
- 结尾行分两档：`_RELAXED_ENDING`（"格式要求优先；但详略仍按问题复杂度判断——简单问题可以只答一句话"）
  与 `_STRICT_ENDING`（"严格遵守上述输出格式"）。
- **机器可读格式不放松**：`extract` 的模板标了 `relax: False`，仍走 `_STRICT_ENDING`
  —— 那段 JSON 是给程序解析的，允许"按复杂度自行判断"就等于允许它输出散文。
  `public_list()` 也把 `relax` 暴露出来，界面/诊断能看出哪些模板是硬格式。

## 三、对比测试

### 3.1 方法（以及为什么这样设计）

工具：`tools/prompt_compare.py`（真模型对比） + `tools/test_prompt_compare.py`（无模型部分，进 CI 与门禁）。

- **旧提示词从 git 取**（`--old-ref`，默认本轮重构前的提交 `4ba3eeb`），不手工复述 ——
  手工"按新写法写旧版"是自欺。旧话术同样从该提交的**语言包**里取。
- **同一进程、同一模型、同一生成参数**，只换系统提示词与模式表；温度各按各模式的预设
  （避免拿新温度跑旧提示词）。
- **只按回答正文算指标**：Qwen3 系列默认带 `<think>`，思考文本会复述系统提示词
  （首轮就因此把"是否在索要材料"这个指标点亮了，而回答正文其实没有索要）。
  用项目自己的 `reasoning.split_text` 拆掉思考再算。
- **客观判据**自动判定：分点行数、是否只反问、是否给出可选方向、是否摘录原文（引号内容
  与原文的重合率）、是否编造卷期页码金额、是否说不知道。**"回答得好不好"不装作客观** ——
  两版输出原文全部留在 `artifacts/prompt-compare-*.json` 里，主观部分单列在第 3.4 节。

场景覆盖任务书要求的五类：简单问题、信息不全、模糊提问（确定性话术 + 引导模式两档）、
复杂问题、重要决策的合同审查；另加一组**防退化**（诱导编造）三问：不存在的法条、
不存在的公司数字、不存在的论文。

### 3.2 首轮实测抓出的三个提示词缺陷（已修）

这是本轮最有价值的部分：**对比测试第一次跑就抓出三个真问题**，都改在了提示词里。

1. **摘要模式"短材料不分点"没生效**（0.6B/1.7B 都失败）。
   原因：阈值只写在 `【详略】`，而 `【输出格式】` 仍写着"先一句话结论，再列关键信息" ——
   模型跟的是输出格式。改法：把阈值写进 `【输出格式】`（"短材料（200 字内）说完就停，
   不要分点"），`【详略】` 只留长材料规则。改后 0.6B 从 4 条要点变成**一段话**，1.7B 从 7 条变成一段话。
2. **没给材料时反而编造"原文摘录"**（0.6B 的"信息不全"场景：风险词命中 6 个，看着通过，
   但三条「原文摘录」全是编的，引号内容与原文重合 0）。
   原因：`contract` 的"先列常见风险"没说**不要用摘录格式**，模型沿用了同一条的
   "原文摘录 → 风险点 → 建议"。改法：详略里显式写"不要写成「原文摘录」形式（没有原文就没有摘录）"。
   同时把这条加进判据：**有风险清单但假摘录 → 判未通过**。
3. **引导模式照抄提示词里的例句**（1.7B 输出 "如果你要的是这个，我会怎么做？" ——
   那是 `【输出格式】` 里给的字面模板）。
   改法：去掉可被照抄的引号模板，改成"每种配一句你会怎么处理"。

另外两处**判据本身**的缺陷（不是提示词问题）：

- "是否说不知道"的词表太窄：1.7B 对不存在的法条回答"目前**尚未正式颁布实施**"，
  这是**正确**回答，却因为词表里没有这个词被判失败。补齐词表，并把防退化判据拆成
  **底线**（没有编造卷期/页码/金额）与**期望**（是否明说不知道）两栏分开报。
- "可选方向数"按行首编号数：0.6B/1.7B 都把三个方向挤进一行（`1) …；2) …；3) …`），
  按行首只数到 1。改成行内编号也算。

### 3.3 客观判据结果（修复后重跑，两个模型档位）

模型：`Qwen3-0.6B-Q6_K`（**随包默认档**，495 MB）与 `Qwen3-1.7B-Q4_K_M`（可选大档，1.06 GB）。
`old` = 重构前提示词，`new` = 重构后。原始输出与全部指标：
`artifacts/prompt-compare-06b.json`、`artifacts/prompt-compare-17b.json`
（首轮修复前的两份留档为 `*-pre-fix.json`）。

| 场景 | 客观判据 | 0.6B old → new | 1.7B old → new |
| :--- | :--- | :--- | :--- |
| simple（这份文件讲什么） | 分点行数 == 0 | ❌ 4 条 → ✅ **0 条（一段话）** | ❌ 7 条 → ✅ **0 条（一段话）** |
| incomplete（这个条款有问题吗） | 风险词 ≥ 2 且无假摘录 | ❌ 只回「未见相关约定」 → ❌ 给了 5 类风险但**编了 2 条摘录** | ❌ 只回「未见相关约定」 → ✅ **5 类风险各一句 + 问属于哪一类** |
| vague_script（帮我看看这个·兜底话术） | 含「回编号」且承诺型条目 ≥ 2 | ❌ 要三点材料 → ✅ **3 个方向 + 回编号** | ❌ → ✅ |
| vague_model（同上·引导模式，模型现列） | 编号方向 ≥ 2 且不是在索要材料 | ❌ 要材料 → ✅ **3 个方向 + 你指哪一种** | ❌ → ✅ |
| complex（需要分点的分享提纲） | 分点行数 ≥ 2 | ✅ 6 条 → ✅ 2 条 + 3 子项 | ✅ 4 条 → ✅ 6 条 |
| contract_decision（重要决策的合同审查） | 保留「建议人工复核」 | ❌ 无免责 → ✅ **有免责** | ❌ 无免责 → ✅ **有免责** |
| fake_law（不存在的法条） | 不编造 + 明说不知道 | ❌ 编条文且不说不知道 → ❌ 同样（改为"该条文规定了…"） | ✅ 否认该法存在 → ✅ |
| fake_company（不存在的公司数字） | 同上 | ✅ 「不知道」 → ✅ 「不知道。」 | ✅ → ✅ |
| fake_paper（不存在的论文） | 同上 | ❌ **编了期刊名与卷期页码** → ✅ 承认不知道 | ✅ 说暂无记录 → ✅ 未发现该论文 |

**通过数**：0.6B **2/9 → 7/9**；1.7B **4/9 → 9/9**。

三点必须如实说明：

- **0.6B 的两处未通过不是提示词缺失**：`incomplete` 与 `fake_law` 都要模型"克制住编造冲动"，
  而 0.6B 这两个场景在新旧提示词下都做不到（旧版更差）。1.7B 全部通过 —— 说明提示词方向对，
  但**0.6B 档位在"没有原文却要引用"和"引用法条"这两件事上不可信**，已写进未完成项。
- `contract_decision` 的判据只覆盖"有没有免责"这一条**任务书明列的硬要求**；
  1.7B 新版这一轮没有引用原文（三条都写成"未见相关约定"），旧的反而引得更全。
  也就是说这里是"**免责换详细度**"的取舍，主观评价见 3.4。
- 指标里的 `fabricates`（是否出现卷期/页码/金额类细节）**只对防退化场景有效**：
  在合同场景里它会被原文里真有的"128.6 万元"点亮，那里只当参考值看。

### 3.4 主观评估（**这一节是主观判断，不是客观判据**）

**读输出后我认为确实变好的**：

- 摘要：短材料从"结论 + 4~7 条要点"变成"结论 + 一段话"，金额、日期、期限一个没丢
  （0.6B：`500 元 / 2026 年 4 月 1 日 / 每月 25 日` 全在；1.7B 同）。这是三处改善里最干净的一处。
- 信息不全：1.7B 从 6 个字的"未见相关约定"变成"先给 5 类常见风险各一句 + 请指明属于哪一类"，
  从**拒绝服务**变成**可用的起点**。现象二修得最到位。
- 模糊提问：两档都从"请你提供内容"变成"1)…2)…3)…你指哪一种？"，用户只需回一个数字。
  这正是任务书对现象三的要求。

**读输出后我认为仍然不够好（如实记录）**：

- 1.7B 在"有材料的合同审查"里**变得更保守**了：三条都写"未见相关约定"，一条原文都没引用；
  旧提示词虽然不给免责，摘录却更完整、更贴原文。按任务书"涉及重要决策必须保留复核建议"
  取了新版，但"免责换详细度"这个取舍我不认为新版全面更优 —— 后续可考虑
  "未引用原文时不算完成"这类更强的格式锚点，或把免责做成界面层固定追加（见未完成项 1）。
- 0.6B 的输出里有**提示词痕迹**：摘要里带出"材料：""短材料："之类标签；
  复杂问题里多余地补一句"如果是 A，建议 X；如果是 B，建议 Y"。前者无害，
  后者说明"摊开推测"对小模型仍太容易被当成必答格式。
- 引导模式的三个方向**有时过于通用**（"看文件内容有没有问题"）——它只能从
  "帮我看看这个"里猜，用户真正想要什么仍需一轮交互才能确定。这是信息量的边界，
  不是措辞能补的；能补的是"猜得更贴题"（关键词表目前只有 5 类）。

### 顺带修掉的两个既有缺陷（不是本轮任务书要求的）

1. **模糊提问检测在流式路径上从未生效**。`_handle_chat`（非流式 action 与斜杠指令）里有
   这条短路，而前端正常对话走的是 `stream()` 的 `chat_stream` —— 那条路径上没有这段代码。
   也就是说"提问太模糊就先追问/给方向"这个功能**在图形界面里从来没触发过**，
   只有后端测试与斜杠指令路径能看到它。本轮把它抽成 `Backend._vague_guide()`，

2. **引导话术不进历史**。旧短路直接 return，不写 `conv.history`；于是用户回答"1"之后，

## 五、未完成项与已知限制

1. **`contract` 的"建议人工复核"在两个档位上都是概率性的**。提示词里是必须要求
   （有断言守住），本轮还把它从【边界】提到【输出格式】（更靠近模型实际遵循的位置），
   0.6B 因此从"不给免责"变成"给"；但这是遵循率问题而不是提示词缺项，
   不能保证 100%。后续若要硬保证，正确做法是在**界面层**为合同模式固定追加一行免责，
   而不是继续加码提示词（那正是本轮要修的毛病）。
2. **0.6B 档位在"没给材料"的合同提问上仍会编造摘录格式**。最终一轮它写了
   `「交付货物需在 60 天内完成」→ 未见相关约定 → …`：内容是自己编的，却套了"原文摘录"的壳。
   判据已能识别（引号内容与原文重合 0 → 判未通过），提示词也加了"没有原文就没有摘录"，
   但 0.6B 遵循不稳。1.7B 在这一场景通过。**这是本轮最需要在后续轮次继续盯的一条**。
3. **0.6B 在防退化上不合格**：对不存在的法条，它两版提示词下都会编出条文内容
   （旧版"明确规定了数据主体应当履行的义务"、新版"该条文规定了数据资产保护的基本原则…（原文：第三十七条）"）。
   1.7B 两版都能明确否认。0.6B 是随包默认档，因此这条要如实写进已知限制：
   **涉及法条、文献、金额来源的问题，0.6B 档位不可信**，界面上的"联网搜索"或换档位是当前的正解。
4. **对比测试是单次采样**：温度非 0，小模型输出有随机性（同一份提示词两次运行，
   0.6B 在"信息不全"场景一次给风险清单、一次只回「未见相关约定」）。结论按
   "两档模型 × 新旧对照"给出，**不做统计显著性声明**；原始输出都在
   `artifacts/prompt-compare-*.json` 里，可复查。
5. **引导方向的关键词表只有 5 类**（object/howto/diagnose/judge/write），冷门提问会落到
   默认三条；没有做"社区语言包自带方向表"的扩展机制 —— 新增方向要同时改
   `prompts._GUIDE_DIRECTIONS` 与两份语言包。
6. **"摊开推测"仍会被过度使用**：0.6B 在复杂问题上会多余地补一句"如果是 A，建议 X"，
   1.7B 首轮也出现过。措辞已收紧为"只有当结论确实取决于用户没给的信息时才用"，仍偶发。
7. 未做（与本轮无关的既有未完成项，沿用前几轮记录）：对话区虚拟化、工具调用流水线、
   会话 JSONL 持久化与崩溃恢复、MCP、多模型适配器、子代理、任务看板。
8. 未做：用真实用户提问语料做回归（手上没有这样的语料，本轮场景是**人工构造**的，
   构造口径与理由写在 `tools/prompt_compare.py` 的场景表注释里）。

### 7.3 GitHub 关联：远端已配好，**推送需要维护者凭据**

任务书要求"关联 GitHub 仓库"。本轮的落点：

- **远端已关联**：`git remote add origin https://github.com/VoidEntropiaStudio/EchoDesk.git`
  （仓库地址取自仓库内既有的 README / SECURITY / installer.iss / SBOM 等处，全仓库一致）。
- **推送未完成，且无法在本机自动完成**：本机没有任何 GitHub 凭据 ——
  凭据管理器里没有 github.com 条目、没有 `~/.git-credentials`、`~/.ssh` 里只有
  `known_hosts`（`ssh -T git@github.com` 返回 `Permission denied (publickey)`）。
  匿名 `git ls-remote` 会要求用户名，说明该仓库是**私有或尚未公开**（公开仓库匿名即可列出引用）。
  联网本身没问题（匿名 `git ls-remote https://github.com/git/git.git` 正常返回 HEAD），
  所以这是凭据问题而不是网络问题。
- **为让维护者一条命令收尾**，新增 `tools\push_release.ps1`：推送前自动核对
  工作区是否干净、标签是否附注标签且指向构建提交、不变式是否成立、安装程序哈希是否
  与 `SHA256SUMS.txt` 一致，然后推送分支与标签；预检不过就拒绝推送。
  `-DryRun` 只检查不推。它不读取、不保存、不打印任何令牌。
- 脚本里有一条来自实测的经验：必须同时设 `GCM_INTERACTIVE=never`。只设
  `GIT_TERMINAL_PROMPT=0` 时，Git Credential Manager 仍会阻塞等待交互，
  脚本静默挂住 5 分钟以上（本轮第一次尝试就是这样，只能超时掐掉）。
- 本机实测：预检全部通过，推送在凭据一步失败，报错
  `fatal: could not read Username for 'https://github.com': terminal prompts disabled`。
  维护者执行 `powershell -ExecutionPolicy Bypass -File tools\push_release.ps1`
  即可完成（凭据方式三选一，脚本失败时会打印具体做法）。
- 推送之后的建议动作（脚本也会提示）：确认默认分支是 `master`；
  用 `.github\workflows\release.yml` 建草稿 Release，附件取
  `publish\EchoDesk-v0.2.1-Setup.exe` + `SBOM.json` + `THIRD_PARTY_LICENSES(.zh-Hans).md` +
  `SHA256SUMS.txt`。
