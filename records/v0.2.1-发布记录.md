### 2.1 实测得到的两条硬约束（写进脚本头部，避免以后重踩）

**（1）`7zS.sfx` 是精简版，支持的配置项只有 7 个。**
用二进制内嵌字符串（UTF-16LE）逐个核对，该模块只识别
`Title` / `BeginPrompt` / `Progress` / `RunProgram` / `Directory` / `ExecuteFile` /
`ExecuteParameters`；**没有** `OverwriteMode`、`ExtractTitle`、`ExtractDialogText`、
`ExtractCancelText`（那些是 7zSD 等第三方改版才有的键，写了会被忽略）。
这条结论直接决定了任务书里"同名文件询问用户"只能换一种实现方式（见 §4）。

**（2）rcedit 只能用于自解压包本身，绝不能碰 `app\backend\EchoDeskBackend.exe`。**
PyInstaller 把 PKG 归档**追加在 PE 映像之后**，rcedit 重写资源时会重建 PE 映像并丢掉
这段追加数据 → 后端启动即报 `Could not load PyInstaller's embedded PKG archive`。
后端的版本资源与图标由 `backend\EchoBackend.spec` 的 `version` / `icon` 参数在追加归档
**之前**写入（字段与自解压包一致）。这条此前已记录在 `tools\set_metadata.bat` 注释里，
本次在 `make_sfx.ps1` 里再强调一次，防止有人"顺手统一处理"。

## 4. 任务一 / 二 / 三：自解压包、安装脚本、版本资源

### 4.1 payload 与拼接（任务一）

- 在**发布目录内**执行 `7z a -t7z -m0=lzma2 -mx=9 -ms=on payload.7z *`：
  归档条目就是 `app\...` / `docs\...` 这样的相对路径，解压到"当前文件夹"后正好还原
  发布物的原始层次（这是"解压到当前文件夹"能成立的前提）。
- 不含模型版额外加 `-xr!app\backend\models` 与 `-xr!app\backend\models\*`：
  目录本身与内容都要排除，否则会留下一个空 `models\`（让人以为模型放这儿却找不到）。
- `config.txt` 用 **UTF-8 无 BOM** 写出（`.NET UTF8Encoding($false)` 显式控制字节）。
  Windows PowerShell 5.1 的 `Set-Content -Encoding UTF8` **会写 BOM**，SFX 读到 BOM 会把
  第一个配置键名弄坏（表现为提示语丢失），所以不能用它。
- 拼接走 **cmd 的 `copy /b`**（PowerShell 的 `Copy-Item` 不能二进制追加）。
  路径先取 8.3 短名（`Scripting.FileSystemObject`）以规避空格与中文；
  拼接后**校验结果字节数 = sfx + config + payload**，不匹配即报错 ——
  只判断"文件存在"会把半截包当成成功。

### 4.2 `install-complete.bat`（任务二）

解压完成后由 SFX 的 `RunProgram` 执行，做四件事：检查 `app\EchoDesk.exe` 是否存在、
创建 `Start-EchoDesk-v0.2.1.lnk`（`WScript.Shell` COM，不依赖外部工具）、
输出中英双语完成提示、`pause` 结束。

编码决策：文件含中文提示，所以 `chcp 65001` + **UTF-8 无 BOM**
（带 BOM 时 cmd 会把 BOM 当命令、首行直接报错；这一点由构建脚本写出后**读回字节校验**）。
`config.txt` 的提示文本用英文（任务书建议），避免编码问题的暴露面。

任务书要求"图标用 `app\EchoDesk.ico`，不存在时回退到 `app\EchoDesk.exe` 自带图标"：
实现为 `IconLocation` 留空即用 exe 内嵌图标。脚本可安全重复运行 ——
已存在同名快捷方式时**先询问是否覆盖**（这是本脚本承担的那部分"同名询问"）。

## 5. 全局要求一：全英文命名（含程序内硬编码名）

任务书列了"需要改名的典型项"，并补充**例外条款**："用户运行程序后由程序自身生成的目录，
若程序内已硬编码中文名，需同步改为英文。" 本版据此改了 6 处：

| 原名 | 现名 | 类型 |
| --- | --- | --- |
| `使用说明.txt` | `USAGE.txt` | 发布物文件 |
| `批量处理结果\` | `results\` | **程序生成目录**（`results_root_name` 默认值） |
| `结果.txt` | `result.txt` | **程序生成文件**（`automation.report_path`） |
| `自动化任务` | `auto-task` | **程序生成目录**（`task_name` 默认值） |
| `失败截图_任务N_时间.png` | `failure-screenshot-taskN-时间.png` | **程序生成文件**（失败截图） |
| `EchoDesk-v0.2.1.lnk` | `Start-EchoDesk-v0.2.1.lnk` | 快捷方式（任务二规定的名字） |

影响面（共 38 个文件、176 处）：后端 `config.py`/`automation.py`/`config.json` 与语言包、
前端 `ShortcutService.cs`/`SettingsWindow.xaml(.cs)`/语言包、`deploy\config.json`、
全部双语文档与 README、`tools\` 下的测试与构建脚本、`.gitignore`。

**两个因此产生的连带修正**（都是机器替换之后人工复核发现的）：

1. **语言包里的"留空时预览默认值"**（`settings.automation.defaultResultsRoot` /
   `defaultTaskName`）原本写的是显示用的中文/英文短语，改名的同时必须与后端真实默认值
   对齐，否则设置窗口预览出来的目录名和实际生成的不一样。
2. **两处中文 UI 文案被机械替换弄坏**（`「批量处理结果保存」` → `「results保存」`、
   `「选择批量处理结果的位置」` → `「选择results的位置」`），已改回通顺中文。

### 5.1 升级影响（**重要**）

结果目录名是**用户数据**，改名后**不会自动迁移**：

- 老用户升级后，新结果写到 `results\`，历史结果仍在 `批量处理结果\`（两处并存，数据不丢）。
- Release Notes 的升级指引第 3 步明确要求"把旧目录改名为 `results\`"，并说明不改也不会丢数据。
- 之所以不做自动迁移：目录改名要处理用户自定义过 `results_root_name` 的情况、
  跨盘符的"保存位置"设置、以及正在被占用的文件，风险高于收益；对一次
  v0.2.1 的开源首发来说，"说清楚 + 手动一步"是更稳的选择。

## 10. 任务五：合规与收尾

### 10.1 「只装 `backend/requirements.txt` 的干净 venv」复核 —— 发现 4 个真问题

这是本轮最有价值的一步。干净 venv 建在 `artifacts\clean-venv`（52 → 55 个发行包），
用它跑 `gen_licenses.py` 与 `gen_sbom.py --check`，逼出了四个此前被"开发机恰好都装了"
掩盖的问题：

**（1）`backend/requirements.txt` 漏声明 3 个**直接 `import`** 的包。**
`marketplace.py` 用 `requests` 与 `urllib3`，`download_utils.py` 用 `tqdm`，
但三者都不在依赖声明里 —— 开发机与打包机上它们作为**传递依赖**恰好存在，
所以问题一直没暴露；按本文件从零建环境时市场功能会直接 ImportError。
修法：显式声明三者，并新增 `tools/check_requirements.py`（AST 取后端自身代码的
第三方顶层导入 + 用指定解释器实测 `import`）作为门禁。现在 14 个第三方顶层导入
全部有声明，且干净 venv 里逐个 `import` 成功。

**（2）发布物含未声明的第三方组件 `cryptography`。**
PyInstaller 是按**打包机环境**分析的，依赖里 `try: import X` 形式的可选依赖只要
打包机装了就会被打进包。开发机装了 `cryptography`（来自 `msoffcrypto-tool`，
一个与本项目无关的旧包），于是它进了发布物，**却不在许可证清单与 SBOM 里** ——
对外分发时这就是"未声明的第三方组件"。
判断：它**确实被功能需要**（`file_parser.py` 对"只设了权限密码"的 PDF 调
`reader.decrypt("")`，pypdf 的 AES 支持依赖 cryptography；缺失时退回只支持 RC4 的实现，
AES 加密的这类 PDF 就解不开，属用户可见差异）。
因此选择**显式声明**而不是排除 —— 声明后干净环境与发布物口径一致。

**（3）`chardet`、`bidi`（均为 LGPL）与 `tzdata` 是被可选 import 带进包的。**
`chardet` 是 requests 的可选编码探测伙伴（requests 优先用已声明的
`charset_normalizer`）；`bidi`/`arabic_reshaper` 是 pypdf 的可选 RTL 支持
（`_appearance_stream.py` 里有 `try: import arabic_reshaper` 守卫，本项目只调
`extract_text()`，用不到）；`tzdata` 来自开发机残留包 `tzlocal`。
三者**都不在依赖声明里**，也就是发布物含未声明的 LGPL 组件。
修法：加进 `backend/EchoBackend.spec` 的 `EXCLUDES`。已验证干净 venv（无这三者）里
`from pypdf import PdfReader` 正常，属纯可选。副作用：`_internal` 文件数
1567 → 930（`tzdata` 自带数百个时区小文件），体积约 −2.6 MB，
**发布物不再包含这两个 LGPL 组件**。
新增 `tools/check_bundled_packages.py` 比对「干净 venv 声明的包」与
「`_internal` 里实际存在的顶层模块」，防止这类偏差再次悄悄出现。

**（4）`tools/gen_licenses.py` 的名称归一化缺陷。**
`「一、后端直接依赖」` 表用 `name.lower()` 直接比较发行名，而
`llama-cpp-python` / `duckduckgo-search` 的元数据名是下划线形式
（`llama_cpp_python` / `duckduckgo_search`），**两个直接依赖因此被漏出该表**。
合规清单少列直接依赖，比多列危险。修法：改为**由 `backend/requirements.txt` 驱动**
（不再依赖手抄列表）+ PEP 503 归一化（`-`/`_`/`.` 等价）+ 对"声明了但环境里没装"的
依赖显式打印告警。修后该表 13 → 17 行，与 `requirements.txt` 声明的 17 项完全一致
（生成器会打印"声明 N 个 / 列出 N 个"，两者不等就说明又漂了）。

**附带修的第五处**：`tools/gen_sbom.py` 的传递闭包**不评估环境标记**，
把 `macholib`、`tomli`、`exceptiongroup`、`importlib-metadata` 等**跨平台标记依赖**
算进发布闭包，于是 `--check` 在干净环境里报"闭包里有、清单里没有"5 项、
**永远无法通过** —— 门禁失效比没有门禁更糟（会被绕过）。
修法：按当前解释器评估 `Requires-Dist` 的 `Requires-Dist` 标记（`packaging` 为**可选**
导入，缺失时退化为保守超集并在输出里标注，不静默改变语义）。

修完后的收口状态：**干净 venv 55 个发行包，`gen_sbom.py --check` 的 A/B/C/D/E 五类
差异全部为 0，退出码 0**；`check_requirements.py` 14/14 可导入；
`check_bundled_packages.py` 顶层模块全部能对应到已声明发行包。

## 11. 任务四：集成到 `tools/build_release.ps1`

任务书要求构建脚本新增开关（如 `-MakeSfx`）把八步收口。实现结构：

```
build_release.ps1 -IncludeModels -MakeSfx
  ├─ 第 1–5 步（构建/收集）：英文名生成 + 双语合规文档成对复制 + 运行期残留清理
  ├─ 第 6c 步：docs\ 整份复制，**按名字排除过程文档**
  ├─ 第 9b 步：结构断言（外层无 exe/dll、全英文命名、无过程文档、无运行期残留、34 项必备文件）
  └─ 第 11 步（-MakeSfx）
       ├─ tools\check_feedback.ps1        ← 任务书第 3 步（反馈渠道）
       └─ tools\make_sfx.ps1              ← 任务书第 5–8 步
            ├─ 可行性检查（十项）
            ├─ payload.7z ×2（极限压缩 / LZMA2 / 固实）
            ├─ config.txt（UTF-8 无 BOM）+ copy /b 拼接
            ├─ rcedit 九字段 + 图标
            └─ SHA256SUMS.txt
```

**关键决策：把 5–8 步放进独立的 `tools/make_sfx.ps1`，而不是全写进构建脚本。**
理由：`make_sfx.ps1` 可以**独立运行**（只改了元数据、只想重打安装包时不必重跑
PyInstaller 与 dotnet publish），并且**自己再做一遍可行性检查** ——
把门槛放在真正使用这些前提的地方才拦得住。

**本轮实测发现并修掉的构建脚本缺陷（三个，前两个是"报告成功但产物是错的"）：**

1. **`rcedit` 写在拼接之后 → 自解压包被削成空壳。**
   `rcedit` 重写资源时会**重建 PE 映像并丢掉映像之后追加的数据**（与
   `app\backend\EchoDeskBackend.exe` 上踩过的是同一个机制）。
   任务书写的是"对两个自解压包分别写入版本资源"，照此实现的结果是：
   拼接出的 603.8 MB 安装包被 rcedit 削成 **176 KB**，而 rcedit 退出码 0、
   脚本一路报告成功 —— 只有"体积合理性检查"报了句"0.2 MB 超出区间"。
   **修法：先给 `7zS.sfx` 桩写资源，再拼接**（两个包的 `FileDescription` 与
   `OriginalFilename` 不同，因此各盖一份桩）；并新增 `Assert-SfxIntact`：
   拼接后断言 `文件大小 == 桩 + config.txt + payload`，且在尾部 64 KB 内能搜到
   7z 归档魔数 `37 7A BC AF 27 1C`。任何将来把顺序改回去的改动都会被拦住。

2. **`install-complete.bat` 里的 PowerShell 片段被 here-string 吃掉变量。**
   生成批处理用的是双引号 here-string，而批处理里有一行 PowerShell 单行命令
   带 `$s` / `$l` 两个变量 —— PowerShell 把它们当成本脚本的变量展开成了空串，
   生成的批处理变成
   ` = New-Object -ComObject WScript.Shell;  = .CreateShortcut(...)`，语法直接坏掉，
   **解压后创建快捷方式必然失败**，而构建过程没有任何报错。
   修法：改用**单引号 here-string**（零展开）+ `__VERSION__` 占位符显式替换，
   并在写出前断言"生成的批处理里必须含 `$s = New-Object` / `$l.Save()`"等片段 ——
   把这类"静默丢字符"变成构建期失败。

3. **失败仍返回退出码 0。** PowerShell 脚本内部抛错时**不设置退出码**，
   于是 `& tools\build_release.ps1 -IncludeModels -MakeSfx` 在"反馈渠道检查通过、
   随后打包阶段抛错"的情况下，外层看到的 `$LASTEXITCODE` 是 0。
   修法：脚本顶部加 `trap`（打印原因并 `exit 1`），并在 `-MakeSfx` 末尾加
   **交付物存在性断言**（缺任何一件即失败）。

4. **发布物里预置的 `.lnk` 会把构建机的个人绝对路径带出去。**
   `build_release.ps1` 一直在发布目录里生成 `Start-EchoDesk-v0.2.1.lnk`，
   而 Windows 快捷方式存的是**绝对路径** —— 打进包里的实际内容是
   `C:\Users\backt\Desktop\编程\GitHub\EchoDesk\publish\EchoDesk-v0.2.1\app\EchoDesk.exe`：
   * 违反任务书「全局要求五」的**个人绝对路径（绝对禁止）**，还顺带泄露了中文目录结构；
   * 在用户机器上必然是死链（v0.2.0 起就存在，前端靠"检测到失效后提示重建"兜着）；
   * **`check_feedback.ps1` 没拦到它** —— 它扫的是文本文件，而 `.lnk` 是二进制、
     又位于 `.gitignore` 覆盖的 `publish\` 下。这是本次自检清单里唯一靠"功能测试"
     才发现的问题（见下）。
   发现方式很有意思：交付物验收里那项"install-complete.bat 真跑一次建快捷方式"
   失败了，报的是"目标不对：…\publish\EchoDesk-v0.2.1\app\EchoDesk.exe" ——
   因为包内**已经有**一个 `.lnk`，安装脚本按设计询问"是否覆盖"，而自动化测试没有输入，
   于是保留了那个指向构建机的死链。**静态检查全绿、只有真跑才暴露。**
   修法：
   * `build_release.ps1` 不再生成 `.lnk`（新增断言：发布目录内出现 `*.lnk` 即失败）；
   * 快捷方式改由 `install-complete.bat` 在目标机器上创建（这正是任务书「任务二」的职责，
     自解压包解压后会自动执行）；zip 免安装解压版的用户手动运行一次，
     或直接启动 `app\EchoDesk.exe` 由程序自己创建；
   * `make_sfx.ps1` / `verify_release.ps1` / `release.yml` 都加了"不得含预置 `.lnk`"的断言；
   * USAGE.txt、README（中英）、FAQ、USER_GUIDE、COMPLIANCE、Release Notes 与升级指引
     同步说明这一步。

**因此新增了一条门禁**：`tools/verify_release.ps1` 里加了
「自解压包：安装脚本真的能创建快捷方式」一项 —— 解压 → 真跑 `install-complete.bat`
→ 读回 `.lnk` 的 TargetPath / WorkingDirectory / IconLocation。
静态检查（"文件里有某段文字"）挡不住这类问题，只有真跑挡得住。

**一条经验**：这三个缺陷都属于"构建报告成功、产物是错的"，而且第一个的线索只有
体积异常。因此本版把"体积/字节数/关键字符串"这类**可计算的期望值**都写成了断言，
而不是靠肉眼。
