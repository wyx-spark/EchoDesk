## 一、任务一：先把输出结构量清楚（六份探针，全部是实测）

任务书要求"动手前先确认事实"。本节所有结论都有可复现的探针（`artifacts/probe_reasoning_1..6.py`
与对应日志，`artifacts/` 不进版本库）。

### 1.1 推理模型是哪一个

`backend/config.json` 写明的默认模型是 **Qwen3.5-0.8B**（`unsloth/Qwen3.5-0.8B-GGUF`）。
本地 `models/` 目录是空的，因此探针从镜像站下载了两个真实模型来测：

| 模型 | 用途 | 大小 |
| --- | --- | --- |
| `Qwen3.5-0.8B-Q4_K_M.gguf` | 应用默认模型，探针三/四 | 532,517,120 B |
| `Qwen3-0.6B-Q4_K_M.gguf` | 模板形态不同（思考默认开启）的对照组，探针二/四 | 396,705,472 B |
| `DeepSeek-R1-Distill-Qwen-1.5B-Q4_K_M.gguf` | 任务书点名的 R1 系列，探针五 | 1,117,321,312 B |

### 1.2 输出是标签包裹还是独立字段

**标签包裹**。三条通道全部实测：

| 考察点 | 实测结果 |
| --- | --- |
| `message` 字段集合（非流式） | 只有 `content` / `role`，**没有 `reasoning_content`** |
| 流式 delta 出现过的键 | 只有 `content` / `role`（首块是 `role`，其余全是 `content`） |
| `llama_types.py` 里有没有 `reasoning_content` | **没有**（直接搜包源码，0 命中） |

### 1.3 原始输出里有什么标签

* **Qwen3-0.6B**：模板的 `add_generation_prompt` 分支只在
  `enable_thinking is defined and enable_thinking is false` 时插入 `think` 空块，
  否则**什么都不加**；`enable_thinking` 未被传入（见 1.5）→ 模型自己生成
  `<think>`（U+003C U+0074 … U+003E）… `</think>`，**起始与结束标签都在生成文本里**。
  实测切分：思考 437 字符 / 回答 12 字符。
* **Qwen3.5-0.8B（默认模型）**：模板条件写反了 ——
  `{%- if enable_thinking is defined and enable_thinking is true %}{{- '<think>\n' }}{%- else %}{{- '<think>\n\n</think>\n\n' }}{%- endif %}`。
  绑定层传不进 `enable_thinking`，于是永远走 `else` 分支：**提示词里塞了一个空的思考块，
  模型直接给答案、不产生任何思考内容**（实测输出 `'**9.11 比 9.9 大**。…'`，无标签）。
* **DeepSeek-R1-Distill-Qwen-1.5B（unsloth GGUF）**：模板末尾是
  `{% if add_generation_prompt and not ns.is_tool %}{{'<｜Assistant｜><think>\n'}}{% endif %}` ——
  **起始标签写在提示词里**，生成文本只会有结束标签。同一个模板对历史里的助手消息做
  `{% if '</think>' in content %}{% set content = content.split('</think>')[-1] %}`，
  即**模型侧自己也丢弃思考内容**（这段是后面"思考不进上下文"决策的直接依据）。
  模板里的标签是纯 ASCII 的 `<think>` / `</think>`（已按码点核对）。

### 1.4 流式 delta 里有没有 `reasoning_content`

**没有**（1.2 已给出实测）。这一条直接否决了任务二的最优路径。

### 1.5 当前 llama.cpp/绑定是否支持 reasoning 分离配置

不支持，三条证据：

1. `create_chat_completion` 的参数表**固定 29 个**：`messages … top_logprobs`，
   不含 `reasoning_format`、`reasoning_content`、`chat_template_kwargs`、`enable_thinking`；
2. `llama_types.py` 没有 `reasoning_content`；
3. 流式 delta 由 `llama_chat_format._convert_text_completion_chunks_to_chat` 生成，
   该函数**只构造 `{"content": …}`**（首块 `{"role": "assistant"}`，末块 `{}`）——
   结构上不可能出现第二个字段。

版本：`llama-cpp-python 0.3.35`（`backend/.venv`），llama.cpp 动态库随包分发。

## 二、任务二：为什么放弃"推理层分离"

任务书说"若 llama.cpp 支持 reasoning 格式配置，优先在这一层分离"。实测（1.5）
**绑定的 Python 接口没有这个能力**：`llama-server` 的 `--reasoning-format` 属于服务端
（`common/chat.cpp`），libllama 不含它，`llama-cpp-python` 也没有暴露。

顺带评估了"能不能在推理层把思考标签剥掉"：模板渲染走 `Jinja2ChatFormatter`，
`create_chat_completion` 不会把额外 kwarg 透传给它，所以连"让模型别输出标签"都做不到；
唯一可行的做法是自建一个 `chat_handler`（把 `{%- set enable_thinking = true -%}` 拼在模板前），
探针四验证过这条路**能改变提示词**（渲染结果确实以 `<think>\n` 结尾，模型也开始思考），
但它有两个代价：依赖 `llm._model.token_get_text` 这类私有接口才能复刻 eos 文案
（用 `detokenize` 在这个模型上得到空串 → `stop=['']` → 一条都不生成，探针六已定位），
而且它只能控制"要不要思考"，**不能把思考与回答分成两个字段**。

**结论**：任务二记为实现不了，理由与证据如上；分流改在应用层做（任务三）。
这不影响用户可见目标（思考可选可见、默认收起、回答区只显示答案）——
任务书本就允许"若推理层不支持，在应用层处理"，且明确要求应用层处理这些边界情况。

## 三、任务三：应用层兜底

新增 `backend/reasoning.py`（纯函数 + 增量分离器，不 import llama_cpp，可脱离模型单测）。

* 通道：`REASONING` / `ANSWER` / `RESET`；`feed(text)` 吐 `(通道, 文本)` 事件，`close()` 收尾。
* **跨 chunk**：任何"可能是某个标签前缀"的尾巴都会被扣住不发（最多扣一个标签长度），
  所以逐字符喂也不会漏判，更不会把半截标签当回答显示出去。
* **嵌套**：按深度配对，内层标签不会提前关掉思考区。
* **多段**：多段思考合并到同一通道，中间补换行。
* **未闭合**：结束时仍在标签内 → 剩余内容全归思考，置 `unclosed=True`，回答区保持为空。
* **孤立结束标签**：先看到结束标签时，把**此前已发到回答通道的内容整体改判为思考**，
  并发一次 `RESET`（不重发文本，界面把自己那份搬过去即可）。
* **标签表可配置**：`config.json` 的 `reasoning.tags` 追加；内置
  `think` / `thinking` / `reasoning` / `thought` / `reflection` / `analysis`
  与 DeepSeek 特殊 token 两种形态；按长度倒序匹配，长标签优先。
* 空思考块（Qwen3.5 关闭思考时模板塞的 `<think>\n\n</think>\n\n`）**不算有思考内容**：
  `has_reasoning()` 为假 → 界面不建折叠区；回答区的首个空行也会被去掉。

### 接线（`llm_engine.py`）

| 方法 | 语义 | 谁在用 |
| --- | --- | --- |
| `chat_stream` | 只产出**最终回答**（思考已剥掉） | 分段摘要、自动化、旧调用方 |
| `chat_stream_split` | 双通道事件 + 可传入自己的 `splitter` | 对话流式路径 |
| `chat_complete` | 只返回**最终回答** | 自动化审核意见、上下文压缩、预热 |
| `chat_complete_split` | 返回 `(思考, 回答)` | 对话非流式路径 |

速度统计（`last_tokens` / `last_tps`）**把思考算进去**：思考也是模型生成的输出，
"变慢了"要如实反映，不能因为分流就少算一截。

## 四、任务四：前端展示（形式由本实现决定）

* 用 WPF 原生 **`Expander`**：标题栏自带展开/收起、键盘操作、读屏语义与 Toggle 自动化接口
  （界面探针可直接驱动），手写折叠按钮只有坏处。
* 视觉区分三件事：标题是副色小字（`SubTextBrush`）、正文整块放在浅底圆角边框里
  （`CodeBackground` + `MessageBorderBrush`）、正文斜体副色。回答区仍是主题正文色、无边框。
* **默认收起**：历史回放、非流式回复、生成结束都保持收起。
* **流式实时更新**：思考增量实时渲染（节流逻辑沿用既有 60ms `DispatcherTimer`）。
* **自动展开/自动收起**：流式出现思考时自动展开（否则用户看不到"它在想"），
  **答案第一段到达时自动收起** —— 比任务书说的"回答完成后自动收起"更早一步；
  用户手动展开过就不再强行收起（尊重用户操作，已在记录中说明）。
* **无思考不占位**：只有真的出现思考内容才创建折叠区。
* **复制交互**：思考区 `Tag="reasoning"`，答案 `Tag="content"` —— 复制按钮、复制全部对话
  （`Ctrl+Shift+C`）、Ctrl+滚轮调字号三处都按 Tag 走，因此复制只拿答案、字号两边都跟着变。
* **只有思考没有答案**时（`reasoning_unclosed`）：自动展开思考区，并在答案区写明原因，
  不留空白气泡。

## 六、自行判断项（任务书要求 DSH 决定）

1. **思考内容要不要持久化** → **要**，单独字段，可关（`reasoning.persist`）。
   理由：任务五明确要求"重新加载含思考内容的历史会话，确认区分正确"，不持久化无法满足。
   同时设 `history_max_chars`（默认 8000）截断上限并加省略标记：思考常比答案长很多，
   不设上限时单个长思考就会把 `session.json` 撑起来。
2. **是否参与上下文** → **不参与**。三条理由：① 思考通常比答案还长，回灌白占窗口；
   ② DeepSeek 官方接口明确要求不要把 `reasoning_content` 传回下一轮；
   ③ R1 的 GGUF 模板自己就只取 `</think>` 之后的内容（实测模板原文）。
3. **token 消耗与窗口占用** → 因为不参与上下文，**不额外占用窗口**；它只占
   `session.json` 的体积（截断上限已给）。这是"持久化 + 不进上下文"组合的直接好处。
4. **折叠区默认状态与展开样式** → 默认收起；展开后浅底圆角边框 + 斜体副色小字标题，
   正文字号跟随全局字号但小 1 号（辅助信息不抢答案视线）。

## 七、与任务书的偏差

| # | 任务书原文 | 实际做法 | 原因 |
| --- | --- | --- | --- |
| 1 | 任务二"优先在推理层分离，配置推理格式使思考归入 `reasoning_content`" | 未实现（记为实现不了） | 绑定层没有 `reasoning_format` / `chat_template_kwargs` / `reasoning_content`，实测证据见 1.5 |
| 2 | 任务四"回答完成后，思考区域可自动收起" | 改为**答案一开始输出就收起** | 与主流推理模型界面的既有习惯一致（思考时展开、出答案即收）；"完成后"再收会让折叠区在整个答案生成期间一直张着 |
| 3 | 任务四"思考过程可选可见" | 有可见/不可见，但没有"完全关掉思考"的开关 | 关掉思考需要推理层支持（`enable_thinking`），绑定层传不进去；`reasoning.enabled=false` 只能退回旧行为（标签原样显示在回答里），不能阻止模型思考 |
| 4 | 任务一"确认当前使用的推理模型是哪一个" | 默认模型是 Qwen3.5-0.8B，且它**默认不产生思考内容** | 事实如此（模板条件写反 + 参数传不进），已写入 CHANGELOG/FAQ，避免用户以为功能没生效 |
| 5 | 任务三"不同模型的标签可能不同（` thinking`、`<reasoning>` 等）" | 默认表里也包含 `▁thinking` 与 `｜begin▁of▁thinking｜`/`｜end▁of▁thinking｜` 特殊 token 形态 | 部分 GGUF 会把特殊 token 解码成文本；多认一种形态不会误伤正常文本 |
| 6 | —（任务书未提复制行为） | 复制按钮与"复制全部对话"**只复制答案** | 复制答案时把思考一起粘走是明显的坏体验；思考仍可在展开区拖选、或从 `/save` 导出件里取 |

## 八、未完成项与已知限制

1. **推理模型默认不思考时无法从界面开启思考**（默认模型就是这种）。
   可行路线已经跑通一半：自建 `chat_handler` + `{%- set enable_thinking = true -%}`
   能让提示词变成 `<think>\n`、模型也确实开始思考（探针四），但要复刻绑定内部
   （`_model.token_get_text` 取 eos 文案、`stop_token_ids`、模板注册名）才稳，
   本次评估后**不做**：收益是"可选开启思考"，代价是绑死私有接口，
   而这属于任务书没要求的功能扩张。
2. **思考内容不做 Markdown 之外的特殊渲染**：思考区正文走既有 `MarkdownRenderer`，
   因此如果思考里出现"看起来像表格的代码块"，会沿用它既有的启发式规则（与答案区一致）。
3. **`reasoning.enabled=false` 只退回旧行为**，不改变模型是否思考（见偏差 3）。
4. **自动化结果、摘要、上下文压缩拿到的都是剥掉思考的文本**：这是有意的（见六·2），
   但如果用户希望"审核意见里保留推理过程"，当前没有开关。

### 9.4 界面探针跑出来的产品缺陷（顺带修掉）

给探针临时写 `config.user.json` 时踩到：**配置文件带 BOM 会让后端启动即崩**
（`JSONDecodeError: Unexpected UTF-8 BOM` → 后端退出 → 程序表现为"后端意外退出"）。
记事本保存 UTF-8 同样带 BOM，所以这是真实用户会遇到的启动失败。
修法：`Config.load` 按 `utf-8-sig` 读；`config.user.json` 坏掉只告警并忽略该覆盖层；
`ConversationManager.load_session` 同样按 `utf-8-sig` 读。回归断言进了 `tools/selftest.py`。
