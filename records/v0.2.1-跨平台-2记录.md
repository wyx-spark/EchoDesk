## 〇、本机条件与一个外部阻碍（决定了本轮能做到什么程度）

| 条件 | 实测 | 影响 |
| :--- | :--- | :--- |
| 操作系统 | Windows（无 WSL / 无 Docker / 无 macOS） | 真实运行只能覆盖 Windows |
| Python | 本机 3.13.5；target 取 python-build-standalone 的 **3.13.16**（同一 minor） | 满足任务书"版本与开发环境一致" |

### 外部阻碍：本轮一开始没能产出三平台后端产物（**已在同一轮内突破，见第十二节**）

`pack_backend.py` 按设计需要从 GitHub Releases 下载三平台的 standalone Python
（45.2 / 71.8 / 24.2 MB）。实测：

1. `api.github.com` 可用（能列出 897 个资产、选定目标资产）；
2. 资源实际下载速度只有 **40–70 KB/s**，单个解释器要十几分钟；
3. 执行到中途，到 `github.com:443` 的连接**完全超时**（curl 连续 9 次重试全部失败），
   `win-x64` 阶段即以退出码 1 结束。

当时的结论是：**脚本、过滤逻辑、依赖解析、启动脚本、清单格式都已实现并验证；
三平台产物本身未产出。** 这一条保留在这里，因为它准确描述了当时的处境，
也是后面"为什么值得写 `fetch_wheel.py` / `fetch_runtime.py`"的动机来源。

**后续突破**（第十二节）：同一轮稍后链路恢复正常，三个平台的产物全部产出并通过校验；
过程中还发现并解决了两个只靠"多试几次"永远发现不了的问题
（macOS 轮子在上游就是坏的、官方有体积小一半的 `install_only_stripped` 变体）。
本节标题里的"没能产出"因此只在**时间意义**上成立。

## 一、任务零（全局约定）：Git 全链路统一 SSH

任务书把"从本轮起统一 SSH"定为前置要求。逐条落地情况：

| 要求 | 落地 | 证据 |
| :--- | :--- | :--- |
| remote 必须是 SSH | 已经是：`origin -> git@github.com:VoidEntropiaStudio/EchoDesk.git` | `git remote -v` |
| 推送脚本改 SSH 语义并**断言** remote | `tools/push_release.ps1`：默认 URL 改 SSH；远端是 HTTPS 直接判预检失败并打印改法 | 实测：临时把 remote 改成 HTTPS → 预检失败 1 项、退出码 1、给出 `git remote set-url`；随后恢复 SSH |
| 失败排查优先给 SSH 做法 | 脚本末尾改为 5 条 SSH 排查（测连通性 / 密钥 / 公钥 / 443 端口 / remote 形式），**删除**全部 PAT 与凭据管理器做法 | 脚本内容 + 新增门禁断言 |
| 清理 cmdkey 里的 HTTPS PAT | **已删除**：`cmdkey /delete:git:https://github.com`（删除前确认存在 User=VoidEntropiaStudio，删除后目标不存在） | 见下方实测 |
| CI 不依赖 HTTPS 凭据 | 核对 `.github/workflows/ci.yml`：只有 `on: push` 触发，**没有任何 git push / 打标签 / 创建 Release 的写操作**，因此无需接 `GITHUB_TOKEN` 或部署密钥 | 全文检索 `git `/`push`/`Release`/`permissions` 无命中写操作 |
| 文档示例统一 SSH | `CONTRIBUTING.md` / `CONTRIBUTING.zh-Hans.md` 新增「获取代码（只用 SSH）」；`docs/{zh-Hans,en}/DEVELOPER.md` 新增「版本控制与推送」章节（含密钥准备与 443 端口写法） | 门禁 `check_git_ssh.ps1` 与 `check_docs_links.ps1` 全通过 |

### 门禁与任务书要求撞车（必须解决，否则两者只能二选一）

`tools/check_feedback.ps1` 的"无个人邮箱"规则用一条通用邮箱正则扫全仓库。
`git@github.com:owner/repo.git` 与 `ssh -T git@github.com` 恰好能被它匹配 ——
于是"文档里写 SSH 地址"会被判为"泄漏个人邮箱"。

**这一冲突本轮修掉了**（而不是像以前那样在脚本里把 URL 运行时拼出来绕过检查）：

* `tools/check_feedback.ps1`：邮箱检查新增两条豁免 ——（a）`@` 后紧跟冒号再接非空白
  （scp 形态 `user@host:path`，邮箱不会长这样）；（b）域名正好是 `github.com`
  （代码托管主机名，GitHub 不提供 `@github.com` 邮箱，`git` 是固定用户名）。
  常用个人邮箱域名另有既有的 `BANNED_MAIL_DOMAINS` 兜底，仍拦得住。
* `tools/push_release.ps1` 里"运行时拼装 SSH URL"的变通做法**随之删掉** ——
  它是把问题藏起来，不是解决它。

### 新增门禁 `tools/check_git_ssh.ps1`

"统一 SSH"如果只靠本轮改一次，下次有人粘一段 HTTPS 示例就漂回去了。新增门禁查五件事：

1. 本仓库 remote 无 HTTPS 形式，且至少有一个 SSH remote；
2. `push_release.ps1` 的默认 `RemoteUrl` 是 SSH；
3. `push_release.ps1` 不含 PAT 引导（只查**引导性措辞**如"当密码""粘贴令牌"，
   不查"个人访问令牌"这个词本身 —— 否则连"这条路不再使用 PAT"这种否定式说明都写不了，
   第一版就是这么误报的）；
4. 仓库内（除 `records/` 等历史目录）不存在 HTTPS 形式的 git 操作示例；
5. `-TestConnection` 时真连一次 GitHub（默认关闭：门禁要能在离线环境跑通）。

**刻意不检查**的两类，理由写在脚本注释里：**网页链接**（Issues / Discussions / Releases /
Advisories / SPDX `documentNamespace` / Inno 的 `MyAppURL`）保持 `https://` 是正确的 ——
SSH 地址在浏览器里打不开，任务书要求改的是 git 操作示例；**`records/` 下的历史记录**记的是
当时的事实，改写它会让"记录可信"本身失真。

### 可证伪证据（不只是"跑通了"）

| 验证 | 做法 | 结果 |
| :--- | :--- | :--- |
| 门禁能失败 | 临时植入 `docs/_temp_gate_probe.md` 含 `git remote add origin https://…` | **失败 1 项**并指出文件与行号；删除后恢复 5 项全通过 |
| 推送脚本拦 HTTPS | 临时 `git remote set-url origin https://…` 后跑 `-DryRun` | 预检失败 1 项、退出码 1、打印改法；remote 已恢复 SSH |
| 门禁第一版自身有 bug | 首跑 6 项失败中有 5 项是**我自己脚本的问题**（记录目录正则用了反斜杠、PAT 关键词过宽、注释自指） | 逐条修正后全绿 —— 说明这组断言确实可失败 |

**SSH 连通性实测**：`ssh -T git@github.com` → `Hi VoidEntropiaStudio! You've successfully authenticated`
（注意 `ssh -T` 成功时**退出码是 1**，所以判据取输出而不是退出码）。

### 踩到的坑：PowerShell 把 ssh 的 stderr 当错误

`ssh -T` 成功时也会往 stderr 写 "does not provide shell access"，Windows PowerShell 5.1
把它包装成 `NativeCommandError`，屏幕上出现红字 `ssh.exe : Hi …` —— 明明是成功却看着像失败。
`*>` 重定向也不行（错误记录会被格式化后照样写进文件）。最终用仓库既有的做法：
`cmd /c "ssh … > 文件 2>&1"`，PowerShell 就看不到那条 stderr 了。
这与记录里"Python 的 stderr 让退出码看起来是 1"是同一类问题的同一个解法。

## 二、任务一：前端迁移（**部分完成**，逐模块交代）

### 迁移策略的调整（这是本轮最重要的方法决策）

WPF 版的设置窗口是 **1 个 1321 行 XAML + 6 个分部类共约 6400 行 C#**。
按任务书"逐模块迁移、每个模块单独验证"，本轮改成了：

> **骨架 + 每页一个 UserControl**（`Views/Settings/*`），页签由代码按统一契约注册。

* 契约文件：`frontend-avalonia/EchoDesk.Avalonia/Views/Settings/ISettingsPage.cs`
  （含 `ISettingsHost`）。
* 好处：每个模块独立编译、独立验证、独立替换；多页可以并行开发且文件互不冲突；
  一个页签的缺陷不必在 8000 行里翻找。
* 代价：与 WPF 版的代码结构不再一一对应（**行为对齐，结构不对齐**）。

页面的职责边界（写进契约注释，避免以后各写各的）：
**界面设置**（主题/字号/语言/emoji）存 `ui_state.json`，由页面直接读写；
**业务设置**（默认模式、自动化配置、模型档位…）存后端 `config.json`，
页面只通过后端动作同步，**前端不复制第二份**。

### 本轮对前端的另一处必要改动：后端定位新增"包内 standalone"候选

新后端布局（`pack_backend.py` 产出）是 `backend/python/**` + `backend/site-packages/**` +
`backend/app/**`。Avalonia 的 `BackendService.ResolveLaunch()` 新增一条候选
（`TryBundledStandalone`）：找到包内解释器与 `app/main.py` 就以
`python -u app/main.py` 启动，并注入 `PYTHONPATH=site-packages;app`
与 `PYTHONDONTWRITEBYTECODE=1`。

**为什么前端直接调解释器、不走 `run-backend.bat` / `.sh`**：中间多一层 shell 会让
"停止后端"变成"杀掉 shell、Python 还活着"，而前端是按子进程管理后端的（终止、退出码、
stdin/stdout 管道）。启动脚本仍然产出，用途是**给人手动启动/调试**。

优先级上它排在 PyInstaller 可执行文件**之后**：两者都在时优先用可执行文件。

## 三、任务二：后端改为跨平台分发（实现完成，产物受阻于网络）

### 方案

`tools/pack_backend.py`：**python-build-standalone + 自建加载脚本**。
在 Windows 打包机上产出三平台后端，目标机解压即用、无需装 Python、无需联网。

产物结构（这就是任务书要的"目录结构判断"）：

```
publish/backend-<rid>/
    python/              standalone CPython（build 20261003，3.13.16）
    site-packages/       pip 交叉下载的依赖（**与解释器并排，不合并进 python/**）
    app/                 后端代码（backend/ 的 *.py、lang/、config.json）
    run-backend.bat      Windows 启动脚本（给人用；前端不经过它）
    run-backend.sh       Linux/macOS 启动脚本（exec，信号与退出码原样透传）
    manifest.json        平台 / Python 版本 / 每个依赖的实际版本 / 各部分体积
```

**为什么依赖不合并进 `python/lib/site-packages`**：并排之后"解释器自带的"与"我们装的"
一眼可分（升级解释器不会把旧依赖留在原地），manifest 也能逐项记录依赖版本；
代价只是启动时多一个 `PYTHONPATH`。任务书把这条交给 DSH 判断，这是一条有理由的选择。

### C 扩展的获取方式（实测结论，任务书要求交代）

| 项 | 实测 |
| :--- | :--- |
| `llama-cpp-python` 在 **PyPI** 上 | **只有 sdist**（0.3.35 仅 1 个文件，无 wheel）→ 在 `--only-binary` 下直接装不上 |
| 有预编译 wheel 的索引 | `--extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpu`（`requirements.txt` 里本来就写着） |
| 可用的 wheel 形态 | 0.3.35/0.3.36 发布的是 **`py3-none-<platform>`**（平台相关、Python 版本无关） |
| 三平台覆盖 | `win_amd64` / `manylinux2014_x86_64`(=`manylinux_2_17`) / `macosx_11_0_arm64` **齐全** |
| 版本选择 | 与本机开发环境一致（本机 0.3.35），不引入跨方案的版本分叉 |
| 结论 | **无需降级到纯 Python 替代方案，也无需本地编译**；任务书担心的"没有预编译 wheel"没有发生 |

其余依赖（`numpy` / `cryptography` 等带 C 扩展的）同样都有三平台 wheel。
`playwright` 自带 Node 驱动（约 100 MB）是必要的：自动化功能靠它驱动本机 Edge。

### 交叉下载的两个真实陷阱（实测确认，都已处理）

1. **pip 用"打包机"的环境标记评估目标平台的依赖。**
   为 Linux 准备依赖时，`pywin32; sys_platform == "win32"` 会被算成"需要"，
   接着 pip 去找 pywin32 的 Linux wheel（不存在）→ 整条依赖链失败：
   实测报 `ERROR: Could not find a version that satisfies the requirement pywin32`。
   修法：脚本自己解析 `requirements.txt`，按**目标平台**评估标记
   （只实现 `sys_platform` / `platform_system` 的等值判断；遇到不认识的形式**直接报错**，
   不猜 —— 猜错的后果是"某平台静默缺一个依赖"，只在目标机器上以 ImportError 暴露）。
2. **不能给 pip 传 `--abi cp313`。** `py3-none-<platform>` 的 wheel 会被 abi 过滤掉，
   然后退回 PyPI 的 sdist 而失败。去掉 `--abi`，让 pip 用兼容标签集匹配。

`pyinstaller` **不装**（构建工具，standalone 方案下目标机不需要）。

### 启动脚本与协议兼容

两个脚本都只做三件必要的事：设 `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`
（POSIX locale 下中文与 emoji 会抛 `UnicodeEncodeError` 把后端打死）、设 `PYTHONPATH`、
调解释器跑 `app/main.py`。POSIX 版用 `exec`，让后端直接接管进程。
两者都不往 stdout 写任何东西 —— stdin/stdout 的 JSON 行协议原样透传。

### 体积（win-x64 **已实测**；Linux/macOS 仍在产出）

**win-x64 实测**（`publish/backend-win-x64/`，`tools/pack_backend.py` 产出，
`tools/check_standalone_backend.py` 已验证结构与本平台可运行）：

| 组成 | 实测 |
| :--- | ---: |
| 包内解释器 `python/` | 约 127 MB（已清理测试套件 / IDLE / tkinter / ensurepip / `__pycache__` 等约 17.5 MB） |
| 依赖 `site-packages/` | **261.2 MB**（520 个目录层） |
| 后端代码 `app/` | 约 1 MB |
| **解压后合计** | **388.3 MB** |
| 对照：PyInstaller onedir（Windows，上一轮） | **246.9 MB** |
| 对照：任务书预估 | 100–150 MB |

**统计口径（必须说清，否则数字会互相矛盾）**：以上按「磁盘实际占用」统计 ——
`dir_size()` 按 `(st_dev, st_ino)` 去重、符号链接只计链接本身。
原因是解压 Linux/macOS 的 tar 包时，tar 里的符号链接会被还原成**硬链接**
（Windows 建不了符号链接，见 `extract_python`），两个名字共享同一份数据；
不去重就会把同一份数据算两次 —— 实测 `libpython3.13.so` 与 `.so.1.0` 各被算了 136.6 MB，
得出 526 MB 这个虚高的数字。

**一个被推翻的中期结论（值得记）**：最早的报表写着"Linux 537.8 MB，比 Windows 388.8 MB 大 149 MB"。
那 149 MB 里有 **136.6 MB 是解压与统计缺陷造成的假象**，不是真实差异。
按去重口径重算，Linux 的 `python/` 约 **389.5 MB**（Windows 同项 125.8 MB，
差异来自 Linux 的 `bin/` 更大，这部分是真实的）。
**教训**：跨平台体积对比必须在"解压方式正确 + 统计口径一致"之后做，
否则会得出一个方向都错的结论，并且它看起来很可信。

**结论：standalone 方案比 PyInstaller 大约 57%（388 vs 247 MB），且远高于任务书预估。**
原因不是"依赖装多了"——`site-packages` 里最大的一项是 `playwright` 的 Node 驱动，
而 PyInstaller 版**同样要带它**（自动化功能靠它驱动本机 Edge）。真正的差异在于
**standalone Python 携带完整标准库（约 127 MB），而 PyInstaller 只收集被实际 import 的模块**。
可优化空间见第九节未完成项（更激进的标准库裁剪；本轮只删了明确与 EchoDesk 无关的部分，
"删多了会让某个边缘功能在运行期才报 ImportError"这个风险必须由证据而不是猜测来承担）。

以下是产出前的预估，保留用于对照"预估 vs 实测"：

## 四、任务三：Windows 安装包——**判断为不需要改动**（并说明理由）

任务书要求"确认 `installer.iss` 的文件清单同步更新""确认卸载清单覆盖新方案产生的运行期文件"。
本轮核对后的结论是：**Windows 正式交付物继续使用 PyInstaller onedir，安装包内容不变**，
因此清单与卸载清单都无需改动。理由（任务书本就把"是否保留 PyInstaller"交给 DSH 判断）：

1. **WPF 版的启动路径不支持"解释器 + main.py"**：`frontend/Services/BackendService.cs`
   的 `ResolveBackendPath()` 只返回一个 exe 路径，进程启动处没有参数与脚本模式字段。
   切换 Windows 后端方案就要改动这段经四轮迭代验证过的进程管理代码。
2. **Windows 上 standalone 没有收益**：PyInstaller 在 Windows 本机就能构建，
   体积相当（246.9 MB），而 standalone 带来的"跨平台"价值在 Windows 上完全用不到。
3. **避免回归风险**：安装包的真装真卸门禁、`selftest`、`ui_probe` 断言都建立在
   现有 `app/backend/EchoDeskBackend.exe` 布局上；换布局要重验一整条链。

**因此**：standalone 方案用于 **Linux/macOS 与跨平台便携包**（Avalonia 前端 + 包内解释器），
Windows 安装包（WPF + PyInstaller）不动。这是一条**刻意的取舍**，不是遗漏。
`installer.iss` 的文件清单与 `[UninstallDelete]` 本轮**未修改**，因为没有引入新的运行期文件类型。

## 八、关键决策一览（每条：背景 → 选择 → 理由 → 影响）

1. **SSH 全链路，并修掉门禁与它的冲突**
   背景：HTTPS 推送反复被中断；任务书要求统一 SSH，但门禁把 SSH 地址当邮箱。
   选择：改脚本 + 改门禁 + 加专门门禁，三处一起钉住。
   理由：只改一处的话，下次改动就漂回去；而"绕过门禁"（运行时拼 URL）是藏问题。
   影响：`git@github.com` 类地址在仓库里合法；`records/` 与网页链接刻意不动。

2. **前端改成"骨架 + 每页一个 UserControl"**
   理由与影响见第二节。行为对齐 WPF，结构不对齐。

3. **Windows 安装包不切换到 standalone**
   理由见第四节。影响：任务三的结论是"确认无需改动"，而不是"改了"。

4. **依赖目录与解释器并排（不合并）**
   理由：可区分、可记录、升级干净。影响：启动需注入 `PYTHONPATH`（两处：启动脚本 + 前端）。

5. **前端直接调解释器，不经过启动脚本**
   理由：进程终止与退出码语义干净。影响：启动脚本只服务人，不服务前端。

6. **按目标平台自己评估依赖环境标记，遇到不认识的标记直接报错**
   理由：pip 用 host 标记评估目标平台（实测踩到）；静默猜错只在目标机器上暴露。

7. **pin `llama-cpp-python` 到与本机一致的版本**
   理由：三平台 `py3-none` wheel 齐全且已验证；避免"两个打包方案装不同版本"。

8. **未迁移的页签给"未迁移说明 + 替代做法"，不给空白面板**
   理由：与第一轮降级策略同一口径；用户需要知道"该怎么办"而不是"这里什么都没有"。

## 十、本轮踩到的新坑（值得记）

1. **`pwsh` 后台任务被 kill 时，它的 Python 子进程不会被一起杀掉。**
   实测：`job_kill` 之后 Python 仍在继续下载并写 `.part` 文件，
   而 `job_output` 已经看不到它的任何输出 —— 于是"看起来停了、其实还在跑"。
   若此时启动第二个下载器写同一个文件，就会得到损坏的产物。
   避免：kill 之后用 `Get-CimInstance Win32_Process` 核对进程，别只看 job 状态。
2. **urllib 拿不到 GitHub Release 的资源，curl 可以。**
   同一个 URL：urllib 正常收到 302 之后**一个字节都收不到**（挂十几分钟、`.part` 为 0）；
   curl 能下（40–70 KB/s）。慢链路还必须能续传 —— 最终脚本优先用 `curl -C -`。
3. **不要用 `pwsh -Encoding utf8NoBOM`。** 本机 shell 实为 Windows PowerShell 5.1，
   该枚举值不存在（报 `Cannot convert value "utf8NoBOM"`）。写无 BOM 文件用
   `[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`。
4. **`Avalonia.*` 与 `EchoDesk.Avalonia.*` 的命名冲突**：在 `namespace EchoDesk.Avalonia.Views`
   里写 `new Avalonia.Thickness(16)` 会被解析成 `EchoDesk.Avalonia.Thickness` 而编译失败。
   要么 `using Avalonia;` 后用短名，要么 `global::Avalonia.…`。
5. **语言包分片的覆盖顺序**：`Loc` 按 `<locale>.json` → `.main.json` → `.settings.json`
   顺序加载并覆盖，所以 `settings.*` 的最终取值来自 **`.settings.json`**。
   新增键要加在那个分片里（只改 `.json` 会被覆盖掉）。
6. **pip 的参数行既不能整行传、也不能拆分后逐行写进 requirements 文件**（连续踩到两次，
   而两次的症状都被"网络很慢"的噪音盖住了，第一次差点被归因成网络问题）：

   | 错误做法 | pip 的反应 |
   | :--- | :--- |
   | 把 `--extra-index-url https://…` 整行当成**一个** argv | `no such option: --extra-index-url https://…` |
   | 把 `shlex.split()` 后的结果**逐行写进** requirements 文件 | `ERROR: Invalid requirement: --extra-index-url`（选项与它的值被拆成两行，pip 把选项名当成依赖名） |

   正确做法：命令行传 `shlex.split(line)` 的结果；requirements 文件里**只写依赖行**，
   选项最多作为注释记录。**教训**：慢网络下的失败不要先归因于网络 —— 先把日志读到底，
   本例中三次失败只有第一次是网络问题。
7. **"GitHub Pages 上的 wheel 索引"不等于"不走 github.com"**：`abetlen.github.io` 只提供索引页，
   wheel 的实际下载地址重定向到 **github.com 的 Releases** —— 于是它受同一网络波动影响。
   pip 默认连接超时 15 秒，在这种链路上会整轮失败；`pack_backend.py` 因此显式传
   `--timeout 120 --retries 8`。
8. **在 Windows 上解压 Linux/macOS 的 tar 包，会把符号链接变成实体文件副本（体积虚增一倍）**。
   实测：`publish/backend-linux-x64/python` 解压后 **537.9 MB**，而同一方案在 Windows 上只有 125.8 MB。
   拆开看原因很清楚：

   | 项 | 实测 | 说明 |
   | :--- | ---: | :--- |
   | `lib/libpython3.13.so` | 136.6 MB | 实体 |
   | `lib/libpython3.13.so.1.0` | 136.6 MB | **本应是上面那个文件的符号链接**，被解压成了第二份实体 |
   | `bin/` | 231.5 MB | 同类情况（多个 N MB 的重复副本） |

   `tarfile.extractall()` 在 Windows 上**无法创建符号链接**（需要特权或开发者模式），
   于是把链接目标复制成了实体文件。产物**功能上仍然可用**（内容相同），但：

   * 体积翻倍，并**掩盖真实体积** —— 会让"standalone 比 PyInstaller 大多少"的判断失真；
   * 打个不准确的包分发出去，用户解压后同样会看到虚胖的目录。

   **修法（未完成项）**：解压时把 tar 里的符号链接成员改为创建**硬链接**
   （NTFS 支持硬链接且无需特权），既保留链接语义又不虚增体积。
   在真正能建符号链接的平台（Linux/macOS/CI）上则应原样创建符号链接。

   **这条也提醒了一件事**：本轮给出的"standalone 388 MB / 537 MB"数字里，
   Linux 那个数字**含有虚增**，不能直接与 Windows 版对比 —— 对比必须在修正解压方式之后再做。
9. **Avalonia 的 `TextBox` 没有 `ScrollBarVisibility` 属性**（WPF 的 TextBox 有）。
   写 `VerticalScrollBarVisibility="Auto"` 会编译报
   `AVLN2000: Unable to resolve suitable regular or attached property`，
   而报错信息**不会**告诉你"这是两个框架的差异"，很容易误以为是拼写问题。
   修法：用一个 `ScrollViewer` 包住 TextBox。
   这类"WPF 有、Avalonia 没有"的差异本轮已踩到四处：`FlowDocument`（整体重写为控件树）、
   `TextBox.Watermark`（改 `PlaceholderText`）、`DataTransfer` 取代 `e.Data`、
   以及这一条。**规律**：凡是从 WPF 版照搬 XAML 属性，都要先确认 Avalonia 有没有它。
10. **`Avalonia.*` 的命名冲突会反复咬人**：在 `namespace EchoDesk.Avalonia.Views.Settings`
    里写 `Avalonia.Input.Key` 会被解析成 `EchoDesk.Avalonia.Input.Key` 而编译失败（`CS0234`）。
    正确写法是顶部 `using Avalonia.Input;` 之后用短名 `Key`。本轮**第二次**踩到
    （第一次在 `SettingsWindow.axaml.cs` 写 `Avalonia.Thickness`）。
    写任何 Avalonia 代码前先决定"这一处用短名还是全名"，比事后修省事。
11. **Avalonia 的控件没有 `ToolTip` 属性**（WPF 的 `Control` 有）：提示是**附加属性**，
    在对象初始化器里写 `ToolTip = "..."` 会编译报 `CS0117: Button 未包含 ToolTip 的定义`，
    必须用 `ToolTip.SetTip(control, text)`。这是本轮第 5 处同类差异
    （前四处：`FlowDocument`、`TextBox.Watermark`、`e.Data`/`DataTransfer`、
    `TextBox` 无 `ScrollBarVisibility`）。
    **规律已经很清楚**：从 WPF 版**照搬属性名**是本轮最高频的编译错误来源 ——
    XAML 属性还好（编译期就报错），代码里设属性更隐蔽（写成初始化器才报）。
    写新页面时先把"这些属性 Avalonia 有没有"过一遍，比编译三遍快。

## 十一、中期结论与自我纠正（三条）

这一节记的是"说过、后来被自己推翻"的判断。**留在记录里而不是删掉**，是因为它们的错法
都很像对的 —— 下次遇到同类情形能更快反应过来。这也是这个仓库一贯的口径：
把"当时为什么这么判断"和"后来证据怎么推翻它"一起留下，比只留最终答案有用。

| 中期结论 | 实测结果 | 错在哪里 |
| :--- | :--- | :--- |
| "三次构建失败都是网络问题" | **只有第一次是。** 第二次是 pip 选项整行当成单个 argv（`no such option`），第三次是选项被拆成两行写进 requirements 文件（`Invalid requirement`） | 慢网络会**掩盖**自己的代码缺陷：失败信息里满是超时与重试，很容易停在第一层归因就不再往下读 |
| "Linux 537.8 MB，比 Windows 388.8 MB 大 149 MB" | 其中 **136.6 MB 是解压+统计缺陷造成的虚增** | Windows 上 `tarfile.extractall()` 建不了符号链接 → 复制成实体；统计又按逻辑大小算 → 同一份数据算两次 |
| "Linux `python/` 去重后约 389.5 MB" | 实际 **235.2 MB** | 那个数是"只去重 `libpython` 一对"的粗算，而实际建立了 **1047 个硬链接**，去重收益少算了 154 MB |

**共同教训**：这三条都不是"数据采错了"，而是**口径错了**（归因口径、解压口径、统计口径）。
体积、性能这类数字，**先把口径写下来再给数**，否则数字会以最可信的样子骗人。

### 12.1 转折点：网络恢复，但真正的坑不在网络

链路恢复后（实测 5–30 MB/s）三平台解释器很快就下完了。然后暴露出两个**与网速无关**的缺陷 ——
它们在任何网速下都存在，只是慢网络会让它们伪装成"又是网络问题"：

**缺陷一：macOS 的 `llama-cpp-python` 轮子在上游就是坏的。**

| 观察 | 结论 |
| :--- | :--- |
| `pip install --platform macosx_11_0_arm64` 失败，报 zlib 解压错误 | 第一反应是"下载坏了" |
| 重新下载，**字节数与官方 digest 完全一致** | 不是下载问题 |
| 逐成员解压校验：103 个成员里 46 个坏（全是 `lib/*.dylib`） | **上游发布的文件本身是坏的** |
| 换版本：cpu 索引 0.3.21 / 0.3.30 / 0.3.35 / 0.3.36 全坏 | 不是个别版本的问题 |
| 换索引：metal 索引 0.3.31～0.3.36 也坏，**0.3.30 完好且所有 dylib 都是合法 Mach-O** | 定位到唯一的可用组合 |

另外两件必须知道的事实：**PyPI 上 `llama-cpp-python` 只有源码包**（所有轮子都在作者自己的
GitHub Releases 索引里），而 **cpu 与 metal 两个索引里存在同名但内容不同的文件** ——
所以"用索引 + 版本号"挑是不确定的，只能**按直接 URL 钉死**那一个完好轮子。

处理：`backend/requirements.txt` 里 macOS 走金属（Metal）索引的那个轮子、按 URL 钉死；
Linux/Windows 不变（它们的轮子实测完好）。这不只是绕过缺陷 ——
**metal 构建对 macOS 本来就更正确**（启用 Apple GPU 后端）。

**缺陷二：官方有体积小一半的解释器变体，我们一直在用大的那个。**

python-build-standalone 的每个平台都同时发布 `install_only` 与 `install_only_stripped`
（共 179 vs 179 个资产）。实测差距（同一次 Release）：

| 平台 | `install_only` | `install_only_stripped` | 省 |
| :--- | ---: | ---: | ---: |
| Linux x86-64 | 71.8 MB | **33.5 MB** | 38.3 MB |
| Windows x86-64 | 45.2 MB | **21.0 MB** | 24.2 MB |
| macOS arm64 | 24.2 MB | 24.1 MB | 0.1 MB |

可以放心剥：调试符号只在用 gdb/lldb 调**原生**崩溃时才需要，Python 自己的 traceback
来自 `.py` 源码与符号表里的 Python 函数名，与 DWARF 无关。
需要原生调试时用 `--keep-symbols` 换回未剥离的变体。

> **自我纠正**：前面把"体积偏大"归因到"完整标准库"，并打算做**标准库裁剪**。
> 真正的账是：Linux 的 `python/` 里 136.6 MB 是 `libpython3.13.so`、
> 77.2 MB 是 `bin/python3` —— 两者都是**未剥离的原生二进制**，不是"模块多"。
> 标准库的 `.py` 文件加起来才几十 MB，其中最该删的（test / idlelib / tkinter /
> ensurepip / distutils / __pycache__）早就删了。**先量再裁**这条在这里又一次成立：
> 若按原计划裁标准库，收益远小于风险（删掉某个冷门模块只会在目标机上以 ImportError 暴露）。

顺带做了两处**可达性论证清楚**的裁剪：
* `tkinter` 的 Python 包已删 → `libtcl9*.so`/`libtk9*.so`/`tcl9/`/`tcl*.dll`/`libs/`
  再无任何 import 能加载（约 7 MB/平台）；
* `Lib/site-packages`（10.2 MB，standalone Python 自带的 pip 等）与 `include/`（1.7 MB）。

### 12.3 第 9 个前端模块：主窗口各功能面板（**已完成**）

设置窗口的 7 个页签此前已迁移完，本模块补上主窗口剩下的功能面板。逐项对应 WPF 版：

| 面板 | 实现要点 | 与 WPF 版的一致性判据 |

| 运行指标 | 首 token / tps / tokens / 耗时，全部由后端上报 | 前端不做任何估算 |

**危险指令的二次确认是本模块唯一"换了做法"的地方，值得记下来**：
Avalonia 没有 `MessageBox`；设置页已有的做法是"再点一次按钮确认"，而指令面板是 **Enter 驱动**的，
没有按钮可点。于是改成：第一次按 Enter 把指令放回指令输入框并提示"再按一次 Enter 确认执行"，
第二次才真的执行。判据是"输入框里现在就是这条危险指令"，用户改一个字即重置。
这与 WPF 版**行为等价**（都要求两次明确动作）但**形式不同**，属记录在案的偏差。

编译证据：`dotnet build` **0 错误 0 警告**（此前一直有 1 条既有警告，本轮顺手清掉）。

**一处自查发现并修掉的隐患**：`RenderTranscript()`（换字号/换语言时整屏重建）会
`MessagePanel.Children.Clear()`，而 Agent 步骤区**不在 `_transcript` 里**（它是过程信息，
与消息正文分开存），于是它被从可视树上摘掉、而字段引用还指着那个已脱离的容器 ——
流式过程中若刚好切了字号，后续步骤行会往一个看不见的容器里追加，
界面表现就是"Agent 步骤突然不动了"。修法是重建时**同时清空引用**。
这类"引用还活着、但对象已经不在树上"的缺陷不会报错、也不会崩，只会静默少显示东西。

### 12.7 本节新增的坑（值得记）

12. **`_read_line` 里的"超时就丢弃的读线程"会把下一行偷走。** 原实现每次读一行新起一个
    线程、超时就把它丢掉 —— 被丢掉的那个线程**仍然阻塞在 `readline()` 上**，
    下一行数据到来时被它先取走，调用方于是永远读不到，表现为"后端明明回了、脚本说没拿到"。
    单动作验证时没暴露（最多超时一次），加上"连续多个动作"的探测后**立刻复现**：
    四个动作全部报"没拿到预期响应"，而手工探查显示后端每个都正常回复。
    改为**常驻读取线程 + 队列**后全部通过。
    教训：**"超时就放弃"在并发读流上不等于"取消"** —— 放弃的是等待，不是那个还在读的人。

13. **`status` 不是后端动作。** 探测表里一开始写了 `("status", "context")`，结果它照样返回了
    一大堆字段（"未知动作"藏在 `content` 里），断言"响应里有 `context` 字段"差点通过。
    断言必须选**只有那个动作才会产生**的字段，否则"未知动作"也能骗过门禁 —— 这与记录里
    早先那条"不要断言内容非空"是同一个错误的不同马甲。

14. **验证脚本本身不能依赖网络。** 最初的动作集里放了 `market_status` / `automation_status`；
    前者会去连技能市场、后者会碰 Playwright。一条会因为"网慢"而失败的验证等于一条会撒谎的
    验证，因此最终只保留 `commands` / `capability` / `context` 三个纯本机动作。

15. **`--reuse-python` 会让人误判"改造没生效"。** 用它重跑 osx-arm64 时，
    输出与改造前**一模一样**（354.3 MB / 120.7 MB），一度以为 stripped 变体对 macOS 无效果 ——
    实际是它复用了**旧的、未剥离的**解压目录。看到"数字一点没变"时，
    先确认这一步到底有没有真的重新执行，而不是先去解释差异。

16. **打包脚本里把"打包机平台"当成"目标平台"用了 —— 这是本轮第三次同类错误。**
    `pack_crossplatform.py` 里解释器路径写成
    `"python/python.exe" if ps.kind() == "windows" else "python/bin/python3"`，
    于是**在 Windows 上为 Linux 打包**时，它会去 Linux 产物里找一个根本不存在的 `python.exe`，
    整轮以"产物结构不符"失败。修法是由 `rid` 推出路径（`rid.startswith("win")`），
    并补一条自证：读后端清单，断言它的 `rid` 与本次目标一致 —— 文件存在性检查挡不住
    "两个平台产物同名同结构"这种情况，清单才是唯一记录"这份产物是给谁打的"的地方。
    前两次同类错误：pip 用打包机的环境标记（去要 Linux 版 `pywin32`）、
    前端的 `ReadyState` 判断。**规律**：只要代码里同时存在"打包机"和"目标"两个平台概念，
    就必须明确每一行读的是哪一个 —— 默认读到的是打包机，而需要的是目标。

17. **管道过滤 + `foreach` 会把失败静默吞掉。** 我用
    `foreach($rid in ...){ python ... | Select-String '^\[pack\]' }` 跑三平台打包，
    看到三段 `[pack]` 输出、作业退出码 0，就记下了"三平台完整发布物已产出"。
    实际上：`Select-String` 把 python 的错误栈**过滤掉了**，而 `foreach` 的退出码
    只反映**最后一次迭代**（win-x64 成功）—— 中间的两次失败既没显示也没影响退出码。
    下一次单独重跑 linux-x64 才看到真正的错误。**教训**：批量跑多个目标时，
    (1) 不要用过滤器替代原始日志（要过滤就把原始日志落盘再过滤）；
    (2) 逐个检查退出码并累加，不要让循环的退出码代表整个批次。
    这条与第十一节"慢网络掩盖自己的代码缺陷"是同一个毛病的另一面：
    **让失败看起来像成功的，往往是自己的观测方式，而不是被观测的东西。**

18. **归档格式与权限位：又一次主机/目标混淆，而且是"双重"的。**
    `archive_fmt = "zip" if ps.kind() == "windows" else "tar.gz"` 用的是**打包机**平台，
    于是三平台全出 `.zip`（与文档里写的 `tar.gz` 不符）。改成按 `rid` 判断之后，
    第二个问题才露出来：`tarfile.add(tree, arcname=name)` 会把**打包机的权限位**写进归档 ——
    Windows 上 NTFS 没有 Unix 权限位，`st_mode` 只有 0o666/0o777，
    于是**从 Windows 打出的 Linux/macOS 归档解压后所有文件都没有可执行位**，
    用户必须先 `chmod +x`。"用 tar.gz 就能保留权限"这句话只在**在 Unix 上打包**时成立，
    而本项目的跨平台包恰恰是刻意在 Windows 上交叉准备的。
    修法：自己走目录树构造每个条目的 `TarInfo`，按**显式策略**给权限位
    （目录与 `app/backend/python/bin/` 下全部 0o755，`start.sh`/`app/EchoDesk`/
    `run-backend.sh` 0o755，其余 0o644），并且**必须"先目录后文件"** ——
    tar 是流式的，写到某个路径前它的父目录要已经出现过。

### 13.3 为什么文档替换要用白名单而不是全文替换

文档里同时存在两类 `v0.2.1`：

* **指当前发布版本/当前产物** → 要改：`EchoDesk-v0.2.1-Setup.exe`、`Start-EchoDesk-v0.2.1.lnk`、
  `用户手册（v0.2.1）`、EULA/PRIVACY 的 `Version: v0.2.1`；
* **指历史上的 v0.2.1** → **不能改**：`v0.2.1 起不再依赖 pyxtxt`、`As of v0.2.1`、
  `PDF 文本提取自 v0.2.1 起由 AGPL 的 PyMuPDF 换成 BSD 的 pypdf`、
  `v0.2.1 或以后版本`、以及所有 `records/v0.2.1-*.md` 与 `prompts/*v0.2.1*` 的引用。

全文替换会把历史叙述改错，而**历史叙述恰恰是这个仓库最看重的东西**（"哪些是当时的事实"
决定了后来的人能不能判断某条结论还成不成立）。因此替换用的是**精确 token 白名单**
（只列"指当前版本"的写法），脚本与预览都在 `artifacts/sweep_version.py`
（不入库，属一次性的迁移工具），替换后的剩余引用逐条人工确认过类型。

同一原则的另一面：`records/` 下的**文件名保持 `v0.2.1-跨平台-2记录.md` 不变** ——
它记的是"撰写时的任务书编号"，不是发布版本号。改文件名会让既有引用（文档、其他记录）
全部失效，而保留它只需在 CHANGELOG 与 `backend/version.py` 的注释里说明一次口径。

### 13.4 与上一节的连带影响

* 三平台后端产物里打包的 `app/version.py` 也随之变成 `v0.2.2`，
  因此**必须重打**（`--reuse-python --reuse-deps` 只重拷 `app/` 与重写归档，几分钟）。
