# v0.2.1 能力扩展-1 记录

任务书：`prompts/EchoDesk-v0.2.1能力扩展-1.md`（七项任务）
前置轮次：`records/v0.2.1-优化已知问题-2记录.md`、`records/v0.2.1-系统提示词重构记录.md`

任务书的性质是"能力扩展"（还缺什么），不是缺陷修复（做得不对）。因此本轮的记录结构是：
**先审计现状 → 再定取舍 → 再实现 → 最后如实交代体积与未完成项**。

审计阶段派了三个只读子代理分别摸清插件生态、模型管理、Agent/MCP/RAG 基建，
结论都带 `文件:行号` 证据，本文只摘录影响决策的部分。

## 二、与任务书的偏差（逐项交代取舍）

| # | 任务书的说法 | 本轮做法 | 为什么 |
| :--- | :--- | :--- | :--- |
| 1 | 任务二："**参考之前讨论的 pre/ask/guard/execute/post 五段流水线**" | 只落地**权限分级 + 预授权 + 统一执行入口**（`ToolRegistry.run`），不引入五段中间件 | 既有记录已经就"为一个调用点引入一套抽象层是有了形状没有内容"做过判断；本轮真正的需求是"哪些工具能自动跑、哪些必须先授权"，而这用三档分级 + 授权名单就能表达清楚。execute 前后的观测点在事件流（`tool_call`/`tool_result`）与 `registry.calls` 审计里，没有另造生命周期钩子 |
| 2 | 任务二："权限确认的粒度（每次确认 vs 会话级授权 vs 白名单）" | 选**会话级/配置级预授权 + 默认最小权限**：敏感工具默认关闭、授权写进 `config.json` 长期生效 | 每次弹窗在本地小模型的快节奏循环里会被用户点烂，最终结果是"整个功能被关掉"；默认关闭 + 一次性授权既安全又可用。写文件/执行命令这类**真正不可逆**的操作本版干脆不提供工具（权限最小化），比"弹窗确认"更彻底 |
| 3 | 任务三："是否本版实现，还是先定义接口、后续接入" | **本版实现 stdio 客户端**，HTTP/SSE 与 resources/prompts 留待后续 | 自研约 200 行、零新依赖、可用随包示例服务器端到端验证；"先定义接口"会得到一个无法验证的空壳 |
| 4 | 任务三："MCP 客户端的依赖选择与体积影响" | 不引入官方 `mcp` 包（会带 anyio/httpx/starlette 等只对服务端有用的依赖） | 发布物体积卡在 350–400 MB；协议本体是 JSON-RPC 2.0，自研可控可测。代价是只支持 stdio，已写进文档与未完成项 |
| 5 | 任务六："检索方案（关键词 / 向量 / 混合）" | **关键词 BM25**，`config.retrieval.mode` 预留 `hybrid`/`vector` | 见上面审计表与模块说明：向量库 + 嵌入模型对体积与"换模型即失效"两点都不划算；关键词可解释、溯源可信 |
| 6 | 任务一："模式数量由 DSH 决定" | 定为 **3 个**（chat / contract / agent） | 判定标准是"用户能不能一眼说清该用哪个"：chat=普通对话、contract=专业审查（有硬格式与免责要求，合并会丢能力）、agent=可调工具。summary/translate/code/creative/guide 的差别只是提示词，搬进任务模板后概念少 4 个、能力一个没少 |
| 7 | 任务一："被移除模式的能力以指令或任务模板的形式保留" | 除模板外，**旧模式名与旧编号仍然可用**，会自动切模式 + 套模板 + 沿用旧温度 | 只保模板不保旧名字，等于让老用户改习惯；而"自动迁移 + 一句说明"几乎没有成本 |
| 8 | 任务五："推理参数可视化的范围（哪些参数值得暴露）" | 暴露 4 个采样参数 + 生成预设 + 上下文策略 + 2 个开关；**不暴露** `n_threads`/`n_batch`/`n_gpu_layers` | 后三个是"改错了会跑不动"的硬件相关参数，而且设置窗口里没有任何解释空间能让普通用户判断该填什么；要调请改 `config.json`（`/status` 会显示实际生效值） |
| 9 | 任务三："与现有技能系统的关系" | 写成对照表进文档：技能=给 EchoDesk 加功能（指令/面板/钩子/解析器），MCP=让 Agent 多几个外部工具；**MCP 工具走 Agent 的同一套权限与审计** | 两套规则并存是概念混乱的温床；MCP 工具被包装成普通 `Tool` 进同一个注册表，权限、可见性、可中断全部复用 |
| 10 | 任务七："多语言与文档" | 语言包键补齐（中英一致）、`USER_GUIDE`/`FAQ`/`DEVELOPER`/`SKILL_GUIDE` 更新 | 由子代理执行，`check_lang.py` 与 `check_docs_links.ps1` 作为客观门禁 |

## 三、本轮实现

### 3.1 任务一：模式简化（`conversation.py`）

* `MODES` 从 7 个降到 **3 个**：`chat` / `contract` / `agent`（chat 由原 general 改名而来，
  contract 一字未动地保留其专业角色与硬输出要求，agent 是新写的）。
* 新增 `LEGACY_MODES`（旧名 → 要套用的模板 id）、`LEGACY_NUMBERS`（旧编号 → 旧名）、
  `LEGACY_TEMPERATURES`（旧温度预设），以及 `canonical_mode()` / `legacy_template()` /
  `legacy_mode_note()` 三个纯函数。
* 迁移**发生在三个入口**：`ConversationManager.__init__`（配置里的旧 `default_mode`）、
  `set_mode()`（旧名与旧编号）、`command_handler._mode()`（切模式 + 套模板 + 沿用温度 + 一句说明）。
  三处共用同一份映射表，不存在"某个入口漏迁移"。
* 语言包：`mode.desc.*` 从 7 条改为 3 条；`cmd.resp.mode_legacy` / `mode_migrated` 新增；
  `/mode` 的帮助文本改成"3 个模式 + 旧名迁移说明"。
* 前端：默认模式下拉 3 项、`/mode` 回退说明改写、`RefreshModeCombo` 的兜底从 `"general"` 改为 `"chat"`。
* 对比工具 `tools/prompt_compare.py` 同步：场景表改成"新侧 = chat + 任务模板"，
  干跑报告新增"被移除的模式 → 迁移落点"一节（让"能力没丢"这件事有可读证据）。

### 3.2 任务二：Agent 平台

* `backend/agent_tools.py`（新）：`Tool` / `ToolContext` / `ToolRegistry` 三个抽象，
  七个内置工具，`parse_tool_call()` 与 `extract_final_answer()` 两个纯函数解析器，
  以及"失败文本约定"`looks_like_failure()`。
  * 计算器用 **AST 白名单**求值（数字、四则、幂、括号、常见数学函数），
    属性访问/下标/推导式/lambda/`__import__` 一律拒绝；幂运算有上限（防本地 DoS）。
  * 解析器容错：```json 代码块、前后有解释文字、键名写成 `name`、参数平铺、嵌套括号；
    截断的 JSON 一律当普通回答（绝不抛异常）。
* `backend/agent.py`（新）：`AgentLoop` 主循环 + `AgentStep`/`AgentRun` 记录。
  * 每步非流式调用（工具调用要求严格形状，而流式下 Jinja handler 对工具语义支持有硬限制）；
  * 达到 `max_steps` 后不再执行工具，改为追加一句"不要再调工具，用已有信息给结论"再问一次；
  * 每步前后检查 `stop_event`；单条工具结果与累计注入都有字符上限。
* `backend/main.py`：`_vague_guide`（模糊提问短路，抽成一份给两条路径用）、
  `_stream_agent`（把同步循环变成流式事件：读者线程 + 队列 + 心跳）、
  `agent_registry()` / `refresh_agent_tools()` / `agent_diagnostics()` / `configure_agent()`，
  以及 `agent_state` / `agent_configure` 两个动作。
* `MODES["agent"]` 只写角色与协议要点，**工具清单与工具协议由运行期追加**
  （清单是动态的，而且模式块有 700 字符的审计上限）。
* 协议新增两类事件：`tool_call` / `tool_result`（外加进度用的 `agent_step`），
  `done` 行带 `agent` 摘要；前端在回答区之前渲染成独立步骤行（`AutomationId="AgentTrace"`）。

### 3.3 任务三：MCP

* `backend/mcp_client.py`（新）：`McpServer` 配置、`StdioMcpClient`（拉起进程、
  `initialize` 握手、`tools/list`、`tools/call`、超时、错误翻译）、`McpBridge`（多 server 管理 +
  发现 + 状态）、`register_mcp_tools()`（把 MCP 工具包装成普通 `Tool` 进 Agent 注册表，**一律 sensitive**）。
  * **读线程 + 队列**：Windows 上 pipe 的 `readline()` 会无限阻塞，靠"循环前看一眼 deadline"拦不住
    对端卡死（实测把测试挂到 600 秒超时）——与流式心跳是同一个教训。
  * 子进程环境变量默认只给最小集合（PATH/TEMP/PYTHON*），要透传的必须在 `passthrough_env` 里点名。
* `examples/mcp/echo_server.py`（新）：纯标准库示例服务器（echo_text / now 两个工具），
  既是示例也是"可执行文档"，测试真的拉起它。
* `/mcp` 指令 + `mcp_state` / `mcp_apply` 动作：状态、启停（**立即生效**）、强制连接；
  配置落 `config.json` 的 `mcp` 段。

### 3.4 任务四：插件生态（`skills_runtime.py`）

* `parse_manifest` 新增 `dependencies`（列表/字典两种写法归一）；新增
  `parse_requirement()` / `version_satisfies()` / `_version_tuple()` 三个纯函数。
* `load_all()` 在发现之后调用 `_check_dependencies()`：依赖缺失/被禁用/版本不满足 → 拒绝加载并说明原因；
  被依赖方没写版本 → 只警告放行。
* 加载期新增 `min_version` 校验（与 `APP_VERSION` 比较）。
* `_verify_declared_commands()`：声明未注册 / 注册未声明 / 什么都没声明却注册了，都写进警告与日志。
* `reload_dev()` 只卸载 `dev`/`local` 来源的那批，返回 `scope="dev"` 与 `reloaded` 列表。
* `command_handler` 的技能指令隔离改为 `except BaseException`。
* 市场安装/卸载成功后自动 `reload_all()` 并把结果写回响应（"装上就能用"）。

### 3.5 任务五：模型管理

* 前端：`frontend/SettingsWindow.Inference.cs`（新，推理参数面板）+ `SettingsWindow.xaml`
  模型页插入宿主行 + `SettingsWindow.Agent.cs`（新，智能体页：工具授权与步数）。
* 后端：`capability_settings` 的温度上限 1.0 → **1.5**（与界面滑块一致）；
  新增 `model_profile_save` / `model_profile_delete` 两个动作与 `save_profile()` / `delete_profile()`：
  字段白名单、别名校验、越界**报错而不静默夹紧**、改名（`rename_from`）、删除只删登记不删文件、
  在用档位拒绝删除。
* 顺带修正：档位写操作的结果文本统一由输出层补 ❌ 前缀（被复用的语言键保持中性）。

### 3.6 任务六：本地检索（`backend/retrieval.py`，新）

* `tokenize()`（中文 2-gram + 英文词 + **数值整体**）、`split_sentences()`（带字符区间）、
  `chunk_text()`（句边界优先、带重叠、超长句硬切）、`BM25Index`（k1=1.5/b=0.75、idf 平滑）、
  `Retriever`（多文件、增量、`as_context()` 带编号与位置的注入文本）、`config_view()`。
* 与摘要的分工落在 `main._retrieval_context_for()`：短文档不检索；长文档检索 top-k；
  **不要求问题里提到文件**（检索自己会自证：没命中就不注入）。
* `conversation.build_messages(..., retrieval_context=)`：检索片段排在所有前置材料的最前面。
* 顺带修掉 `conv.files_total_chars` 从未赋值（`config.files.total_chars` 从未生效）这个既有缺陷。

### 3.7 任务七：多语言与文档

* 语言包（中英同步）：模式说明 3 条、旧名迁移 2 条、`/agent` 与 `/mcp` 的指令说明与响应文案、
  插件依赖与版本错误、档位写操作错误、MCP 错误 —— 全部走语言包；

## 五、未完成项与已知限制

1. **MCP 只支持 stdio**：不支持 HTTP/SSE 传输，不支持 resources / prompts / sampling / roots。
   要用上这些需要换官方 `mcp` 包（届时只需替换传输实现，`McpBridge` 与 `register_mcp_tools` 不用改）。
2. **没有真实的第三方 MCP Server 联调过**：只用随包示例服务器（自己写的）验证了协议通路。
   社区 server 的 `initialize` 参数差异、非文本 content 类型、进度通知等都没有实测覆盖。
3. **Agent 的工具集是"够用"而不是"齐全"**：没有代码沙箱、没有写文件、没有执行命令（刻意的）。
   计算器只支持算术与常见数学函数（不是符号计算），日期工具只做加减与差值，
   单位换算覆盖 9 类常见单位。
4. **Agent 每步都是非流式调用**：界面上看到的是"整步出现"而不是逐字输出（有进度事件与心跳，
   不会显得卡住）。要做逐字流式需要自研"单函数强制 tool_choice"的流式循环，本版没做。
5. **模型市场详情面板仍缺几个字段**（仓库级下载量/更新时间/参数量：后端已返回、前端未消费），
   以及 `.part` 分片占用的显示与"存在未完成分片可续传"的提示；`model_hub.download_retries`
   仍不在配置白名单里（界面调不了）。
6. **能力画像缺"是否支持思考模式"**：目前只能在运行期按输出标签判断，选模型前无法预知。
7. **发布物体积仍只有"打印 + 警告阈值"，没有机器可读的硬门禁**（审计结论）：本轮没有新增依赖，
   所以没有触发风险，但这条建议后续补上。
8. **提取/检索都没有"跨文档去重"**：同一段内容出现在两份文件里会各出一条（对溯源无害，对上下文略浪费）。
9. **引导方向关键词表只有 5 类**（沿用上轮），冷门提问会落到默认三条。
10. **前端没有真机 GUI 验证**：三个前端子代理都只做到"编译通过 + 语言键完整 +
    逐字段对照后端事件形状（含用临时 WPF 工程实测'移除后重建同名元素不会 duplicate name'
    与真实请求体形状）"，没有启动 WPF 实际点选、拖滑块、跑一轮 agent 对话看步骤行排版。
    真机验证列在第七节，由维护者在打包后执行（`tools/ui_probe.ps1` 与新控件的 AutomationId
    已备好：`InferencePanel` / `AgentPanel` / `AgentToolList` / `AgentTrace` / `McpTitle` /
    `McpServerList` / `ProfileEditorPanel` 等）。
11. **前端联调发现、已在后端修掉的三个问题**（记下来是因为它们都属于"接口形状不对"，
    而不是"界面没做"）：
    * `mcp_state` 原先**不回传 `env`**，而 `mcp_apply` 是整份替换 —— 在界面上改个超时再保存
      会把 `config.json` 里手写的环境变量抹成 `{}`（静默数据丢失）。现在 `public()` 回传
      `env`/`passthrough_env`，并且 `mcp_apply` 对"没带这两个字段"的条目**按 name 与既有配置合并**；
    * `profiles_state` 原先不回传 `path`/`note`，档位编辑表单无法回填 → 已补；
    * 打包脚本原先只复制 `examples\skills\`，**没有 `examples\mcp\`**，于是设置页那个
      「＋ 加示例服务器」在发布版里会指向不存在的文件 → 已补进打包流程。
12. **刻意没做的界面项**（都属取舍，不是遗漏）：MCP 的 `env`/`passthrough_env` 只能看不能改
    （要改仍写 `config.json`）；MCP 删除没有二次确认（改动是"暂存"的，点保存才生效，
    且只动配置不动磁盘文件）；档位编辑表单是单实例（编辑 B 档时再点 A 档的编辑会丢掉未保存输入）。
13. **`⏸`（U+23F8）是 emoji 门禁的盲点**：它落在 `check_emoji.ps1` 的扫描区间之外，
    所以门禁不会要求它进降级表。本轮主动把 `⏸ → [pause]` 补进两张表（"门禁没查"
    不等于"不会显示成方块"），但**扫描区间的这个盲点本身没有修**（属工具侧，未做）。

### 6.4 真模型端到端证据（Agent 平台到底能不能用）

单元测试用的是桩 LLM，"0.6B 能不能按协议调工具"这件事必须用真模型回答
（`artifacts/probe_agent_real.py`，随包默认档 `Qwen3-0.6B-Q6_K.gguf`）：

```
问题：3000 美元按 7.2 的汇率换成人民币，再扣 5% 手续费，最后能拿到多少人民币？
[步骤] 第 1/3 步 · thinking
[工具调用] 第 1 步 -> calc {'expr': '3000*7.2*0.95'}  理由：计算汇率、手续费和最终金额
[工具结果] calc 成功（0 ms）：3000*7.2*0.95 = 20520
[步骤] 第 2/3 步 · thinking
[回答] 人民币20520元。
[完成] 步数=2 工具=['calc'] 触顶=False 用时=15633 ms
```

三点值得记下来：

1. **协议在随包默认档上确实成立**：0.6B 一次就把三个运算合成一个表达式交给 `calc`，
   拿到结果后给了正确答案（3000×7.2×0.95 = 20520）。也就是说"一行 JSON 协议"
   不是"只有大模型才玩得转"的设计。
2. **模型比预期更省步数**：它没有分三次调用（换算 → 手续费 → 合计），而是一次算完。
   所以 `max_steps=4` 的默认值对真实任务偏宽松，留作"复杂任务"的余量是合理的。
3. **一个显示细节**：`agent_step` 的 answer 阶段事件没带 `max_steps`（前端因此显示
   "第 2/None 步"），前端已按"无上限"文案兜底（`main.agent.stepNoMax`）。
   这是有意的（收敛阶段不再是"第 N/上限"），但值得知道。

**没有做的真模型验证**：多工具任务（例如"先检索文档再算数"）、工具失败后的重试、
达到步数上限的收敛路径 —— 这三条只有桩 LLM 覆盖。真模型跑一次约 16 秒，
发布前可以再多跑几组。

**一个诚实的负面发现（同一轮里第二次跑就复现了）**：把问题换成同义的
「3000 美元按 7.2 的汇率换成人民币，再扣 5% 手续费，**是多少**？」之后，
0.6B 算出的是 `3000*7.2*0.05 = 1080`（**手续费**）并把它当成最终答案。
工具调用本身完全正确（`tool_call` 与 `tool_result` 事件都对、参数也对），
错的是"它以为题目问的是手续费"。这不是平台缺陷，是 0.6B 的**理解问题**，
但用户看到的就是"答案错了"，所以：

* 在**运行期追加的工具协议**里加了一条自检要求："给出「最终答案：」之前，再读一遍用户的问题，
  确认你算的量与他问的量一致（要总额还是差额、要比例还是金额、有没有算漏一步）"；
* 记录里如实写明：**Agent 在 0.6B 档位上能用，但复杂口算题仍可能答错**，
  重要数字请用 `/mode chat` 复核或换 1.7B 档位。这比"测试全绿"更值得写下来。

### 7.3 GitHub 推送

同上一轮：远端 `origin` 已配好，但本机**没有任何 GitHub 凭据**（凭据管理器无条目、
无 `~/.git-credentials`、无 SSH 私钥），因此推送需要维护者执行
`powershell -ExecutionPolicy Bypass -File tools\push_release.ps1`
（预检 + 推送 + 失败时打印三种凭据做法）。

本轮实测：预检**全部通过**（工作区/标签/不变式/产物哈希与清单一致/远端已配置），
推送在凭据一步失败，报错是网络层的 `Recv failure: Connection was reset`
（上一轮是"读不到用户名"，说明这台机器既没有凭据、到 GitHub 的推送连接也不稳定）。

**顺带修掉该脚本的一个设计缺陷**：它把"期望哈希"写死在参数默认值里，而每次重新打包
哈希都会变 —— 于是下一次发布会以"安装程序与脚本登记的不一致"这种看起来像产物坏了的信息
失败（本轮第一次跑预检就是这样）。现在改为**以 `SHA256SUMS.txt` 为准**：按**文件名**
取出该产物的哈希再比对（只查"清单里出现过这个哈希"发现不了"清单是旧的、产物是新的"
这种更危险的情况），需要钉死某一版时才显式传 `-ExpectedSha256`。
