## 一、任务一：浏览器登录态复用（方案 A）

### 1.1 实现方案

| 任务书要求 | 实现 |
| --- | --- |
| 用 `launch_persistent_context` 指定固定数据目录 | `AutomationEngine._open_session()`：`playwright.chromium.launch_persistent_context(user_data_dir=…, headless=False, viewport=1440×900, accept_downloads=True)`；通道 `msedge` 失败时回退默认 Chromium（与原 `_launch` 的降级顺序一致） |
| 独立数据目录，与 `browser_state.json` 同级 | 新增配置项 `login_state_dir`（默认空）；空值解析为 `dirname(login_state_file)/browser_profile`，即与 `browser_state.json` 同级 |
| 首次运行引导手动登录 | `_wait_login()`：`_login_present()` 判定为未登录时暂停并提示；首次使用目录时提示语换成 `automation.login.first_run`（"首次使用需要你手动登录…"） |
| 登录态检测 | `_login_present()` 三级判据：`login_check_selector`（登录后才出现的元素）→ `login_url_keywords`（URL 关键词）→ `None`（无法判断，**不阻塞**） |
| 清除登录态按钮 | `clear_login_state()` + `main.py` 的 `automation_clear_login` 动作 + 设置窗口「登录态」区块的「🗑 清除自动化登录态」按钮（带确认框） |
| 多站点可共用一个目录 | 不做任何额外处理：浏览器本身按域名隔离 Cookie；在设置界面与文档中说明 |

### 1.2 关键决策

1. **`_BrowserSession` 收口**：`launch_persistent_context` **返回的是上下文而不是浏览器**，
   而且 Python 侧 `context.browser` 对持久化上下文**恒为 None**。原实现有 6 处调用点各自写
   `browser = self._launch(...)` / `context = self._new_context(browser)` / `browser.close()`，
   换机制必须全部改。因此引入 `_BrowserSession(playwright, context, browser, note, profile_dir, first_run)`，
   提供 `new_page()` / `pages` / `close()`（关闭顺序固定为 **context → browser → playwright**）。
   顺序不能反：先关上下文才能保证 Cookie 落盘，否则下次启动拿不到这次刚登录的会话。

2. **`login_state_file` 保留但降级为"备份/迁移"**：原机制是 `storage_state` 文件。换成持久化目录后
   它是冗余的，但直接删掉会有两个代价：老用户的登录态丢失（要重新登录）、配置导出逻辑
   （`main.py::_exportable_automation` 会 pop 掉这个键）与文档中的引用全部失效。
   因此保留为：**首次使用新目录时把里面的 Cookie 导入一次**（`_migrate_legacy_state()`，
   只导入不删除源文件），**每次会话结束再导出一份**。老用户升级后不必重新登录。

3. **未登录时中止本轮，而不是继续跑**：任务书说"暂停自动化并提示用户手动登录"。
   等满 `manual_login_wait_seconds` 仍未登录时，实现选择**中止本轮**并报
   `未检测到登录状态（已等待 N 秒），本轮不再继续`，与既有的"验证码超时则继续下一个任务"不同。
   理由：没登录的话后面每个任务都会失败，跑完再报 20 条失败对用户没有任何帮助。
   （验证码的既有行为**未改动**，因为验证码是逐任务出现的。）

4. **登录动作与验证码等待分开**：新增 `_wait_login()` 而不是复用 `_wait_manual()`。
   两者判据不同（登录态检测 vs 验证码特征）、提示语不同、超时后的处置也不同（中止 vs 继续）。

### 1.3 审计日志（任务四）

新增事件（全部只记路径、结果与计数，**不记 Cookie 内容**）：

| 事件 | 触发时机 |
| --- | --- |
| `login_state_used` | 复用了持久化目录里的登录态（`result=ok`）或无法判断（`result=unknown`） |
| `login_required` | 判定未登录、开始等待用户手动登录 |
| `login_completed` | 等待期间检测到登录成功 |
| `login_timeout` | 等待超时仍未登录 |
| `login_state_cleared` | 用户清除登录态（含删除的文件数） |
| `login_state_migrated` | 从 `browser_state.json` 导入 Cookie（含条数） |

登录成功后**立刻**调用一次 `_save_storage_state()`：用户随后强退浏览器的话，这次登录才不会白做。
审计用 `profile=<数据目录路径>`（走既有的 `_redact`），没有任何 Cookie/Token 字段。

## 二、任务二：href 提取的正确流程

### 2.1 实现方案

任务书要求"选择器只负责定位元素，不负责读取属性"，实现把四步拆开：

| 步骤 | 实现 |
| --- | --- |
| 1. 定位 | `_collect_links()` 原有逻辑（主文档 → 同源 iframe → Shadow DOM 穿透） |
| 2. 读取属性 | `_read_href(handle, base_url)`：先 `get_attribute("href")`，取不到再 JS 求值 `getAttribute('href') \|\| el.href \|\| data-href \|\| data-url`（兼容用 `<div data-href>` 承载地址的站点） |
| 3. 规范化 | `_classify_href(raw, base_url)` → `_HrefInfo(raw, url, kind)`，相对路径用 `urljoin` 拼成绝对地址 |
| 4. 特殊情况回退 | `kind` 为 `javascript` / `fragment` / `empty` / `other` 时 `click_only=True`，由 `_click_into()` **点击元素**触发跳转 |

`kind` 的完整取值与判定顺序：

| kind | 判据 | 可用 URL |
| --- | --- | --- |
| `absolute` | 带协议且在白名单内（`http` / `https` / `file` / `ftp`） | 原值 |
| `relative` | 无协议、非 `#` 开头 | `urljoin(base, raw)` |
| `javascript` | 以 `javascript:` / `vbscript:` / `about:blank` 开头 | 空 |
| `fragment` | 以 `#` 开头 | 空 |
| `empty` | 属性为空或根本没有 href 类属性 | 空 |
| `other` | 有协议但不在白名单（如 `mailto:` / `tel:`） | 空 |

### 2.2 顺带修正的两个既有缺陷

1. **伪链接被去重压掉**（严重）：`_collect_links()` 原来按 `entry.key = href or text` 去重。
   一页里几十个任务的 `href="javascript:void(0)"` 值完全相同，会被压成 **1 个任务**。
   现改为：**只有拿到 URL 的元素才按 URL 去重**，无 URL 的元素一律保留。
   实机测试里用一个含 5 类 href 的页面验证：5 个任务全部采集到（旧逻辑只剩 2 个）。

2. **`urljoin` 把伪链接拼成"看起来像地址"的东西**：`urljoin(base, "#")` 会返回 `base + "#"`，
   `urljoin(base, "javascript:void(0)")` 原样返回。前者会让程序"导航到列表页自身"并看起来成功。
   现在这两类在拼接**之前**就被拦成 `click_only`。

### 2.3 回退路径的实现

`_click_into(context, page, entry, pages_before)`（生成器，靠 `return` 传值）：
点击后用两种方式接住跳转 —— ① `_new_pages()` 找到新标签页；② 比对 `page.url` 判断当前页跳转。
两条都不成立时给出 `已点击元素，但页面既没有跳转也没有打开新标签页`。
`wizard_step()` 是同步方法、没有进度通道，因此加了一个 `_drive()` 小工具把生成器跑完并取回返回值。

`_process_one()` 相应改为：有 `href` 就 `_goto`，否则若 `click_only` 且有句柄就 `_click_into`，
并把返回的新页面当成本任务的详情页（后续定位附件、下载、截图都针对它）。

## 三、任务三：可视化选取的语义明确

### 3.1 实现方案

| 任务书要求 | 实现 |
| --- | --- |
| 选取后预览「程序将从这些元素提取以下网址：…」 | `_preview_pick()` 用选择器**回到页面里真实查一遍**，产出 `matches` / `links` / `click_only` / `hrefs`（前 5 条）/ `samples` / `warnings` / `message`，随 `done` 事件回传；前端 `ConfirmPickPreview()` 弹确认框，**点取消就放弃这次选取、不写配置** |
| 非链接元素识别 | `PICKER_JS` 额外回传 `isLink` / `hasHref` / `linksInside`；`_preview_pick()` 在"必须是链接"的位置（`task_list` / `task_detail_file`）判定为 `blocking`：这是**拦截**——不发 `done` 事件、不返回选择器（配置不会被写坏），提示语是任务书要求的那句 |
| 空 href / JavaScript 链接提示 | 非 `blocking` 的伪链接在预览里附上 `提取不到网址（JavaScript 伪链接），程序会改为点击元素触发跳转`；`_process_one` 下载附件时也会报 `有 N 个附件提取不到网址…将改为点击元素触发下载` |
| 选取语义与程序逻辑对应 | `_PICK_PURPOSE` 明确四个位置的用途与"是否必须是链接"：`task_list`=(jump, 必须) / `task_row`=(row, 不要求) / `next_page`=(click, 不要求) / `task_detail_file`=(download, 必须)；另加 `login_check`=(presence, 不要求，任务一用) |

### 3.2 关键决策

1. **预览由后端回到页面重查，而不是让注入脚本回传**：脚本回传的是"点击那一刻"的快照，
   而后端重查得到的正是**自动化稍后真正会用的那份结果**（同一套 `_collect_links`），
   两边的口径天然一致——这正是任务书要的"选取语义与程序逻辑对应"。副作用是
   `matches` 的口径是"会被处理的元素数"，而不是裸 `querySelectorAll` 计数（更好）。

2. **"非链接"是拦截而非仅提示**：任务书的措辞是"提示…请重新选择"。实现选择不返回选择器，
   理由是：一个读不到网址的选择器被写进配置后，后续每一步都会失败，而用户并不知道是自己选错了位置。
   同时把"选中容器"和"选中按钮"分成两句提示（前者指出容器里有几个链接）。

3. **页面提示条文案不再硬编码中文**：`PICKER_JS` 原来自带中文提示条。改为箭头函数、
   由后端传入 `automation.pick.banner`，跟随界面语言（英文界面不再出现中文横幅）。

4. **顺带加了一条"只匹配到 1 个元素"的提示**（超出任务书）：可视化选取生成的选择器是
   **精确到所点那一个元素**的（例如 `li:nth-of-type(1) > a.task`），而任务列表位置通常需要匹配多条。
   预览里会提醒把选择器改通用（例如 `a.task`），或在「任务行容器」里选一整行。
   这条**不拦截**（单任务站点是合法用法），只提示。

### 5.1 关于"手动登录"的如实说明

任务书要求"第一次运行时手动登录"。本机没有第二个人可以操作，因此**那一次"点登录按钮"的动作
由测试脚本代劳**（在真实浏览器里导航到 `/do-login`，等价于点了页面上的登录按钮），
其余环节（浏览器启动、Cookie 落盘、关闭、重启、复用检测）**全部是真实链路**，没有打桩。
人工登录路径另由"未登录检测"一项覆盖：程序确实会暂停并显示手动登录提示，且超时后如实中止。
这一点不构成"虚构测试结果"，但为避免误解，在此写明。

### 5.2 顺带发现并修掉的两个真实缺陷

测试写得比较实在，跑第一遍就抓到两个问题（**其中一个是本轮的回归，一个是既有缺陷**）：

1. **`PICKER_JS` 语法错误（本轮引入，已修）**：把注入脚本从 IIFE 改成箭头函数时，
   结尾仍留着 `})();`，浏览器侧报 `SyntaxError: Unexpected token ')'`，
   **可视化选取 100% 失败**。这轮之前 `pick_selector` 没有任何自动化测试覆盖，所以以前改动它不会有人发现；
   现在第 5/6 项测试真实跑完整条链路，这类问题跑一次就会暴露。
2. **`_process_one` 里 `context` 未定义（本轮引入，已修）**：把 `_run_impl` 的
   `browser/context/playwright` 三件套换成 `session` 时漏改了一处传参，导致**每个任务都失败**
   （`任务处理异常：name 'context' is not defined`），由既有 `tools/test_automation_e2e.py` 抓到。

  `docs/zh-Hans/AUTOMATION_GUIDE.md` 第十节 10.7 说明其优缺点。**未实现**。

### 6.2 已知限制（本轮不修，建议后续处理）

1. **可视化选取生成的选择器"太具体"**：拾取脚本优先返回**唯一**匹配的选择器
   （例如 `li:nth-of-type(1) > a.task`），而任务列表位置通常需要匹配多条。
   本轮的处理是**在预览里明确提示**（并引导改通用或在「任务行容器」里选一整行），
   **没有**改拾取策略。要彻底解决需要让拾取脚本按"选取位置"决定是追求唯一还是追求同构多匹配
   （例如优先返回 `a.task` 这种类名选择器），属于独立改动，风险面较大（会影响所有选取位置的既有行为）。
2. **`_download_entry` 对"点击后当前页跳转到附件"的场景不够稳**：若某个附件链接是伪链接、
   点击后浏览器**在原地内联打开**了 `.txt`/`.pdf`（没有触发下载、也没有开新标签页），
   当前实现会返回"下载失败"，并且工作页面已经被导航走，可能影响该任务后续附件的定位。
   常见站点（触发下载或开新标签）不受影响。
3. **登录检测的判据依赖用户配置**：默认的 URL 关键词只覆盖常见拼写；没有配
   `login_check_selector` 且站点用非常规登录路径（例如 `/portal/sign-in-v2` 之外的自定义路由）时，
   程序会返回"无法判断"并**继续跑**（不阻塞，但也就没有保护）。
   建议：对关键站点总是配一个"登录后才出现的元素"。
4. **测试覆盖面**：`test_automation_login.py` 用的是自建回环站点，没有覆盖真实 OA 系统的
   iframe / Shadow DOM / 多页翻页 + 登录态组合场景；`href` 的 Shadow DOM 穿透路径
   （`handle=None`，只能按 URL 请求兜底）本轮没有真机验证。

### 6.3 建议的后续动作

- 在装了 Edge 的机器上跑一次完整 `tools/verify_release.ps1`（本轮只跑了打包门禁与上述套件）；
- 若要让"选取位置=任务列表"稳定拿到多条，按 6.2 第 1 点改造拾取策略，并补一条
  "同一列表里 5 个任务全部被匹配"的断言；
- 若要支持 CDP 方案，建议做成 `automation.connect_mode = "launch" | "cdp"` 的显式开关，
  并把"以调试模式启动浏览器"的步骤写成界面引导，而不是让用户自己敲命令行。
