## 一、修复一（P0 致命）：设置窗口卡死

### 现象与真实根因

任务书描述为"点击设置后界面无响应，必须从任务管理器强制结束进程"，
并给出 5 个排查方向（UI 线程阻塞 / 请求闸门死锁 / 启动预加载阻塞 /
控件初始化异常被吞 / Playwright 初始化阻塞）。

**实测定位结果不是死锁，而是空引用崩溃导致进程被终止**：

1. 用 UI Automation 复现：启动发布版 → 点击设置按钮 → 10 秒内设置窗口未出现，
   且 `Process.Responding` 变为 `False`，随后进程自行消失（复现稳定）。
2. 从 Windows 事件日志取到决定性证据（`.NET Runtime` 事件 ID 1026）：

```
The process was terminated due to an unhandled exception.
Exception Info: System.NullReferenceException
   at EchoDesk.SettingsWindow.FontSizeSlider_ValueChanged(Object sender, RoutedPropertyChangedEventArgs`1 e)
   at System.Windows.Controls.Primitives.RangeBase.OnMinimumChanged(DependencyObject d, ...)
```

3. 机理：`SettingsWindow.xaml` 的字体大小滑块写的是
   `<Slider Minimum="10" Maximum="24" .../>`。XAML 解析按属性顺序应用值时，
   `Minimum` 先把 `Value` 从默认 `0` **强制抬到 10**，于是触发 `ValueChanged`；
   而此时 `FontSizeLabel`（在 XAML 中排在 Slider **之后**）尚未由 `InitializeComponent`
   创建，`FontSizeSlider_ValueChanged` 里的 `FontSizeLabel.Text = ...` 抛
   `NullReferenceException`。
4. 前端当时**没有任何全局异常处理器**，UI 线程未处理异常直接终止进程
   （并伴随 29MB WER 转储）。用户看到的就是"界面无响应，只能强制结束"，
   且程序目录里**没有留下任何线索**——这也是最初难以定位的原因。

> 事件日志里还能看到用户在 18:45 连续两次触发同一崩溃，与现象描述完全吻合。

### 修复内容

| # | 修复 | 说明 |
|---|---|---|
| 1 | `_uiReady` 门闩 | `InitializeComponent()` 完成前，所有由 XAML 挂接的事件处理器直接返回；`FontSizeSlider_ValueChanged` 另加 `FontSizeLabel is null` 判空；XAML 补 `Value="14"` 明确默认值 |
| 2 | 全局异常兜底 | `App.xaml.cs` 接管 `DispatcherUnhandledException` / `AppDomain.UnhandledException` / `TaskScheduler.UnobservedTaskException`，统一写入程序目录 `frontend_crash.log`，并弹提示后让程序**继续可用**（连续 5 次后不再拦截，避免带病运行） |
| 3 | 打开即见 | 设置窗口构造与显示不再做任何后端等待；数据加载改到 `ContentRendered` 之后异步执行，底部常驻一行加载状态（"正在读取配置…" → "✅ 配置已载入"），加载期间界面完全可交互 |
| 4 | 通信层可超时 | stdout 改为**唯一泵线程投递到队列**，请求方从队列取行（详见下文"关键决策"）；请求闸门等待默认 15 秒超时，响应空闲超时默认 10 分钟、重任务 45 分钟，超时抛出可识别异常并给出提示 |
| 5 | 后端忙可见 | 设置窗口对 `BackendBusyException` 自动重试并在界面显示"后端正在忙（第 N 次等待）"，而不是静默卡住；窗口关闭时取消在途请求 |
| 6 | 构造兜底 | `OpenSettings` 整体 try/catch：万一构造失败只记日志 + 提示，不再终止进程 |
| 7 | 遗留文案格式 | `HandleChatResponse` 中残留的 `"模式: x"` / `"搜索: 开"` 与状态区格式统一 |
| 8 | 对话框归属 | 启动期三个 `MessageBox`（缺少模型 / 快捷方式失效 / 是否创建快捷方式）补上 owner，避免对话框跑到主窗口后面造成"看不到提示、界面像卡住" |

### 关键决策：为什么重构 stdout 读取方式

原实现里"写请求 + 读响应"由 `SemaphoreSlim` 闸门串行化，是正确的；
但**请求一旦开始读就必须读到那一行**，否则无法安全中断——若用
`Task.WhenAny(ReadLine, Delay)` 或取消 `ReadLineAsync` 来实现超时，
被放弃的读取会在稍后"吃掉"下一条响应，造成响应错位（流式响应尤其致命）。

因此改为：**一个后台泵线程独占 stdout 并投递到 `Channel<string>`**，
请求方从队列 `ReadAsync`。这样超时只是停止等队列，**不会留下悬挂的读取**，
超时机制才真正安全。副作用是 `wait: true` 语义更清晰，也顺带消除了
"闸门外等待"与"读取中"耦合带来的隐患。

## 二、修复二（P0 数据风险）：命令栏 Enter 行为

### 现象与根因

指令列表只做**前缀过滤**并保持 `Commands` 数组的声明顺序，
`CommandList.SelectedIndex = 0` 后按 Enter 会执行列表**第一项**。
`/clearcache` 在数组中排在 `/clear` 之前，因此输入 `/clear` 再按 Enter 会执行
`/clearcache`（清空 KV 缓存）。

### 修复内容

1. **排序规则（`RankCommands`）**
   1. 与输入**完全一致**的命令排最前；
   2. 其余按**命令名长度升序**——前缀相同时，命令越短说明已输入前缀占该命令的比例越高、
      越具体（这条正好把 `/clear` 排到 `/clearcache` 前面）；
   3. 最后按指令表原有顺序（近似"常用度"），保证结果稳定可预期。
2. **不盲目执行**：当候选**多于一个且首项并非精确匹配**时，Enter **只补全命令名**并提示
   "已补全为 X，确认无误后再按 Enter 执行"，由用户看过完整名称与参数格式后再决定。
3. **列表显示完整名称与参数格式**：新增 `CommandItem.Usage`
   （形如 `用法：/model <名称|别名|list>`，无参数则显示 `用法：/clear（无参数）`），
   替换原先"Format 为空就折叠"的写法；同时给列表项加
   `AutomationProperties.Name/HelpText`（可访问性 + 回归测试锚点）。
4. **危险指令二次确认**：`/clear`、`/clearcache` 执行前弹确认框，说明后果；
   取消时**保留输入框内容**便于修改。可在「设置 → 常规」关闭
   （`ui_state.json: ConfirmDestructiveCommands`，默认开启）。

### 与任务书的偏差

- `/exit` **未**纳入确认集。任务书把它列为示例之一，但它本身已有"致谢语 + 10 秒可中断倒计时"
  的内置确认，再叠一层弹窗属于重复打断。已在下方"未完成项/偏差说明"记明。

### 实测（探针自动断言）

```
输入 '/clear' -> 首项 '/clear'（共 2 项：/clear /clearcache）
输入 '/c'     -> 首项 '/clear'（共 2 项：/clear /clearcache）
输入 '/cl'    -> 首项 '/clear'（共 2 项：/clear /clearcache）
输入 '/sum'   -> 首项 '/summarize'（共 1 项）
输入 '/s'     -> 首项 '/stop'（共 6 项：/stop /save /search /status /snippet /summarize）
在 '/cl' 上按 Enter：'/cl' -> '/clear '（只补全、不执行）

```

- 逐条对应任务书的验证用例：`/clear` 必须执行 `/clear` ✅；`/c` 因前缀长度相同，
  按"命令长度升序"取更短的 `/clear` ✅；`/s` 匹配项多，改为让用户从列表明确选择 ✅。

## 三、新增三（P1）：批量处理结果目录结构

### 目录结构（与任务书一致）

```
程序根目录\
└── 批量处理结果\            ← 顶层文件夹名可在设置中自定义
    └── 2026-09-23\          ← 运行日期 YYYY-MM-DD（同日多次运行合并）
        ├── 合同审查\         ← 任务名称（同名自动追加 -1、-2…）
        │   ├── 合同正文.txt   ← 该轮下载的原始文件（重名自动加序号）
        │   └── 结果.txt      ← 纯文本、无任何 Markdown 标记
        └── 合同审查-1\
```

### 实现

- **`backend/plaintext.py`（新增）**：Markdown → 纯文本。
  `#` 标题转为"文字 + `=`/`-` 下划线"；`**`、`*`、`~~`、反引号只保留文字；
  `-`/数字列表保留；`|` 表格转为**按显示宽度对齐**的纯文本（中日韩字符按 2 列计，
  否则中文表格在记事本里会错位）；`[文字](地址)` → `文字（地址）`；`![alt]` → `[图片：alt]`；
  代码围栏去掉并把内容缩进四格；`>` 引用缩进两格；HTML 标签剥离、转义还原；末尾压缩空行。
  另提供 `contains_markdown()` 供自检。
- **`backend/config.py`**：新增 `program_root()`（打包后取 exe 的上一级，源码运行取仓库根目录）；
  `AutomationConfig` 新增 `results_root_name`（默认"批量处理结果"）、
  `results_location`（默认空 = 程序根目录）、`task_name`（第三层目录名），
  移除旧的 `results_dir`。
- **`backend/automation.py`**：
  - `results_root` = 保存位置 / 顶层文件夹名；`_prepare_task_dir()` 创建
    `结果根目录\YYYY-MM-DD\任务名`，同名自动 `-1`、`-2`；
  - 结果文件固定 `结果.txt`，**每条任务完成/失败即整份重写**——中途崩溃或按停止，
    已处理任务的结果不丢；
  - 文件头记录任务名称、运行日期、开始时间、任务列表、任务指令、结果目录；
  - **失败任务**调用 `_save_failure()` 把失败原因与失败截图文件名写进 `结果.txt`；
  - **下载的原始文件由临时目录移动进任务目录**（成功与失败都保留），
    临时文件只在"未能移入"时才删除；
  - 失败截图从 `results_dir/errors/` 改为直接放在任务目录内；
  - `status()` 增补 `results_root` / `results_dir` / `report_path` 供界面展示。
- **前端（设置 → 自动化）**：新增「任务名称」「顶层文件夹名」「保存位置（留空 = 程序根目录）」
  三个配置项，「浏览…」文件夹选择器、「打开结果目录」按钮，以及实时目录结构预览。

### 与任务书的偏差

- 任务书示例中"任务名称A / 任务名称B"是**同一日期下的两个任务**。本实现把
  "任务名称"理解为**用户在本轮运行前设定的批次名**（设置里的「任务名称」），
  一次运行 = 一个任务目录，该轮所有任务的原始文件与汇总的 `结果.txt` 都放在里面。
  理由：任务书规定结果文件**固定命名 `结果.txt`**，若按页内每个任务各写一份会同名冲突；
  同时"同名任务自动加序号"只有在名称由用户指定时才有意义（页内任务标题天然唯一）。
- 「结果.txt」聚合整轮结果（每个任务一个分节，含失败分节），而不是每个任务一个文件。

## 四、新增四（P1）：模型选择栏

### 数据源

| 源 | 地址 | 说明 |

| 镜像源 | `https://hf-mirror.com` | 国内推荐；`auto` 模式优先 |

- 设置中可选「自动 / 镜像 / 官方」；自动模式先探测镜像可达性
  （拉一条 `limit=1` 的搜索结果），不可达则回退官方源。
- **当前使用的源始终显式告知**：搜索/详情返回值都带 `source_note`
  （如"自动选择：镜像源 hf-mirror.com（可达）"、"⚠️ 原数据源请求失败，已回退官方源 huggingface.co"），
  界面状态行与设置页都会显示。

### 功能

| 任务书要求 | 实现 |
|---|---|
| 搜索（名称/作者/标签，防抖） | `GET {base}/api/models?filter=gguf&search=...`；前端 400ms 防抖 |
| 筛选/排序（大小、量化、更新时间、下载量） | 排序：下载量 / 最近更新 / 点赞 / 名称；筛选：最低下载量 + 量化格式（可输入）；结果含更新时间与量化推断 |
| 结果展示（名称/作者/大小/量化/说明/是否需登录） | 列表显示名称、作者、⬇下载量、⭐点赞、更新日期，「● 已下载」「🔒 需登录」徽标 |
| 详情查看（所有可用 GGUF 文件） | Tab 内展开详情面板：`GET /api/models/{repo}?blobs=true`，列出全部 `.gguf` 与精确大小、量化格式、sha256、是否已下载，附许可证 |
| 下载确认（大小与预计磁盘占用） | 确认框逐项列出仓库、文件、量化、大小与"预计磁盘占用" |
| 进度（实时/速度/剩余时间/取消） | 进度条 + `📥 12.3%  64.1/507.9 MB  2.14 MB/s  剩余 03:27`；「取消下载」向后端发 `stop`，**保留断点** |
| 自动入库 | 完成后写入 `backend\models_registry.json`（模型名、路径、仓库、量化、大小、下载时间、来源） |
| 模型库管理 | 列表显示量化/来源/大小/下载时间/**最后使用时间**，当前使用中标记「▶ 正在使用」且禁止删除；删除前二次确认 |
| 断点续传 / 失败重试 | `.part` + `Range`；服务端不支持 206 时自动从头；默认重试 3 次（退避） |
| 完整性校验 | 比对文件大小；拿到 `lfs.sha256` 且文件 ≤2GB 时再比对哈希 |
| Gated 模型 | 401/403 时提示"请在「设置 → 模型」填写 Token"；Token 走 `PasswordBox`（留空不覆盖），也可用环境变量 `HF_TOKEN` |
| 与 `/model` 指令协作 | 下载目录就是 `/model` 使用的 `backend\models\`，因此 `/model list` 能识别；模型库列表把 `/model` 当前加载的模型标为"正在使用" |

### 关键决策：为什么自己实现下载而不用 `hf_hub_download`

`huggingface_hub` 的数据源由模块级常量 `HF_ENDPOINT` 决定，**导入后无法为单次调用切换**，
而"镜像/官方可切换 + 自动回退"是本任务的核心要求。自实现 urllib 下载还顺带满足了
断点续传、重试、实时速度/剩余时间、取消、完整性校验与 Gated 提示——
这些都是任务书明确要求的，用 `hf_hub_download` 反而要绕路实现。

### 已知偏差

- 搜索接口**不返回文件大小**，因此列表页不显示大小（避免为每条结果再发一次详情请求），
  大小/量化/磁盘占用在**详情面板**中给出精确值。任务书要求"每个模型显示文件大小"，
  这里做了性能与请求量的折中并在界面与文档中说明。

  全链路（4.7KB 文件：首次下载成功并入库；只留 10 字节后重新下载能补齐且内容一致；
  故意传错大小会被校验拦下）。

## 五、优化五（P2）：状态栏信息分层

### 分层方案

```
┌──────────────────────────────────────────────────────────┐
│ 📡 EchoDesk v0.2.0  Powered by … 已就绪 [🧠 模型: …] [🛠️ 模式: …] │ ← 顶部只留关键状态
├──────────────────────────────────────────────────────────┤
│                      对话区域                             │
├──────────────────────────────────────────────────────────┤
│  [输入框]                                         [发送]  │
├──────────────────────────────────────────────────────────┤
│ 🔍搜索：开 ⚙️自动化：关 🌐市场：已同步 📊上下文 1% 💾KV: 384.0 MB  ▾ │ ← 轻量状态区（可折叠）
├──────────────────────────────────────────────────────────┤
│              通知条 / 操作提示（固定高度）                  │
└──────────────────────────────────────────────────────────┘
```

- **顶部只保留**：运行状态（就绪/处理中/错误）、当前模型、当前模式。
  模型与模式做成可点击小胶囊，分别跳到「设置 → 模型」「设置 → 常规」。
  原来的搜索/自动化/市场三段从顶部移除。
- **轻量状态区**（输入框下方，任务书正文措辞；布局示意图标注为"输入框上方/下方"，
  本实现取正文的"下方"）：5 项 + 折叠按钮，全部"图标 + 简短短语"，
  每项都有 ToolTip 与 `AutomationProperties.HelpText`。
- **点击行为**：🔍 搜索 → 直接切换开关（搜索没有独立设置页，切换即"对应设置"，
  为此 `/search` 新增 `toggle` 支持）；⚙️ 自动化 → 设置→自动化；
  🌐 市场 → 设置→技能市场；📊 上下文 → 立即刷新；💾 KV → 设置→模型。
- **折叠**：右侧 `▾/▸` 按钮收起/展开，状态写入 `ui_state.json`（`StatusStripCollapsed`），
  下次启动沿用。
- **可访问性**：状态区本身与各项均有 HelpText 说明；状态文本**不再**用
  `AutomationProperties.Name` 覆盖——那会让屏幕阅读器只读到"运行状态"而**丢掉"已就绪"**这个真实状态
  （这个坑在本次修复中真实踩到并已纠正）。
- **数据来源**：后端 `_attach_context` 现在额外回传 `n_ctx` / `kv_cache_text` / `model` / `search`，
  前端不必解析 `/status` 的中文文本（同时保留文本行解析作为兜底）。

### 实测

```
轻量状态区文本：⚙️ 自动化：未启用 | 🔍 搜索：开 | 📊 上下文 1% |
                🌐 市场：已同步（当前无匹配技能）| 💾 KV: 384.0 MB
✅ 轻量状态区为图标+简短短语，且含上下文百分比
✅ 轻量状态区可折叠且可恢复
✅ 点击状态区「自动化」跳转到设置→自动化
```

## 七、偏差与未完成项（如实记录）

### 与任务书的偏差

1. **修复一未按"死锁"方向修**：真实根因是空引用崩溃（已附事件日志证据），
   但任务书关心的所有"卡死"表现都已按 5 条要求处理（异步、超时、可交互、可见加载状态、
   不阻塞 UI 线程），并额外补了全局异常兜底与崩溃日志。
2. **`/exit` 未加入危险指令确认集**：它已有致谢语 + 10 秒可中断倒计时（等价内置确认）。
3. **结果目录的"任务名称"是运行批次名**（设置项），一轮一个目录、一份聚合 `结果.txt`；
   理由见第三节"与任务书的偏差"。
4. **模型列表不显示文件大小**：搜索接口不返回大小，改在详情面板给出精确值（性能折中）。
5. **状态区位置按正文放在输入框下方**：任务书正文写"输入框下方"，布局示意图标注为
   "输入框上方/下方"，取正文口径。
6. **模型 Token 未做加密存储**：明文保存在 `config.json`（或 `config.user.json`），
   与任务书"提示用户配置 Token"一致，但未实现 Windows DPAPI 加密。

### 未完成项 / 已知限制

- **结果目录的"文件过多再分子目录"**未实现（任务书标注"默认可平铺"，当前恒为平铺）。
- **模型选择栏的下载队列**：同一时刻只允许一个下载（再次点击会提示等待），
  未实现多任务并行/排队。
- **模型选择栏不显示每个仓库的 README 摘要**（技能市场有；模型详情仅给许可与标签）。
- **`/model` 从模型选择栏下载后自动切换**未实现：下载完成后仍需用户执行 `/model` 切换并加载。
- **真实大模型下载只验证了机制**：为控制时间与流量，端到端只下载了真实小文件走完整链路；
  完整大模型（数百 MB ~ 数 GB）的下载请在真实网络下自行确认（逻辑分支已被
  `test_model_hub_e2e.py` 与单元路径覆盖）。
- **UI 探针依赖桌面会话**：`tools\ui_probe.ps1` 需要交互式桌面（UI Automation 驱动），
  在无桌面环境（如 CI 容器）中无法运行；本轮全部 UI 验证均在开发机桌面完成。
- **模型库 `last_used` 只在后端启动加载模型时更新**，运行中切换模型后需重启才刷新该字段。
- 其余 v0.2.0 既有限制（扫描件 PDF 无 OCR、自动化依赖本机 Edge、
  技能市场 topic 尚无仓库、依赖不自动 pip 安装、无代码签名/自动更新等）保持不变，
  详见 `docs\CHANGELOG.md` 的「已知限制」。
